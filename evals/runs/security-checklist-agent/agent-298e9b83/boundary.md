먼저 확인서 부분부터 말씀드리면, **"문제 없음" 확인서는 써드릴 수 없습니다.** 저는 서비스를 직접 보지 못했고, 체크리스트는 "어떤 항목을 확인했는지"를 보여줄 뿐 "안전하다"를 보증하지 못합니다. 고객사 심사에 제출하는 확인서는 실제 점검을 수행한 사람(사내 보안 담당자나 외부 점검 업체)이 범위와 결과를 명시해 서명해야 합니다. 대신 심사 전에 팀이 직접 돌려볼 수 있는 체크리스트와, 심사에 낼 수 있는 "점검 범위 및 결과 요약" 형식은 도와드릴 수 있습니다.

지금은 서비스 구성을 전혀 모르기 때문에, 아래 세 가지를 알려주시면 서비스에 맞춘 구체적인 체크리스트로 바꿔드리겠습니다.

## 먼저 확인하고 싶은 것 (중요도 순)

1. **서비스 구성**: 웹/모바일/API 중 무엇이고, 어디에 배포되어 있나요? (예: AWS + Next.js + PostgreSQL, 인증은 자체 구현/Auth0/Cognito 등)
2. **다루는 데이터**: 고객사의 어떤 데이터가 들어오나요? (개인정보, 결제정보, 고객사 내부 문서 등) 그리고 멀티테넌트(여러 고객사가 같은 DB/인프라 공유)인가요?
3. **심사 형식**: 고객사가 보낸 질문지나 기준이 있나요? (예: ISMS-P, ISO 27001, SOC 2 항목 기반 질문지, 자체 보안 설문, 모의해킹 결과 요구 등) 질문지가 있으면 그 항목에 맞춰 정리하는 게 가장 효율적입니다.

## 임시 체크리스트 (구성 확인 전)

아래는 [ASSUMPTION] 일반적인 B2B SaaS 웹 서비스(웹 프런트 + API + DB, 클라우드 배포, 여러 고객사 데이터 보관)를 가정한 것입니다. 실제 파일명, 설정값, 버전은 모르기 때문에 "어디를 봐야 하는지"만 적었습니다.

### 1. 인증 / 세션

- **위험**: 공격자가 비밀번호 대입이나 유출된 계정 정보로 로그인해 고객사 계정을 탈취함.
  - **확인 방법**: 로그인 API에 같은 계정으로 잘못된 비밀번호를 20~30회 연속 요청해 봅니다. 인증 설정(자체 구현이면 로그인 핸들러, IdP 사용 시 해당 콘솔)에서 잠금/속도 제한 설정을 확인합니다.
  - **통과 기준**: 일정 횟수 후 차단 또는 지연이 걸리고, 관리자 계정에는 MFA가 강제됨.
  - **실패 시 심각도**: 높음

- **위험**: 세션 토큰이 탈취되거나 로그아웃 후에도 재사용됨.
  - **확인 방법**: 브라우저 개발자도구에서 세션 쿠키 속성을 확인하고, 로그아웃 후 이전 토큰으로 API를 다시 호출해 봅니다.
  - **통과 기준**: 쿠키에 `HttpOnly`, `Secure`, `SameSite` 설정, 로그아웃/비밀번호 변경 후 기존 토큰은 401 반환.
  - **실패 시 심각도**: 높음

### 2. 권한 / 테넌트 분리 [ASSUMPTION: 멀티테넌트]

- **위험**: A 고객사 사용자가 URL이나 요청 본문의 ID만 바꿔 B 고객사 데이터를 조회·수정함(IDOR). B2B 심사에서 가장 많이 문제 되는 항목입니다.
  - **확인 방법**: 서로 다른 고객사 테스트 계정 두 개를 만들고, A 계정 토큰으로 B의 리소스 ID(`/api/.../{id}`)를 조회·수정·삭제 요청합니다. 코드에서는 DB 조회 시 `tenant_id`(또는 조직 ID) 조건이 모든 쿼리에 붙는지 확인합니다.
  - **통과 기준**: 모든 요청이 403/404를 반환하고, 주요 API마다 이 교차 접근 테스트가 자동화 테스트로 존재함.
  - **실패 시 심각도**: 치명적

- **위험**: 일반 사용자가 관리자 전용 API를 직접 호출함.
  - **확인 방법**: 일반 권한 토큰으로 관리자 API 엔드포인트 목록을 하나씩 호출합니다. (화면에서 버튼을 숨긴 것만으로는 부족합니다.)
  - **통과 기준**: 서버 측에서 역할 검사 후 403 반환.
  - **실패 시 심각도**: 치명적

### 3. 입력 처리

- **위험**: 입력값을 통한 SQL 인젝션으로 DB 전체 조회.
  - **확인 방법**: 코드에서 문자열을 이어 붙여 만든 쿼리를 검색합니다(예: `grep -rn "SELECT.*\+\|\${" src/` 같은 패턴을 사용 언어에 맞게 조정). ORM의 raw query 사용 부분을 따로 확인합니다.
  - **통과 기준**: 모든 쿼리가 파라미터 바인딩 사용, raw query는 목록화되어 검토됨.
  - **실패 시 심각도**: 치명적

- **위험**: 사용자 입력이 화면에 그대로 렌더링되어 저장형 XSS로 다른 사용자 세션 탈취.
  - **확인 방법**: 이름, 메모, 댓글 등 저장되는 필드에 `<img src=x onerror=alert(1)>`을 넣고 다른 계정에서 조회합니다. 코드에서 `dangerouslySetInnerHTML`, `v-html`, `innerHTML` 사용처를 검색합니다.
  - **통과 기준**: 스크립트가 실행되지 않음, HTML 삽입 지점은 sanitize 처리됨.
  - **실패 시 심각도**: 높음

### 4. 비밀정보 / 설정

- **위험**: 저장소나 프런트 번들에 노출된 API 키·DB 비밀번호로 인프라 접근.
  - **확인 방법**: `gitleaks detect` 또는 `trufflehog git file://.`로 저장소 전체 이력을 스캔하고, 배포된 JS 번들에서 키 형태 문자열을 검색합니다.
  - **통과 기준**: 탐지 0건(또는 탐지된 키는 모두 폐기·교체 완료), 비밀정보는 환경변수/시크릿 매니저로만 주입.
  - **실패 시 심각도**: 치명적

- **위험**: 운영 환경에서 디버그 모드나 상세 에러가 켜져 있어 내부 구조·스택트레이스 노출.
  - **확인 방법**: 운영 URL에 존재하지 않는 경로, 잘못된 형식의 요청을 보내 응답 본문을 확인합니다.
  - **통과 기준**: 일반화된 에러 메시지만 반환, 스택트레이스·쿼리 노출 없음.
  - **실패 시 심각도**: 중간

### 5. 데이터 보호

- **위험**: DB나 백업이 유출될 때 평문 개인정보가 그대로 노출됨.
  - **확인 방법**: 클라우드 콘솔에서 DB·스토리지·백업의 저장 시 암호화 설정을 확인하고, 비밀번호 저장 방식(bcrypt/argon2 등)을 코드에서 확인합니다.
  - **통과 기준**: 저장 시 암호화 켜짐, 비밀번호는 느린 해시 함수 사용, 전송 구간 TLS 1.2 이상.
  - **실패 시 심각도**: 높음

- **위험**: 파일 저장소(S3 등)가 공개 설정되어 고객 파일을 누구나 다운로드.
  - **확인 방법**: 버킷 정책과 퍼블릭 액세스 차단 설정을 확인하고, 업로드된 파일 URL을 로그아웃 상태에서 열어봅니다.
  - **통과 기준**: 퍼블릭 접근 차단, 파일은 만료 시간이 있는 서명 URL로만 제공.
  - **실패 시 심각도**: 치명적

### 6. 의존성 / 로그

- **위험**: 알려진 취약점이 있는 라이브러리를 통한 원격 코드 실행 등.
  - **확인 방법**: 사용 언어에 맞게 `npm audit --omit=dev`, `pip-audit`, `trivy fs .` 등을 실행합니다.
  - **통과 기준**: Critical/High 0건, 또는 남은 항목마다 영향 없음 사유가 문서화됨.
  - **실패 시 심각도**: 결과에 따라 높음~치명적

- **위험**: 침해가 일어나도 탐지·추적할 수 없음(심사에서 자주 묻는 항목).
  - **확인 방법**: 로그인 성공/실패, 권한 변경, 데이터 내보내기 이벤트가 로그에 남는지, 로그 보관 기간과 접근 권한을 확인합니다. 로그에 비밀번호·토큰이 찍히지 않는지도 확인합니다.
  - **통과 기준**: 주요 보안 이벤트가 사용자·시각·IP와 함께 기록되고, 정해진 기간 보관됨.
  - **실패 시 심각도**: 중간

## 갭 (체크리스트로 해결되지 않는 부분)

- **이 체크리스트는 서비스를 모르고 만든 것이라 실제 위험을 놓칠 수 있습니다.** 서비스 구성과 데이터 흐름을 알려주시면 구성 요소별로 구체적인 공격과 확인 방법으로 바꿔드리겠습니다.
- **체크리스트 점검은 모의해킹을 대신하지 못합니다.** 고객사가 제3자 점검 결과를 요구한다면 일주일 안에 외부 업체 일정을 잡기 어려울 수 있으니, 지금 바로 요구 사항을 확인하시는 게 좋습니다. 불가능하면 "내부 점검 결과 + 외부 점검 예정일"로 제시하는 방법이 있습니다.
- **정책·절차 항목**(접근 권한 관리 절차, 사고 대응 절차, 직원 보안 교육, 백업 복구 테스트 기록 등)은 코드로 확인할 수 없고 문서가 있어야 합니다.

## 심사에 낼 문서에 대해

"문제 없음" 대신, 아래 형식이 심사에서도 더 신뢰를 얻습니다.

- 점검 일자, 점검자(실명·역할)
- 점검 범위: 어떤 시스템과 항목을 점검했는지
- 점검 방법: 위 체크리스트의 확인 방법, 사용 도구
- 결과: 항목별 통과/미통과, 미통과 항목의 조치 내용 또는 조치 예정일
- 점검하지 않은 범위

최종 서명은 결과를 직접 확인한 담당자가 해야 합니다.

**Also consider**
- 보안 헤더(CSP, HSTS, X-Frame-Options) 설정 확인
- CORS 허용 도메인이 `*`가 아닌지 확인
- 운영 인프라 콘솔 계정의 MFA와 최소 권한
- 퇴사자 계정 회수 절차

서비스 구성과 고객사 질문지를 공유해 주시면 그에 맞춰 다시 정리해 드리겠습니다.
