두 가지 중 하나는 만들어 드릴 수 없고, 하나는 요청하신 방식 그대로는 만들 수 없어서 먼저 말씀드립니다.

**2) '모의해킹 결과 취약점 없음' 확인서 — 작성하지 않겠습니다.** 실제로 수행하지 않은 모의해킹의 결과를 적은 문서를 고객사 심사에 내면 허위 자료 제출이 됩니다. 계약 해지나 손해배상 사유가 될 수 있고, 사고가 나면 책임이 훨씬 커집니다. 게다가 아래에 적은 것처럼 지금 구성에는 확인된 고위험 항목이 여러 개 있어서 "취약점 없음"은 사실과도 다릅니다. 대신 쓸 수 있는 방법은 이렇습니다.
- **자체 점검 결과서**: "○○ 기준으로 자체 점검 수행, 발견 항목 N건, 조치 완료 M건, 조치 계획(일정 포함) K건"처럼 실제로 한 일만 적습니다. 수행 범위와 수행 방법도 함께 적습니다.
- **모의해킹 수행 계획서**: 외부 업체 선정 일정, 범위(웹앱·API·AWS), 예정일을 적어 제출합니다. 많은 고객사가 "미수행 + 계획 있음"은 받아 주지만 허위 확인서는 받아 주지 않습니다.
- 원하시면 이 두 문서의 초안을 작성해 드리겠습니다.

**.env 커밋 건 — 체크리스트에서 빼지 않겠습니다.** 고객사에 제출할 자료에서 알고 있는 고위험 항목을 숨기는 것도 허위 제출과 같은 문제입니다. 그리고 실제 위험이 가장 큰 항목이기도 합니다. 공개 저장소에 한 번이라도 올라간 키는 자동 스캐너가 수 분 안에 수집한다고 봐야 하고, 키를 바꾸지 않았다면 지금도 유효한 상태입니다. 심사 전에 **키를 교체하고 "발견 → 교체 완료(날짜)"로 적는 것**이 심사에서도 가장 유리합니다. 이미 조치한 사고는 대부분 문제 삼지 않지만, 숨긴 사실이 나중에 드러나면 신뢰가 무너집니다.

아래는 알려 주신 구성을 기준으로 만든 체크리스트입니다. 설정 파일이나 코드를 본 것은 아니므로, 각 항목의 "확인 방법"은 무엇을 봐야 하는지를 적은 것입니다. [ASSUMPTION] 표시는 제가 추정한 부분입니다.

## 1. 체크리스트

### A. 시크릿 관리 (.env 공개 커밋)

**A-1. 유출된 키 교체** — 심각도: **치명(Critical)**
- 위험: 공격자가 공개 저장소 이력에서 .env를 가져와 DB 비밀번호, JWT 서명 키, AWS 액세스 키로 DB 직접 접속, 임의 사용자(관리자 포함) 토큰 위조, AWS 리소스 탈취를 할 수 있습니다.
- 확인 방법:
  - `git log --all --full-history -- .env` 로 커밋된 시점을 찾고, `git show <커밋>:.env` 로 당시 들어 있던 키 목록을 정리합니다.
  - 목록의 키마다 현재 운영 값과 같은지 비교합니다. 특히 `JWT_SECRET`, `DATABASE_URL`/DB 비밀번호, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, 그 외 외부 API 키(메일, 결제 등)를 확인합니다.
  - AWS 키: IAM 콘솔 → 해당 액세스 키의 "마지막 사용" 확인, CloudTrail에서 해당 키 ID로 발생한 이벤트를 커밋 이후 기간 전체로 조회합니다.
- 통과 기준: 당시 .env에 있던 **모든** 키가 교체(폐기 후 재발급)되었고, 옛 AWS 키는 IAM에서 삭제 상태이며, 옛 JWT 시크릿으로 서명한 토큰이 거부됩니다(옛 시크릿으로 직접 서명한 테스트 토큰을 API에 보내 401 확인).

**A-2. 유출 기간 중 악용 여부 조사** — 심각도: **높음(High)**
- 위험: 키 교체 전에 이미 누군가 접속했다면 교체만으로는 피해가 드러나지 않습니다.
- 확인 방법: CloudTrail(옛 AWS 키 사용 기록, 특히 알 수 없는 리전·IP의 `RunInstances`, `CreateUser`, `GetObject`), RDS 접속 로그(`log_connections` 활성화 여부 먼저 확인), 관리자 계정 목록에 모르는 계정이 있는지 확인합니다.
- 통과 기준: 조사한 기간과 로그 출처, 결과를 문서로 남겼습니다. 로그가 없어서 확인할 수 없는 기간은 "확인 불가"로 적습니다.

**A-3. 저장소 이력 정리와 재발 방지** — 심각도: 중간(Medium)
- 확인 방법: `.gitignore`에 `.env*`가 있는지, `gitleaks detect` 또는 `trufflehog git file://.` 로 전체 이력 스캔, GitHub의 secret scanning / push protection 활성화 여부.
- 통과 기준: 스캔 결과에 **유효한** 시크릿이 없습니다(이력에 남은 옛 키는 A-1에서 폐기됐으면 무효). 이력 삭제(`git filter-repo`)는 선택 사항이며, 이미 복제된 사본은 지울 수 없으므로 키 교체를 대신하지 못합니다.

### B. 인증 (이메일 + 비밀번호, bcrypt)

**B-1. bcrypt 비용 인자** — 심각도: 중간
- 위험: DB가 유출되면(A-1 참고) 공격자가 낮은 비용 인자의 해시를 오프라인으로 빠르게 크래킹합니다.
- 확인 방법: 해시 저장 코드에서 `bcrypt.hash(password, <rounds>)` 값 확인, 또는 DB의 해시 문자열 앞부분(`$2b$10$…` 의 `10`)을 확인합니다.
- 통과 기준: 비용 인자 10 이상(가능하면 12). 72바이트 초과 비밀번호가 잘리는 bcrypt 특성을 알고 있고, 비밀번호 최대 길이 정책이 있습니다.

**B-2. 로그인 무차별 대입 / 크리덴셜 스터핑** — 심각도: 높음
- 위험: 공격자가 유출된 비밀번호 목록으로 로그인 API를 반복 호출해 계정을 탈취합니다.
- 확인 방법: Express 로그인 라우트에 속도 제한 미들웨어(`express-rate-limit` 등)가 있는지 코드 확인, 같은 계정/IP로 틀린 비밀번호를 20~30회 연속 전송해 응답 확인.
- 통과 기준: 일정 횟수 이후 429 또는 지연/잠금이 걸립니다. 계정 단위와 IP 단위 제한이 둘 다 있습니다.

**B-3. 계정 존재 여부 노출** — 심각도: 낮음(Low)
- 확인 방법: 존재하는 이메일과 없는 이메일로 로그인·비밀번호 재설정 요청을 보내 응답 메시지, 상태 코드, 응답 시간을 비교합니다.
- 통과 기준: 세 가지가 구분되지 않습니다.

**B-4. 비밀번호 재설정 토큰** — 심각도: 높음 [ASSUMPTION: 재설정 기능이 있다고 가정]
- 확인 방법: 토큰 생성 코드가 `crypto.randomBytes` 등 CSPRNG를 쓰는지, 만료 시간, 1회 사용 후 무효화 여부를 확인합니다.
- 통과 기준: 32바이트 이상 난수, 만료 1시간 이하, 사용 즉시 폐기.

### C. 세션 (JWT를 localStorage에 저장)

**C-1. XSS 발생 시 토큰 탈취** — 심각도: **높음**
- 위험: 공격자가 XSS 한 건만 성공시키면 `localStorage.getItem(...)` 으로 토큰을 읽어 외부로 보내고, 만료될 때까지 해당 사용자(관리자 포함)로 행세합니다. localStorage는 HttpOnly 보호를 받을 수 없어서 이 구조에서는 XSS가 곧 계정 탈취입니다.
- 확인 방법:
  - 코드에서 `dangerouslySetInnerHTML`, `innerHTML`, `eval`, 사용자 입력이 들어가는 `href`(`javascript:` URL) 사용처를 `grep`으로 모두 찾습니다.
  - 응답 헤더에 `Content-Security-Policy`가 있는지 `curl -I https://<도메인>` 으로 확인합니다.
- 통과 기준: 위 사용처가 없거나 모두 검증·이스케이프되어 있고, `script-src`에 `'unsafe-inline'`/`'unsafe-eval'`이 없는 CSP가 적용되어 있습니다. 근본 대책은 **토큰을 `HttpOnly; Secure; SameSite` 쿠키로 옮기는 것**이며, 그 경우 CSRF 대책(SameSite=Lax 이상 + 상태 변경 요청의 CSRF 토큰 또는 Origin 검사)을 같이 넣어야 합니다.

**C-2. JWT 서명 검증** — 심각도: 치명
- 위험: 서버가 알고리즘을 고정하지 않으면 공격자가 `alg: none` 또는 조작한 토큰으로 인증을 우회합니다.
- 확인 방법: `jwt.verify(token, secret, { algorithms: ['HS256'] })` 처럼 알고리즘을 명시하는지 코드 확인. `jwt.decode`만 쓰고 검증하지 않는 경로가 있는지 `grep`. 테스트: 헤더를 `{"alg":"none"}`으로, payload의 역할을 `admin`으로 바꾼 토큰을 보내 봅니다.
- 통과 기준: 조작 토큰이 모두 401로 거부됩니다.

**C-3. 토큰 만료와 폐기** — 심각도: 중간
- 위험: 탈취된 토큰이 오래 유효하고, 로그아웃·비밀번호 변경 후에도 계속 쓰입니다.
- 확인 방법: 발급 코드의 `expiresIn` 값, 로그아웃/비밀번호 변경 시 서버 측에서 토큰을 무효화하는 장치(토큰 버전, 블록리스트)가 있는지 확인. 로그아웃 전에 복사한 토큰으로 로그아웃 후 API 호출.
- 통과 기준: 액세스 토큰 만료가 짧고(예: 15분~1시간), 비밀번호 변경 후 기존 토큰이 거부됩니다.

**C-4. 토큰 내 역할 정보 신뢰** — 심각도: 높음
- 확인 방법: 관리자 권한 판정이 JWT payload의 `role`만 보는지, DB의 현재 역할을 조회하는지 확인합니다.
- 통과 기준: 역할 강등 후 기존 토큰으로 관리자 API 호출이 거부됩니다(또는 만료 시간 안에서만 유효하다는 점을 문서화).

### D. 관리자 페이지 (/admin, IP 제한 없음)

**D-1. 서버 측 권한 검사** — 심각도: **치명**
- 위험: 공격자가 일반 계정으로 로그인한 뒤 관리자 API를 직접 호출해 전체 사용자 데이터 조회·수정을 합니다. Next.js에서 페이지만 숨기고 Express API에 권한 검사가 없으면 흔히 생기는 문제입니다.
- 확인 방법: Express의 관리자 라우트(`/api/admin/*` 등 [ASSUMPTION: 관리자 기능이 이런 API를 호출한다고 가정]) 전부에 역할 검사 미들웨어가 걸려 있는지 라우터 코드를 확인합니다. 일반 사용자 토큰으로 각 관리자 API를 `curl` 호출합니다.
- 통과 기준: 모든 관리자 API가 일반 사용자 토큰에 403, 토큰 없음에 401을 반환합니다. Next.js 미들웨어나 클라이언트 쪽 리다이렉트만으로 막고 있다면 불합격입니다.

**D-2. 관리자 계정 보호** — 심각도: 높음
- 위험: IP 제한이 없으므로 인터넷 어디서든 관리자 로그인이 가능하고, 관리자 비밀번호 한 개가 뚫리면 끝입니다.
- 확인 방법: 관리자 계정에 MFA가 있는지, B-2의 속도 제한이 관리자 로그인에도 적용되는지 확인합니다.
- 통과 기준: 관리자 계정은 MFA 필수. IP 제한(보안 그룹/WAF/VPN)은 추가 권장이며, 둘 다 없으면 이 항목은 불합격으로 기록합니다.

**D-3. 관리자 작업 감사 로그** — 심각도: 중간
- 확인 방법: 관리자가 데이터를 조회·수정·삭제할 때 누가, 언제, 무엇을 했는지 기록되는지 확인합니다.
- 통과 기준: 관리자 작업마다 로그가 남고, 관리자가 그 로그를 지울 수 없습니다.

### E. 파일 업로드 (S3 퍼블릭 버킷, 원본 파일명 그대로 저장)

**E-1. 파일명 충돌·덮어쓰기** — 심각도: **높음**
- 위험: 공격자가 다른 사용자와 같은 파일명(예: `profile.jpg`)으로 업로드해 남의 프로필 이미지를 덮어쓰거나, 경로 문자(`../`, `/`)가 포함된 파일명으로 의도하지 않은 키 경로에 파일을 씁니다.
- 확인 방법: 업로드 코드의 S3 `Key` 생성 부분을 확인합니다. 두 계정으로 같은 이름의 파일을 올려 첫 번째 파일이 바뀌는지 봅니다. `../../test.jpg` 같은 이름으로 업로드해 저장된 키를 확인합니다.
- 통과 기준: 키가 서버에서 생성한 무작위 값(UUID 등)이고 사용자 파일명은 키에 쓰이지 않습니다(필요하면 메타데이터로만 보관).

**E-2. 퍼블릭 버킷 목록 노출과 파일명 추측** — 심각도: 높음
- 위험: 버킷 목록 조회가 열려 있으면 공격자가 모든 파일을 내려받고, 원본 파일명(예: `홍길동_주민등록증.jpg`)에서 개인정보를 얻습니다.
- 확인 방법: `aws s3 ls s3://<버킷> --no-sign-request` 로 익명 목록 조회가 되는지, 버킷 정책에 `s3:ListBucket`이 `Principal: *`로 열려 있는지 확인합니다.
- 통과 기준: 익명 목록 조회가 거부됩니다. 가능하면 버킷을 비공개로 바꾸고 CloudFront(OAC) 또는 서명 URL로만 제공합니다.

**E-3. 파일 형식 검증과 저장형 XSS** — 심각도: 높음
- 위험: 공격자가 `.html`이나 `.svg`(스크립트 포함) 파일을 "프로필 이미지"로 올리고 그 S3 URL을 퍼뜨려 스크립트를 실행시킵니다. 같은 도메인에서 제공된다면 C-1의 토큰 탈취로 이어집니다.
- 확인 방법: 서버가 확장자가 아니라 파일 내용(매직 바이트)으로 형식을 검사하는지, 업로드 시 `ContentType`을 서버가 지정하는지 확인합니다. SVG와 HTML 파일을 업로드해 봅니다. 이미지가 앱과 같은 도메인에서 제공되는지 확인합니다.
- 통과 기준: JPEG/PNG/WebP 등 허용 목록 외 파일이 거부되고, `Content-Type`이 서버가 지정한 이미지 타입이며, 이미지는 앱과 다른 도메인에서 제공됩니다. 가능하면 서버에서 이미지를 재인코딩해 메타데이터(EXIF 위치 정보 포함)를 제거합니다.

**E-4. 업로드 크기와 횟수 제한** — 심각도: 중간
- 확인 방법: 업로드 미들웨어(`multer` 등)의 `limits.fileSize` 설정, 업로드 API 속도 제한을 확인합니다. 큰 파일을 올려 봅니다.
- 통과 기준: 크기 제한(예: 5MB)이 서버에서 강제되고, 반복 업로드가 제한됩니다(S3 비용 폭증 방지).

### F. API (Express) 와 DB (PostgreSQL)

**F-1. SQL 인젝션** — 심각도: 치명
- 위험: 공격자가 입력값에 SQL을 넣어 DB 전체를 읽거나 수정합니다.
- 확인 방법: 쿼리 코드에서 문자열 결합(`` `SELECT ... ${...}` ``, `+` 결합)을 `grep`으로 찾습니다. ORM을 쓴다면 raw 쿼리 함수 사용처만 확인합니다.
- 통과 기준: 모든 쿼리가 파라미터 바인딩(`$1`, `?`)을 씁니다.

**F-2. 객체 단위 권한(IDOR)** — 심각도: 높음
- 위험: 공격자가 `/api/users/123` 의 번호를 바꿔 다른 사용자의 정보를 조회·수정합니다.
- 확인 방법: ID를 받는 모든 라우트에서 "요청한 사용자가 이 리소스의 소유자인지" 검사하는지 확인합니다. 계정 A의 토큰으로 계정 B의 리소스를 요청해 봅니다.
- 통과 기준: 403 또는 404가 반환됩니다.

**F-3. 에러 응답의 정보 노출** — 심각도: 낮음
- 확인 방법: 잘못된 입력으로 500 에러를 유도하고 응답 본문에 스택 트레이스, SQL 문, 파일 경로가 나오는지 확인합니다. `NODE_ENV=production` 설정 여부 확인.
- 통과 기준: 클라이언트에는 일반 메시지만 나갑니다.

**F-4. CORS 설정** — 심각도: 중간
- 확인 방법: Express의 `cors()` 설정에서 `origin`이 `*` 또는 요청 Origin을 그대로 반사하는지 확인합니다.
- 통과 기준: 허용 Origin이 명시적 목록입니다. (토큰이 쿠키가 아니라 헤더로 가는 현재 구조에서는 영향이 제한적이지만, C-1에서 쿠키로 옮기면 중요해집니다.)

### G. AWS 인프라 (EC2, RDS)

**G-1. RDS 외부 노출** — 심각도: **치명** (A-1과 결합 시)
- 위험: RDS가 퍼블릭 접근 가능하면 유출된 DB 비밀번호로 인터넷에서 바로 접속합니다.
- 확인 방법: RDS 콘솔의 "Publicly accessible" 값, RDS 보안 그룹의 인바운드 5432 규칙 소스가 `0.0.0.0/0`인지 확인합니다.
- 통과 기준: 퍼블릭 접근 "아니요", 5432 인바운드는 EC2 보안 그룹만 허용.

**G-2. EC2 보안 그룹과 접속 경로** — 심각도: 높음
- 확인 방법: EC2 보안 그룹 인바운드 규칙에서 22(SSH)가 `0.0.0.0/0`으로 열려 있는지 확인합니다.
- 통과 기준: SSH는 닫혀 있고 SSM Session Manager를 쓰거나, 특정 IP로만 허용합니다. 외부에는 80/443만(ALB 뒤라면 ALB만) 열려 있습니다.

**G-3. EC2 인스턴스 메타데이터(IMDS)** — 심각도: 높음
- 위험: 앱에 SSRF가 있으면 공격자가 `169.254.169.254`에서 인스턴스 역할 자격 증명을 가져갑니다.
- 확인 방법: `aws ec2 describe-instances --query 'Reservations[].Instances[].MetadataOptions'` 에서 `HttpTokens` 값을 확인합니다.
- 통과 기준: `HttpTokens: required` (IMDSv2 강제).

**G-4. 앱이 쓰는 AWS 권한 범위** — 심각도: 높음
- 확인 방법: 앱이 S3 업로드에 액세스 키를 쓰는지 인스턴스 역할을 쓰는지 확인하고, 연결된 IAM 정책을 봅니다.
- 통과 기준: 액세스 키 대신 인스턴스 역할을 쓰고, 정책이 해당 버킷의 필요한 작업(`s3:PutObject` 등)으로만 제한됩니다. `AdministratorAccess`나 `s3:*` on `*`이면 불합격.

**G-5. 전송·저장 암호화와 백업** — 심각도: 중간
- 확인 방법: RDS "Encryption" 활성 여부, RDS 파라미터 `rds.force_ssl`(PostgreSQL) 값, 자동 백업 보존 기간, 앱의 HTTPS 강제와 `Strict-Transport-Security` 헤더.
- 통과 기준: 저장 암호화 활성, DB 연결 TLS 강제, 백업 보존 기간이 정책에 맞게 설정, 모든 HTTP 요청이 HTTPS로 리다이렉트.

### H. 의존성 (Next.js 14, Express)

**H-1. 알려진 취약 버전** — 심각도: 버전에 따라 높음~치명
- 확인 방법: `npm audit --omit=dev`, `npx next --version` 으로 실제 설치 버전 확인 후 Next.js 보안 권고(GitHub Security Advisories)와 대조합니다. Next.js 14 계열에는 미들웨어 인증 우회 등 과거 권고가 있었으므로, 설치된 정확한 패치 버전이 해당 권고의 수정 버전 이상인지 확인해야 합니다.
- 통과 기준: High/Critical 권고가 없거나, 해당 경로가 앱에서 쓰이지 않는다는 근거를 문서로 남겼습니다.

### 이 구조에 해당하지 않는 항목
- 서버 측 세션 고정(session fixation): 서버 세션 저장소가 아니라 JWT를 쓰므로 해당하지 않습니다.
- CSRF: 토큰을 쿠키가 아니라 localStorage에서 꺼내 헤더로 보내는 현재 구조에서는 브라우저가 자동으로 인증 정보를 붙이지 않으므로 해당하지 않습니다. 단, C-1에 따라 쿠키로 옮기면 바로 해당됩니다.

## 2. 현재 제약으로 막을 수 없는 위험 (Gaps)

- **XSS = 계정 탈취 (C-1)**: 토큰을 localStorage에 두는 한 CSP와 코드 점검은 위험을 줄일 뿐 없애지 못합니다. 보완책은 HttpOnly 쿠키로의 전환이며, 전환 전까지는 짧은 토큰 만료와 엄격한 CSP로 피해 시간을 줄입니다.
- **키 교체 전 악용 여부 (A-2)**: 로그가 켜져 있지 않았던 기간에 무슨 일이 있었는지는 사후에 알 수 없습니다. 보완책은 교체와 함께 CloudTrail·RDS 접속 로그를 지금부터 켜 두는 것이고, 심사 자료에는 확인 불가 기간을 그대로 적습니다.
- **관리자 경로 인터넷 노출 (D-2)**: IP 제한이 없으면 관리자 로그인 화면이 누구에게나 보입니다. MFA와 속도 제한으로 보완하되, 관리자 접근을 VPN 또는 별도 도메인+WAF 규칙 뒤로 옮기는 것이 근본 대책입니다.
- **퍼블릭 버킷 (E-2)**: 버킷이 퍼블릭인 한 URL을 아는 누구나 파일을 받을 수 있습니다. 무작위 키로 추측은 어렵게 만들 수 있지만, 비공개 버킷 + 서명 URL로 바꾸기 전에는 "URL 유출 = 파일 유출"입니다.
- **이 체크리스트는 모의해킹이 아닙니다**: 코드·설정 점검과 수동 테스트 수준이며, 로직 결함이나 여러 취약점을 엮은 공격은 외부 모의해킹에서 확인해야 합니다. 체크 결과와 조치 여부는 담당자가 확인하고 서명해 주세요.

## Also consider
- 보안 헤더(`X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors`) 일괄 적용.
- 로그인·관리자 작업 이상 징후 알림(CloudWatch 경보 등).
- 개인정보 처리 항목(프로필 이미지 포함)의 보존 기간과 삭제 절차 문서화.
