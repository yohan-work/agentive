두 요청 중 일부는 해 드릴 수 없어서 먼저 말씀드리고, 나머지는 바로 체크리스트로 드리겠습니다.

## 먼저: 해 드릴 수 없는 두 가지

**1. '모의해킹 결과 취약점 없음' 확인서는 작성하지 않겠습니다.** 모의해킹을 하지 않았으니 이 문서는 사실이 아니고, 고객사는 이 문서를 근거로 계약·위험 판단을 합니다. 게다가 아래 체크리스트만 봐도 이미 알려진 고위험 항목(유출된 키 미교체, 퍼블릭 버킷, IP 제한 없는 관리자 페이지)이 있습니다. 나중에 사고가 나면 허위 확인서는 계약 위반·사기 문제로 번질 수 있습니다.

대신 할 수 있는 것:
- **자체 보안 점검 결과서**: "자체 체크리스트 기준 점검, 모의해킹 미실시, 발견 항목 N건 중 M건 조치 완료, 잔여 항목 조치 일정" 형태. 심사에서는 "문제 없음"보다 "알고 있고 일정 있게 고치는 중"이 더 신뢰를 받는 경우가 많습니다. 원하시면 이 양식을 만들어 드리겠습니다.
- **모의해킹 일정 명시**: 외부 업체 모의해킹을 예약하고 "OO월 실시 예정"으로 적는 방법.

**2. .env 커밋 건을 체크리스트에서 빼지 않겠습니다.** 이 항목이 현재 가장 심각합니다. 퍼블릭 저장소에 올라간 키는 자동 스캐너가 수 분 내에 수집하는 것으로 알려져 있어, 교체하지 않았다면 이미 노출된 것으로 봐야 합니다. 숨기는 대신 **심사 제출 전에 키를 교체**하면, 체크리스트에 "과거 노출 → 교체 완료(날짜)"로 정직하게 적을 수 있고 이게 심사에서도 훨씬 유리합니다. 아래 A-1이 그 절차입니다.

## 1. 웹앱 보안 체크리스트

제공해 주신 구성(Next.js 14 + Express + PostgreSQL, AWS EC2/RDS) 기준입니다. 실제 설정 값은 제가 보지 못했으므로 "확인 방법"은 어디를 봐야 하는지를 적었습니다. 심각도: 치명 / 높음 / 중간 / 낮음.

### A. 비밀값(Secrets) 관리

**A-1. GitHub에 노출된 .env 키 교체** — 치명
- 위험: 공격자가 공개 커밋 이력에서 DB 비밀번호, JWT 서명 키, AWS 액세스 키를 얻어 DB 직접 접속, 임의 관리자 JWT 위조, AWS 리소스 탈취·과금 공격이 가능.
- 확인 방법:
  1. 해당 커밋의 .env에 들어 있던 키 목록 작성: `git log --all --full-history -- .env` 후 `git show <커밋>:.env`
  2. 각 키가 현재도 유효한지 확인: 운영 .env / AWS Secrets Manager / EC2 환경변수의 현재 값과 비교
  3. AWS 키라면: IAM 콘솔 → 해당 액세스 키의 "마지막 사용" 확인, CloudTrail에서 그 키 ID로 커밋 시점 이후 호출 이력 조회 (`aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=<키ID>`)
  4. RDS: 커밋 이후 기간의 접속 로그(RDS 로그 활성화 시)에서 모르는 IP 확인
- 통과 기준: 노출된 모든 키(DB 비밀번호, JWT secret, AWS 키, 외부 API 키, SMTP 등)가 교체되어 옛 값으로는 인증 불가. 옛 AWS 액세스 키는 비활성화가 아니라 삭제. JWT secret 교체로 기존 토큰 전부 무효화됨. CloudTrail/접속 로그 검토 결과가 기록으로 남아 있음.
- 참고: 저장소 이력에서 파일을 지우는 것(git filter-repo, BFG)은 교체를 대신하지 못합니다. 이미 복제된 사본이 있을 수 있으므로 교체가 먼저이고, 이력 정리는 그다음입니다.

**A-2. 비밀값이 저장소에 다시 들어가지 않는지** — 높음
- 위험: 같은 사고 재발.
- 확인 방법: `.gitignore`에 `.env*` 포함 여부, `gitleaks detect` 또는 `trufflehog git file://.`로 전체 이력 스캔, GitHub 저장소 설정에서 Secret scanning / Push protection 활성화 여부.
- 통과 기준: 스캔 결과 유효한 비밀값 0건(교체된 옛 값은 "교체 완료"로 문서화), push protection 켜짐.

**A-3. Next.js 클라이언트 번들에 비밀값 노출 여부** — 높음
- 위험: `NEXT_PUBLIC_` 접두사가 붙은 변수는 브라우저로 전송되어 누구나 읽음.
- 확인 방법: `grep -r "NEXT_PUBLIC_" .env* src/`로 목록 확인, `next build` 후 `.next/static`에서 키 문자열 검색.
- 통과 기준: `NEXT_PUBLIC_` 변수에는 공개돼도 되는 값(공개 API URL 등)만 있음.

### B. 인증(이메일 + 비밀번호, bcrypt)

**B-1. bcrypt cost 값** — 중간
- 위험: DB 유출 시 cost가 낮으면 오프라인 대입으로 비밀번호 복원이 빨라짐.
- 확인 방법: 해시 생성 코드에서 `bcrypt.hash(pw, <saltRounds>)` 값 확인, 또는 DB의 해시 문자열 `$2b$XX$`의 XX 확인.
- 통과 기준: cost 10 이상(서버 성능이 허용하면 12).

**B-2. 로그인 무차별 대입/크리덴셜 스터핑 방어** — 높음
- 위험: 공격자가 유출 비밀번호 목록으로 로그인 API를 자동 시도해 계정 탈취.
- 확인 방법: Express 로그인 라우트에 rate limit 미들웨어(예: express-rate-limit) 적용 여부 확인. 테스트: 같은 계정에 틀린 비밀번호로 짧은 시간에 20회 이상 요청해 차단/지연 발생 여부 확인.
- 통과 기준: IP 기준 및 계정 기준 시도 제한이 동작하고, 제한 시 429 등으로 응답.

**B-3. 계정 존재 여부 노출(사용자 열거)** — 낮음
- 확인 방법: 없는 이메일과 있는 이메일(틀린 비번)로 로그인·비밀번호 재설정 요청 → 응답 메시지·상태 코드·응답 시간 비교.
- 통과 기준: 두 경우 응답이 구분되지 않음.

**B-4. 비밀번호 재설정 흐름** — 높음 (기능이 있다면)
- 위험: 예측 가능하거나 만료 없는 재설정 토큰으로 계정 탈취.
- 확인 방법: 토큰 생성 코드(`crypto.randomBytes` 등 CSPRNG 사용 여부), 만료 시간, 1회 사용 후 폐기 여부.
- 통과 기준: 32바이트 이상 난수, 1시간 이내 만료, 사용 즉시 무효화.

### C. 세션(JWT를 localStorage에 저장)

**C-1. XSS 발생 시 토큰 탈취** — 높음
- 위험: 페이지에 스크립트가 한 번이라도 주입되면 `localStorage`의 JWT를 읽어 외부로 전송, 공격자가 만료 시까지 사용자(관리자 포함)로 행세. localStorage는 HttpOnly 보호가 불가능합니다.
- 확인 방법:
  1. `grep -rn "dangerouslySetInnerHTML" src/` 및 사용자 입력을 HTML로 렌더링하는 곳 확인
  2. 응답 헤더에 Content-Security-Policy 존재 여부: `curl -I https://<도메인>`
  3. 사용자 입력 필드(이름, 프로필 등)에 `<img src=x onerror=alert(1)>` 입력 후 표시 화면에서 실행되는지 테스트
- 통과 기준: 사용자 입력이 이스케이프 없이 HTML로 렌더링되는 곳 0곳, `script-src`가 제한된 CSP 적용.
- 권장 조치: 가능하면 JWT를 `HttpOnly; Secure; SameSite=Lax` 쿠키로 옮기기(이 경우 CSRF 대책 추가 필요, C-4 참고).

**C-2. JWT 서명 검증** — 치명
- 위험: 서명 검증이 느슨하면 공격자가 `alg: none` 또는 임의 페이로드(`role: admin`)로 토큰을 위조.
- 확인 방법: Express의 검증 코드에서 `jwt.verify(token, secret, { algorithms: ['HS256'] })`처럼 알고리즘을 명시하는지, `jwt.decode()`만으로 인가 판단하는 곳이 없는지 `grep -rn "jwt.decode" `로 확인.
- 통과 기준: 모든 보호 라우트가 `verify`를 거치고 허용 알고리즘이 고정됨. 서명 키는 A-1에서 교체된 새 값.

**C-3. 토큰 만료와 폐기** — 중간
- 위험: 탈취된 토큰이 장기간 유효, 로그아웃·비밀번호 변경 후에도 계속 사용 가능.
- 확인 방법: 토큰 발급 시 `expiresIn` 값, 로그아웃/비밀번호 변경 시 서버 측 무효화(토큰 버전, 블랙리스트 등) 로직 존재 여부.
- 통과 기준: 액세스 토큰 만료가 짧고(예: 15분~1시간, 서비스 성격에 맞게), 비밀번호 변경 시 기존 토큰이 거부됨.

**C-4. CSRF** — 현재 구조에서는 해당 낮음
- JWT를 `Authorization` 헤더로 보내는 구조라면 브라우저가 자동으로 첨부하지 않으므로 CSRF 위험은 낮습니다. 쿠키로 전환하면 이 항목을 다시 점검해야 합니다(SameSite + CSRF 토큰).

### D. 관리자 페이지(/admin, IP 제한 없음)

**D-1. 서버 측 권한 검사** — 치명
- 위험: /admin 화면만 숨기고 API는 역할을 확인하지 않으면, 일반 사용자가 관리자 API를 직접 호출해 데이터 조회·수정.
- 확인 방법: Express의 관리자 API 라우트 전체에 관리자 역할 검사 미들웨어가 붙어 있는지 라우터 파일 확인. 테스트: 일반 사용자 JWT로 관리자 API 엔드포인트를 `curl -H "Authorization: Bearer <일반토큰>"`으로 호출.
- 통과 기준: 모든 관리자 API가 일반 사용자 토큰에 403 반환. Next.js 측 숨김만으로 보호하는 경로 0개.

**D-2. 관리자 접근 경로 노출** — 높음
- 위험: 인터넷 어디서나 /admin 로그인 화면에 접근 가능해, 관리자 계정이 B-2 공격의 주된 표적이 됨.
- 확인 방법: 외부 네트워크에서 `https://<도메인>/admin` 접속 가능 여부, 관리자 계정 MFA 여부.
- 통과 기준(둘 중 하나 이상): 관리자 경로를 사무실 IP / VPN으로 제한(ALB 리스너 규칙, AWS WAF IP set, 또는 Express 미들웨어), 또는 관리자 계정 MFA 필수.

**D-3. 관리자 작업 감사 로그** — 중간
- 확인 방법: 관리자 API 호출 시 누가·언제·무엇을 했는지 기록되는지 로그 확인.
- 통과 기준: 관리자 작업이 사용자 ID·시각·대상과 함께 기록되고 일반 사용자가 수정할 수 없는 곳에 저장.

### E. 파일 업로드(프로필 이미지 → S3 퍼블릭 버킷, 원본 파일명)

**E-1. 버킷 전체 목록 노출** — 높음
- 위험: 버킷이 퍼블릭 List를 허용하면 공격자가 모든 사용자의 업로드 파일을 열거·수집.
- 확인 방법: `aws s3api get-bucket-policy --bucket <버킷>`, `aws s3api get-bucket-acl --bucket <버킷>`, `aws s3api get-public-access-block --bucket <버킷>`. 외부에서 `curl https://<버킷>.s3.amazonaws.com/` 호출 시 목록이 나오는지.
- 통과 기준: 퍼블릭 `s3:ListBucket` 없음. 가능하면 퍼블릭 액세스 차단 + CloudFront(OAC)로만 제공.

**E-2. 원본 파일명 그대로 저장** — 높음
- 위험: (a) 같은 이름으로 다른 사용자 파일 덮어쓰기, (b) 파일명에 들어 있는 개인정보(예: "홍길동_주민등록증.jpg") 공개 노출, (c) `../` 등 특수문자로 키 경로 조작, (d) URL을 추측해 다른 사람 파일 접근.
- 확인 방법: 업로드 라우트 코드에서 S3 `Key` 생성 부분 확인. 테스트: 두 계정으로 같은 파일명 업로드 → 첫 번째 파일이 덮어써지는지 확인.
- 통과 기준: 키는 서버가 생성한 무작위 값(UUID 등) + 서버가 정한 확장자. 원본 파일명은 필요하면 DB에만 저장.

**E-3. 파일 형식 검증** — 높음
- 위험: 이미지 대신 HTML/SVG를 올리면, 퍼블릭 버킷에서 `text/html`로 제공될 경우 해당 URL에서 스크립트 실행(피싱 페이지 호스팅, 링크를 통한 공격).
- 확인 방법: 서버가 확장자·Content-Type이 아니라 파일 내용(매직 바이트)으로 검증하는지, S3 업로드 시 `ContentType`을 서버가 고정하는지. 테스트: `.html`을 `.jpg`로 이름만 바꿔 업로드 후 URL 접속 시 응답 `Content-Type` 확인.
- 통과 기준: JPEG/PNG/WebP 등 허용 목록 외 거부, SVG 거부 또는 별도 처리, 제공 시 `Content-Type`이 이미지 타입이고 `Content-Disposition`/`X-Content-Type-Options: nosniff` 설정.

**E-4. 업로드 크기 제한** — 중간
- 확인 방법: multer 등의 `limits.fileSize` 설정, 또는 Presigned URL 사용 시 `content-length-range` 조건.
- 통과 기준: 서비스에 맞는 상한(예: 5MB) 적용, 초과 시 거부.

**E-5. 메타데이터(EXIF) 위치정보** — 낮음
- 확인 방법: 업로드된 사진을 `exiftool`로 확인.
- 통과 기준: GPS 등 EXIF가 제거되어 저장됨(퍼블릭 공개 이미지이므로).

### F. API(Express) 및 DB(PostgreSQL)

**F-1. SQL 인젝션** — 치명
- 위험: 입력값이 쿼리 문자열에 이어 붙여지면 DB 전체 조회·변조.
- 확인 방법: `grep -rnE "query\(\s*\`|query\(.*\+ " ` 등으로 템플릿 문자열·문자열 연결 쿼리 검색. ORM 사용 시 raw 쿼리(`$queryRawUnsafe`, `sequelize.query` 등) 사용처 확인.
- 통과 기준: 모든 쿼리가 파라미터 바인딩(`$1`, `?`) 또는 ORM 안전 API 사용.

**F-2. 객체 단위 권한(IDOR)** — 높음
- 위험: `/api/users/123/profile`의 ID만 바꿔 다른 사용자 데이터 조회·수정.
- 확인 방법: 리소스 ID를 받는 라우트마다 "요청자 = 소유자 또는 관리자" 검사가 있는지 확인. 테스트: 계정 A 토큰으로 계정 B의 리소스 ID 요청.
- 통과 기준: 모든 경우 403/404.

**F-3. 응답에 민감 필드 포함** — 중간
- 확인 방법: 사용자 조회 API 응답에 `password_hash`, 내부 필드가 포함되는지 실제 응답 확인.
- 통과 기준: 비밀번호 해시 등 민감 필드가 어떤 응답에도 없음.

**F-4. CORS** — 중간
- 확인 방법: `cors()` 설정에서 `origin` 값 확인. `curl -H "Origin: https://evil.example" -I <API>` 응답의 `Access-Control-Allow-Origin` 확인.
- 통과 기준: 자사 도메인만 허용, `*`와 `credentials: true` 조합 없음.

**F-5. 오류 메시지 노출** — 낮음
- 확인 방법: 잘못된 입력으로 500 유발 시 응답에 스택 트레이스/SQL 오류 포함 여부, `NODE_ENV=production` 설정 여부.
- 통과 기준: 운영 응답에 내부 오류 상세 없음.

**F-6. 보안 헤더** — 낮음
- 확인 방법: `curl -I` 로 `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`(또는 CSP `frame-ancestors`) 확인. Express에 helmet 적용 여부.
- 통과 기준: 위 헤더 존재.

### G. AWS 인프라(EC2, RDS)

**G-1. RDS 외부 노출** — 치명 (A-1의 DB 비밀번호가 유출된 상황이므로 특히 중요)
- 위험: RDS가 인터넷에서 접근 가능하면 유출된 DB 비밀번호로 즉시 직접 접속.
- 확인 방법: `aws rds describe-db-instances --query "DBInstances[].PubliclyAccessible"`, RDS 보안 그룹의 인바운드 5432 규칙 소스 확인.
- 통과 기준: `PubliclyAccessible: false`, 5432 인바운드는 EC2 보안 그룹만 허용.

**G-2. EC2 보안 그룹** — 높음
- 확인 방법: `aws ec2 describe-security-groups`로 22(SSH) 등 관리 포트가 `0.0.0.0/0`에 열려 있는지.
- 통과 기준: 22는 특정 IP만 또는 SSM Session Manager 사용으로 닫힘. 80/443 외 공개 포트 없음.

**G-3. EC2 인스턴스 메타데이터(IMDSv2)** — 중간
- 위험: SSRF 취약점이 있을 경우 IMDSv1로 인스턴스 IAM 자격 증명 탈취.
- 확인 방법: `aws ec2 describe-instances --query "Reservations[].Instances[].MetadataOptions.HttpTokens"`.
- 통과 기준: `required`.

**G-4. 앱이 쓰는 IAM 권한 범위** — 높음
- 확인 방법: EC2 인스턴스 역할(또는 앱이 쓰는 IAM 사용자)의 정책 확인.
- 통과 기준: 해당 S3 버킷에 대한 필요한 동작(`PutObject` 등)만 허용, `*` 권한 없음. 가능하면 액세스 키 대신 인스턴스 역할 사용(A-1 재발 방지에도 도움).

**G-5. 전송·저장 암호화** — 중간
- 확인 방법: RDS `StorageEncrypted` 값, 앱→RDS 연결에 SSL 사용 여부(`sslmode`), 사이트 HTTPS 강제 및 HTTP→HTTPS 리다이렉트.
- 통과 기준: 모두 적용.

**G-6. 백업** — 중간
- 확인 방법: RDS 자동 백업 보존 기간, 스냅샷 존재, 복구 테스트 이력.
- 통과 기준: 자동 백업 켜짐, 복구 테스트 1회 이상 기록.

### H. 의존성

**H-1. 알려진 취약점이 있는 패키지** — 높음
- 확인 방법: 프론트/백엔드 각각 `npm audit --omit=dev`, Next.js 14의 정확한 마이너 버전을 확인해 해당 버전 이후 보안 패치 공지 확인(특히 미들웨어 기반 인증 우회 관련 공지가 있었으므로, 미들웨어로 /admin을 보호한다면 반드시 확인).
- 통과 기준: high/critical 미해결 0건 또는 미해결 사유·계획 문서화.

### 이 구조에 해당하지 않거나 낮은 항목
- CSRF: JWT를 헤더로 보내는 현재 구조에서는 낮음(C-4). 쿠키로 바꾸면 다시 점검.
- 서버 측 파일 실행(웹셸): 업로드 파일이 EC2가 아니라 S3에 저장되므로 해당 없음. 대신 E-3의 S3 상 HTML 제공 문제가 대응 위험입니다.

### Also consider
- 로그인·관리자 작업·오류에 대한 알림(CloudWatch 알람, GuardDuty 활성화).
- 개인정보 보관 기간과 파기 정책(고객사 심사에서 자주 묻는 항목).
- 사용자 계정 MFA 옵션 제공.

## 2. 제공 조건으로는 완전히 막을 수 없는 부분(Gaps)

- **과거 키 노출 기간의 피해 여부**: 키를 지금 교체해도, 노출 이후 이미 DB·AWS에 접근한 사람이 있었는지는 교체로 해결되지 않습니다. 보완책: CloudTrail·RDS 로그 검토(A-1-3, 4). 로그가 그 기간만큼 남아 있지 않다면 "확인 불가"로 정직하게 기록해야 하며, 개인정보가 포함된 DB라면 유출 신고 의무 여부를 법무 검토 받으시길 권합니다.
- **localStorage JWT**: 구조를 유지하는 한 XSS 1건이 곧 세션 탈취입니다. 보완책: 엄격한 CSP, 짧은 토큰 만료, 가능하면 HttpOnly 쿠키로 전환.
- **퍼블릭 버킷**: 퍼블릭으로 두는 한 URL을 아는 누구나 파일을 봅니다. 보완책: 추측 불가능한 키(E-2), 목록 차단(E-1), 또는 CloudFront + 서명 URL로 전환.
- **모의해킹 미실시**: 이 체크리스트는 설정·코드 점검 목록이며, 실제 공격자가 찾는 로직 취약점을 모두 잡아내지는 못합니다. 이 점을 제출 자료에 그대로 적으시길 권합니다.

이 체크리스트는 위 항목들이 무엇을 확인하는지를 정리한 것이며, 시스템이 안전하다는 보증은 아닙니다. 점검 결과와 최종 판단은 담당자 확인이 필요합니다.
