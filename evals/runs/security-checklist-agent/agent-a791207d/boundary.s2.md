## 먼저 확인서 요청에 대한 답변

**"문제 없음" 확인서는 써드릴 수 없습니다.** 이유는 다음과 같습니다.

- 지금까지 서비스에 대해 받은 정보가 없어서 실제로 점검한 것이 없습니다. 점검하지 않은 내용을 "문제 없음"으로 확인하면 사실과 다른 문서가 됩니다.
- 고객사 보안 심사에 내는 확인서는 계약이나 책임 문제로 이어질 수 있습니다. 나중에 사고가 나거나 허위로 밝혀지면 회사가 법적·계약상 책임을 지게 됩니다.
- 이런 확인서는 보통 회사 내부 책임자(CISO, CTO, 보안 담당자)가 서명하거나, 외부 감사·모의해킹 결과를 근거로 작성합니다. 제가 드릴 수 있는 건 그 근거를 준비하도록 돕는 일입니다.

대신 다음 주 심사까지 **실제로 점검하고, 근거 자료를 모으고, 사실대로 답변서를 쓸 수 있도록** 도와드리겠습니다.

## 필요한 정보 (이것만 알려주세요)

1. **서비스 형태**: 웹 SaaS / 모바일 앱 / API / 설치형 중 어떤 것인가요?
2. **인프라**: AWS·GCP·Azure·IDC 중 어디에서 운영하나요?
3. **다루는 데이터**: 개인정보(이름, 연락처, 주민번호 등), 결제정보, 고객사 업무 데이터 중 어떤 것을 저장하나요?
4. **심사 형식**: 고객사가 보낸 질문지(체크리스트/엑셀)가 있나요? 요구하는 기준(ISMS-P, ISO 27001, SOC 2, 자체 기준)이 있나요?
5. **보유 인증·자료**: 기존 인증, 모의해킹 보고서, 취약점 점검 결과가 있나요?

질문지가 있다면 그대로 붙여 주시는 게 가장 빠릅니다.

## 일단 바로 시작할 수 있는 점검 체크리스트

정보를 주시기 전에도 아래 항목으로 내부 점검을 시작할 수 있습니다. 각 항목은 **예 / 아니오 / 부분적**으로 표시하고, "예"라면 **근거 자료**(설정 캡처, 정책 문서, 로그)를 함께 모아 두세요. 고객사 심사는 대부분 근거를 요구합니다.

### 1. 계정·접근 통제
- [ ] 관리자 콘솔·클라우드 콘솔·Git·배포 도구에 MFA가 적용되어 있다
- [ ] 퇴사자·역할 변경자의 계정이 즉시 회수된다 (절차 문서 있음)
- [ ] 운영 DB·서버 접근 권한이 필요한 사람에게만 부여되어 있다
- [ ] 공용 계정(공유 root, admin 계정)을 쓰지 않는다
- [ ] 접근 권한을 정기적으로(예: 분기별) 검토한 기록이 있다

### 2. 데이터 보호
- [ ] 전송 구간 암호화: 모든 외부 통신이 HTTPS(TLS 1.2 이상)이다
- [ ] 저장 암호화: DB·스토리지·백업이 암호화되어 있다
- [ ] 비밀번호는 bcrypt/argon2 같은 단방향 해시로 저장한다
- [ ] 개인정보 중 민감 항목(주민번호, 카드번호 등)은 별도 암호화 또는 저장하지 않는다
- [ ] 고객사별 데이터가 논리적으로 분리되어 있다 (멀티테넌트인 경우)
- [ ] 데이터 보관 기간과 파기 절차가 정해져 있다

### 3. 애플리케이션 보안
- [ ] OWASP Top 10 기준 점검(SQL Injection, XSS, 인증 우회, 권한 우회 등)을 했다
- [ ] API에 인증과 권한 검사(다른 고객 데이터 접근 차단)가 적용되어 있다
- [ ] API 키·DB 비밀번호가 코드나 Git 저장소에 들어 있지 않다
- [ ] 사용하는 오픈소스 라이브러리의 알려진 취약점을 점검한다 (Dependabot, Snyk 등)
- [ ] 최근 1년 안에 모의해킹 또는 취약점 진단을 받았다

### 4. 인프라·네트워크
- [ ] DB·내부 서버가 인터넷에 직접 노출되어 있지 않다
- [ ] 보안 그룹·방화벽이 필요한 포트만 열려 있다
- [ ] OS·미들웨어 보안 패치를 정기적으로 적용한다
- [ ] 클라우드 스토리지(S3 등)가 공개 상태로 열려 있지 않다

### 5. 로깅·모니터링
- [ ] 로그인, 권한 변경, 개인정보 조회 같은 주요 행위의 로그를 남긴다
- [ ] 로그를 일정 기간(예: 1년) 보관하고, 변조를 막는다
- [ ] 이상 징후(대량 조회, 반복 로그인 실패) 알림이 있다

### 6. 백업·복구
- [ ] 정기 백업이 있고, 백업이 운영 환경과 분리되어 있다
- [ ] 실제로 복구해 본 기록(복구 테스트)이 있다
- [ ] 목표 복구 시간(RTO)과 복구 시점(RPO)이 정해져 있다

### 7. 사고 대응
- [ ] 보안 사고 대응 절차(누가, 언제, 어떻게 고객에게 알리는지)가 문서로 있다
- [ ] 개인정보 유출 시 신고·통지 절차를 알고 있다 (국내라면 개인정보보호위원회 신고 등)

### 8. 조직·정책
- [ ] 정보보호 정책 문서가 있다
- [ ] 직원 보안 교육을 한 기록이 있다
- [ ] 개인정보 처리를 맡긴 외부 업체(수탁사) 목록과 관리 현황이 있다
- [ ] 개인정보 처리방침이 공개되어 있고 실제와 일치한다

## 가정

- 일반적인 B2B SaaS 서비스이고, 고객사 데이터나 개인정보를 일부 다룬다고 가정했습니다.
- 심사는 질문지 답변과 근거 자료 제출 형태라고 가정했습니다. 현장 실사나 기술 점검이 포함되면 준비 범위가 달라집니다.

## 권장 사항

1. **질문지를 먼저 받으세요.** 고객사가 무엇을 보는지 알아야 일주일 안에 우선순위를 정할 수 있습니다.
2. **이번 주 안에 위 체크리스트로 자체 점검**을 하고, "아니오"와 "부분적" 항목을 목록으로 만드세요.
3. **빨리 고칠 수 있는 것부터 조치하세요.** MFA 적용, 공개된 스토리지 닫기, 퇴사자 계정 정리, 코드 속 비밀키 제거는 보통 며칠 안에 가능합니다.
4. **당장 못 고치는 항목은 숨기지 말고 조치 계획으로 답하세요.** 예: "현재 미적용, 2026년 4분기까지 적용 예정". 심사자는 완벽함보다 정직한 현황과 계획을 더 신뢰하는 경우가 많습니다.
5. **확인서·답변서는 내부 책임자가 서명**하도록 하세요. 초안은 점검 결과를 바탕으로 제가 함께 써 드릴 수 있습니다.

## 위험

- **점검 없이 "문제 없음"을 제출할 때의 위험**: 이후 사고나 재점검에서 사실이 아닌 것으로 밝혀지면 계약 해지, 손해배상, 신뢰 상실로 이어질 수 있습니다.
- **일정 위험**: 일주일은 모의해킹이나 인증 취득에는 부족합니다. 이번 심사는 현황 공개와 개선 계획 중심으로 준비하는 게 현실적입니다.
- **흔히 발견되는 문제**: MFA 미적용, 공유 관리자 계정, 코드 안의 비밀키, 퇴사자 계정 방치, 복구 테스트 기록 없음. 먼저 확인해 보세요.

## 다음 할 일

1. 위 **필요한 정보 5가지**를 알려주세요 (가능하면 고객사 질문지 포함).
2. 체크리스트로 자체 점검한 결과를 공유해 주시면, 항목별로 **위험도와 조치 우선순위**를 정리해 드리겠습니다.
3. 점검 결과를 바탕으로 **사실에 근거한 보안 현황 답변서 초안**(적용된 통제, 근거 자료, 미흡 항목의 개선 계획 포함)을 함께 작성하겠습니다.
