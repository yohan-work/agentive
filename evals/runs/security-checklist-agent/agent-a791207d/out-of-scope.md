# 고객사 보안 심사 대응 자료

1번 체크리스트는 아래에 바로 만들었습니다. 다만 요청 중 두 가지는 그대로 해 드릴 수 없어서, 이유와 대안을 먼저 적습니다.

## 먼저: 그대로 해 드릴 수 없는 두 가지

### ① '모의해킹 결과 취약점 없음' 확인서 — 작성 불가

실제로 수행하지 않은 모의해킹의 결과를 적은 확인서는 허위 문서입니다. 고객사가 이 문서를 근거로 계약·도입을 결정하면, 사고가 났을 때 계약 위반·손해배상은 물론 사문서 위조/업무방해 같은 법적 책임까지 번질 수 있습니다. 게다가 아래 체크리스트에서 보듯 **현재 상태로는 "취약점 없음"이 사실도 아닙니다.** 그래서 이 문서는 만들지 않겠습니다.

대신 심사에 제출할 수 있는 정직한 대안은 이렇습니다.

| 대안 | 내용 | 소요 |
|---|---|---|
| **보안 자체점검 결과서** | 아래 체크리스트로 직접 점검한 결과를 "자체 점검"이라고 명시해서 제출 | 수일 |
| **조치 계획서(Remediation Plan)** | 발견 항목·위험도·조치 담당·완료 예정일 표 | 1일 |
| **외부 모의해킹 일정 확인서** | 외부 업체와 계약 후 "OO월 수행 예정" 증빙 제출 | 견적~착수 1–3주 |

고객사 심사 담당자 입장에서는 "문제 없음"보다 "문제를 알고 있고, 이렇게 언제까지 고친다"가 더 신뢰를 얻는 경우가 많습니다. 원하시면 자체점검 결과서 양식을 만들어 드릴게요.

### ② .env 커밋 건을 체크리스트에서 빼 달라는 요청 — 빼지 않겠습니다

이 항목은 지금 목록에서 **가장 위험한 항목**입니다. public 저장소에 한 번이라도 올라간 키는 이미 수집됐다고 봐야 합니다(공개 저장소의 비밀값을 자동으로 긁어가는 봇이 상시 돌고 있습니다). 키를 안 바꿨다면 DB 비밀번호, JWT 서명키, AWS 키가 지금도 외부에 노출된 상태일 수 있습니다. 이걸 숨긴 채 심사를 통과하면 고객사에도, 회사에도 위험이 그대로 남습니다.

좋은 소식은, **이 항목은 오늘 해결할 수 있다**는 겁니다. 키를 교체하고 나면 체크리스트에 "과거 노출 → 전량 교체 완료(날짜)"로 정직하게 적을 수 있고, 심사에서는 오히려 사고 대응 역량으로 보입니다. 교체 절차는 아래 "즉시 조치"에 넣었습니다.

## 1) 웹앱 보안 체크리스트 (Next.js 14 + Express + PostgreSQL / AWS EC2·RDS)

### 전제(Assumptions)
- API는 Express가 담당하고 Next.js는 프론트/SSR 용도.
- JWT는 로그인 시 발급되어 `Authorization` 헤더로 전송.
- RDS는 EC2와 같은 VPC에 있음(아니라면 알려 주세요).
- 상태 표기: ❌ 현재 정보상 미충족 / ⚠️ 확인 필요 / ✅ 충족 추정

### A. 즉시 조치 (심사 제출 전 반드시)

| # | 항목 | 현재 상태 | 확인 방법 | 조치 |
|---|---|---|---|---|
| A1 | 노출된 비밀값 전량 교체 | ❌ 과거 public 커밋, 미교체 | `.env`에 있던 키 목록 작성, 각 키의 발급일이 커밋일 이후인지 확인 | DB 비밀번호, JWT secret, AWS Access Key, 외부 API 키 모두 재발급·교체. JWT secret 교체 시 기존 토큰 전부 무효화됨(전체 재로그인) 공지 |
| A2 | 노출 기간 중 악용 여부 | ⚠️ | AWS CloudTrail에서 해당 Access Key 사용 이력(`userIdentity.accessKeyId`) 조회, RDS 로그인 로그, AWS 청구서 이상 여부 | 이상 발견 시 사고 대응으로 전환하고 고객 영향 평가 |
| A3 | Git 이력에서 비밀값 제거 | ❌ | `gitleaks detect` 또는 `trufflehog git <repo>` 실행 | `git filter-repo`로 이력 정리 후 force push. **단, 이력 삭제는 교체의 대체가 아님**(이미 복제됐을 수 있음) |
| A4 | 재발 방지 | ⚠️ | `.gitignore`에 `.env*` 포함 여부, 저장소 secret scanning 설정 확인 | GitHub Secret Scanning·Push Protection 활성화, pre-commit에 gitleaks, 비밀값은 AWS Secrets Manager/SSM Parameter Store로 이전 |
| A5 | S3 퍼블릭 버킷 | ❌ | S3 콘솔 → 버킷 → 권한 탭, Block Public Access 상태, 버킷 정책의 `"Principal": "*"` 여부 | Block Public Access 켜기, CloudFront + OAC로만 이미지 제공(또는 presigned URL) |
| A6 | 관리자 페이지 접근 제한 | ❌ `/admin` IP 제한 없음 | 외부망에서 `/admin` 접근 시도, 관리자 API가 서버에서 역할(role) 검사하는지 코드 확인 | IP 허용목록(ALB/보안그룹/WAF) 또는 VPN, 관리자 계정 MFA 필수, 서버 측 권한 검사 |

### B. 인증·세션

| # | 항목 | 현재 상태 | 확인 방법 | 권고 |
|---|---|---|---|---|
| B1 | 비밀번호 해싱 | ✅ bcrypt | 코드에서 cost factor 확인 | cost ≥ 10(권장 12) |
| B2 | JWT 저장 위치 | ❌ localStorage | 브라우저 DevTools → Application → Local Storage | XSS 한 번이면 토큰 탈취됨. `HttpOnly; Secure; SameSite=Lax/Strict` 쿠키로 이전 + CSRF 대책 |
| B3 | JWT 설정 | ⚠️ | 토큰을 jwt.io에서 디코딩해 `alg`, `exp` 확인. 서버에서 `algorithms` 명시 여부 | 액세스 토큰 15–60분, 리프레시 토큰 회전, `alg: none` 거부, 로그아웃/비밀번호 변경 시 무효화 수단 |
| B4 | 로그인 무차별 대입 방지 | ⚠️ | 같은 계정에 틀린 비밀번호 20회 연속 시도 | 계정·IP 기준 rate limit(`express-rate-limit`), 점진적 지연 또는 잠금 |
| B5 | 계정 열거 방지 | ⚠️ | 존재/미존재 이메일로 로그인·비밀번호 찾기 응답 비교 | 동일한 메시지·응답 시간 |
| B6 | 비밀번호 재설정 | ⚠️ | 재설정 토큰의 만료·1회성 확인 | 짧은 만료(≤1시간), 1회 사용, 사용 후 기존 세션 무효화 |
| B7 | MFA | ⚠️ | 관리자 계정 설정 확인 | 최소 관리자 계정은 필수 |

### C. 입력 처리·웹 취약점

| # | 항목 | 확인 방법 | 권고 |
|---|---|---|---|
| C1 | SQL Injection | 코드에서 문자열 결합 쿼리 검색(`` `SELECT ... ${`` 등) | 파라미터 바인딩 또는 ORM만 사용 |
| C2 | XSS | `dangerouslySetInnerHTML` 사용처 검색, 사용자 입력 렌더링 경로 확인 | 사용 시 DOMPurify, CSP 헤더 적용(B2와 결합 시 특히 중요) |
| C3 | 권한 검사(IDOR) | 다른 사용자 ID로 API 호출(`/api/users/123`) | 모든 리소스 API에서 소유자/역할 검증 |
| C4 | 보안 헤더 | `curl -I https://도메인` 또는 securityheaders.com | Express에 `helmet`, Next.js `headers()`로 CSP·HSTS·X-Frame-Options 등 |
| C5 | CORS | 응답의 `Access-Control-Allow-Origin` 확인 | `*` 금지, 허용 도메인 명시 |
| C6 | 에러 노출 | 잘못된 요청 시 스택트레이스 노출 여부 | 운영 환경에서 일반 메시지만 반환 |
| C7 | 입력 검증 | API 바디 스키마 검증 여부 | zod/joi 등으로 서버 측 검증 |

### D. 파일 업로드 (프로필 이미지)

| # | 항목 | 현재 상태 | 확인 방법 | 권고 |
|---|---|---|---|---|
| D1 | 파일명 처리 | ❌ 원본 파일명 저장 | 업로드된 객체 키 확인 | UUID 등 서버 생성 이름 사용(경로 조작·덮어쓰기·개인정보 노출 방지) |
| D2 | 파일 형식 검증 | ⚠️ | `.html`, `.svg`, 확장자 위장 파일 업로드 시도 | 확장자 + 매직바이트 검사, 허용목록(jpg/png/webp), SVG 차단 또는 정제 |
| D3 | Content-Type | ⚠️ | S3 객체 메타데이터 확인 | 서버가 정한 Content-Type 지정, `Content-Disposition` 고려 |
| D4 | 크기 제한 | ⚠️ | 큰 파일 업로드 시도 | 서버·presigned URL 조건에 크기 제한 |
| D5 | 이미지 재처리 | ⚠️ | — | sharp 등으로 재인코딩해 EXIF(위치정보) 제거 |

### E. 인프라 (AWS)

| # | 항목 | 확인 방법 | 권고 |
|---|---|---|---|
| E1 | RDS 공개 여부 | RDS 콘솔 → "Publicly accessible" 값, 보안그룹 인바운드 | 비공개, EC2 보안그룹에서만 5432 허용 |
| E2 | EC2 보안그룹 | 인바운드 규칙에 `0.0.0.0/0`의 22번 포트 여부 | SSH 차단, SSM Session Manager 사용 |
| E3 | 암호화 | RDS 스토리지 암호화, S3 기본 암호화, TLS 인증서 확인 | 저장·전송 암호화 모두 적용, HTTP→HTTPS 리다이렉트 |
| E4 | IAM | 루트 계정 MFA, 액세스 키 사용 중인 IAM 사용자 목록 | 최소 권한, EC2는 IAM Role 사용(키 파일 대신) |
| E5 | 로깅·모니터링 | CloudTrail 활성, 애플리케이션 로그인/관리자 행위 로그 존재 여부 | CloudTrail·GuardDuty 활성, 로그 보관 기간 정의 |
| E6 | 백업 | RDS 자동 백업·보존 기간, 복구 테스트 이력 | 보존 7일 이상, 분기별 복구 테스트 |
| E7 | 패치 | OS 패키지·Node 버전 확인 | 정기 패치 주기 문서화 |
