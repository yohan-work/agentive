두 가지 중 1)번 체크리스트는 바로 만들어 드릴게요. 다만 2)번과 .env 건은 요청하신 그대로는 도와드리기 어렵습니다. 이유부터 짧게 말씀드리고, 대신 쓸 수 있는 방법을 같이 드리겠습니다.

## 먼저: 도와드리기 어려운 두 가지

**① '모의해킹 결과 취약점 없음' 확인서**
모의해킹을 하지 않았는데 "취약점 없음"이라고 쓴 확인서는 고객사를 속이는 허위 문서가 됩니다. 계약서의 보안 조항이나 진술·보증 위반이 될 수 있고, 나중에 사고가 나면 회사와 서명한 사람 모두 법적 책임을 크게 지게 됩니다. 게다가 아래에서 보시듯 지금 구성에는 실제로 확인된 취약점이 여러 개 있어서, "취약점 없음"은 사실과도 맞지 않습니다.

**② 체크리스트에서 .env 커밋 건 빼기**
이 문제는 목록에서 뺀다고 없어지지 않습니다. public 저장소에 한 번이라도 올라간 비밀값은 이미 유출된 것으로 봐야 합니다. 공개 GitHub을 긁어 가는 자동 봇이 많아서, 보통 커밋 후 몇 분 안에 수집됩니다. 커밋을 지우거나 히스토리를 고쳐도 포크, 캐시, 이미 수집된 사본은 그대로 남습니다. 이걸 숨긴 채 심사를 통과했다가 나중에 사고가 나면, 알면서 숨긴 게 되어 훨씬 심각해집니다.

좋은 소식은 **키를 교체하는 데는 보통 몇 시간이면 충분하다**는 점입니다. 교체를 마치면 "과거 노출 사고를 발견해 조치 완료"라고 쓸 수 있고, 심사에서는 오히려 좋은 인상을 주는 항목이 됩니다.

## 1) 웹앱 보안 체크리스트

앱 구성: Next.js 14 + Express API + PostgreSQL / AWS EC2, RDS

"현재 상태" 칸은 말씀해 주신 정보를 바탕으로 채웠습니다. 나머지 칸은 직접 확인하신 뒤 채워 주세요.

### A. 비밀값 및 자격증명 관리

| # | 항목 | 확인 방법 | 현재 상태 |
|---|---|---|---|
| A1 | 소스 저장소(히스토리 포함)에 비밀값이 없음 | `gitleaks detect` 또는 `trufflehog git`으로 전체 히스토리 스캔. `.gitignore`에 `.env*`가 들어 있는지 확인 | **미흡**: 과거 public 저장소에 `.env` 커밋 |
| A2 | 노출된 비밀값을 모두 교체했음 | 키별 교체 날짜를 기록. AWS IAM 콘솔에서 이전 액세스 키가 비활성화 또는 삭제됐는지 확인 | **미조치** → 교체 후 "조치 완료"로 갱신 |

| # | 항목 | 확인 방법 | 현재 상태 |

## 2) 확인서 대신 고객사에 낼 수 있는 것

허위 확인서 대신, 아래 중 사정에 맞는 것을 쓰시면 됩니다.

**옵션 A: 자체 보안 점검 결과서 (지금 바로 가능)**
위 체크리스트를 실제로 점검한 결과를 정리한 문서입니다. 이름부터 정직하게 쓰면 됩니다.

> **자체 보안 점검 결과서**
> - 점검 방식: 내부 인력의 체크리스트 기반 점검 (외부 모의해킹 아님)
> - 점검 일자 / 점검자 / 점검 범위
> - 점검 결과: 항목별 양호 / 조치 완료 / 조치 예정 (예정 항목은 완료 목표일 포함)
> - 주요 조치 이력: 예) "2026-10-xx 과거 저장소 노출 이력이 있는 자격증명 전체 교체 및 접근 로그 검토 완료"
> - 향후 계획: 외부 모의해킹 실시 예정 시기

많은 고객사 심사는 "모의해킹을 했느냐"보다 "위험을 알고 관리하고 있느냐"를 봅니다. 발견하고 조치한 이력과 명확한 계획은 대개 긍정적으로 평가됩니다.

**옵션 B: 외부 모의해킹 진행**
고객사가 모의해킹 결과를 꼭 요구한다면 외부 전문 업체에 맡기는 것이 유일한 방법입니다. 웹앱 하나 규모면 보통 1~2주 정도 걸립니다. **위의 "지금 바로 해야 할 일" 5개를 먼저 조치한 뒤에** 받으시는 게 결과도 좋고 비용도 아낍니다. 일정이 빠듯하다면 고객사에 "모의해킹 예정일 및 결과 제출 예정일"을 알리고 옵션 A 문서를 먼저 내는 방법도 흔히 받아들여집니다.
