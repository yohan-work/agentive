보안 점검 준비는 기꺼이 도와드릴게요. 다만 **"문제 없음" 확인서는 제가 써드릴 수 없습니다.** 이유는 두 가지예요.

1. **저는 아직 서비스에 대해 아무것도 보지 못했습니다.** 코드, 인프라 구성, 설정, 운영 절차를 보지 않은 상태에서 "문제 없음"이라고 쓰면 사실이 아닌 문서가 됩니다.
2. **보안 확인서는 책임이 따르는 문서입니다.** 고객사 보안 심사에 제출하는 확인서는 보통 회사의 보안 책임자(CISO/담당자)나 외부 감사·인증 기관이 서명합니다. AI가 쓴 "문제 없음" 문서는 심사에서 근거로 인정받기 어렵고, 나중에 사고가 나면 허위 확인으로 문제가 될 수도 있습니다.

대신 다음 주 심사까지 **실제로 점검하고, 근거를 갖춘 답변을 준비하는 것**은 충분히 도와드릴 수 있어요.

## 1. 먼저 알려주시면 좋은 것

- 서비스 형태: 웹 / 모바일 앱 / API / SaaS 등
- 인프라: AWS·GCP·Azure·온프레미스 등
- 다루는 데이터: 개인정보, 결제정보, 고객사 기밀 데이터 여부
- 고객사가 보낸 **보안 질문지나 체크리스트**가 있는지 (있으면 그걸 기준으로 맞추는 게 가장 효율적입니다)
- 보유 인증: ISMS/ISMS-P, ISO 27001, SOC 2 등

## 2. 보안 심사에서 흔히 묻는 항목 (자가 점검용)

**계정·접근 관리**
- [ ] 관리자 계정에 MFA(2단계 인증) 적용
- [ ] 퇴사자 계정 즉시 회수 절차
- [ ] 최소 권한 원칙, 권한 부여·변경 기록
- [ ] 공용 계정/공유 비밀번호 사용 여부

**데이터 보호**
- [ ] 전송 구간 암호화(HTTPS/TLS 1.2 이상)
- [ ] 저장 데이터 암호화(DB, 백업, 스토리지)
- [ ] 비밀번호는 bcrypt/argon2 등으로 해시 저장
- [ ] 개인정보 보관 기간·파기 절차

**애플리케이션 보안**
- [ ] SQL 인젝션, XSS, CSRF 등 OWASP Top 10 대응
- [ ] 입력값 검증, 인증·세션 관리
- [ ] 의존성 라이브러리 취약점 점검(예: Dependabot, npm audit, Snyk)
- [ ] API 키·비밀값이 코드 저장소에 들어가 있지 않은지

**인프라·운영**
- [ ] 불필요한 포트/서비스 차단, 보안 그룹 설정
- [ ] OS·미들웨어 보안 패치 주기
- [ ] 접근·변경 로그 수집 및 보관 기간
- [ ] 백업과 복구 테스트 실시 여부

**정책·조직**
- [ ] 보안 사고 대응 절차(누가, 몇 시간 내에, 고객사에 어떻게 통보하는지)
- [ ] 임직원 보안 교육 이력
- [ ] 외주·협력사 보안 관리
- [ ] 최근 취약점 진단 또는 모의해킹 결과

## 3. 일주일 안에 할 수 있는 현실적인 준비

1. **고객사 질문지 확보** → 항목별로 "예 / 아니오 / 부분 적용"과 근거를 정리
2. **빠르게 확인 가능한 것부터 점검**: MFA, HTTPS 설정, 저장소 내 비밀값, 의존성 취약점 스캔
3. **증빙 자료 모으기**: 설정 화면 캡처, 정책 문서, 로그 보관 설정, 교육 이력 등
4. **미흡한 항목은 숨기지 말고 개선 계획으로 제시**: "현재 미적용, ○월까지 적용 예정"처럼 쓰는 편이 심사에서 훨씬 신뢰를 얻습니다
5. **확인서는 회사 명의로**: 점검 결과를 바탕으로 보안 담당자가 사실대로 작성·서명
