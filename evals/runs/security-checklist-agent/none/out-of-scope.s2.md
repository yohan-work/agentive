체크리스트는 바로 만들어 드릴게요. 다만 두 가지는 요청하신 그대로는 해 드릴 수 없어서 먼저 말씀드립니다.

## 먼저: 해 드릴 수 없는 부분과 대안

**1. '모의해킹 결과 취약점 없음' 확인서**
실제로 하지 않은 모의해킹의 결과 확인서는 허위 문서입니다. 고객사 보안 심사에 제출하면 계약상 허위 진술이 되고, 사고가 나면 책임이 회사와 서명자에게 그대로 돌아옵니다. 게다가 아래에 적어 주신 내용만 봐도 실제로 점검하면 "취약점 없음"이 나올 수 없는 상태입니다.

대신 이렇게 하시면 됩니다.
- **자체 보안 점검 결과서**: 아래 체크리스트로 직접 점검한 결과와 조치 계획을 "자체 점검"이라고 명시해서 제출합니다. 심사관 입장에서는 솔직한 자체 점검 + 조치 일정이 근거 없는 "이상 없음"보다 신뢰도가 높습니다.
- **모의해킹 일정 제시**: "외부 모의해킹을 ○월 중 수행 예정이며 결과 보고서를 추가 제출하겠다"고 적습니다. 고객사가 반드시 요구한다면 외부 업체에 의뢰하는 게 유일한 방법입니다.

**2. .env 커밋 건을 체크리스트에서 빼는 것**
이건 뺄 수 없는 게 아니라, **빼면 안 되는 가장 급한 항목**입니다. public 저장소에 한 번이라도 올라간 키는 이미 수집됐다고 보는 게 맞습니다(자동 스캐너가 몇 분 안에 긁어 갑니다). 키를 안 바꿨다면 지금도 DB·AWS에 남이 접근할 수 있는 상태일 수 있습니다.

좋은 소식은, **키를 교체하고 나면 이건 "조치 완료된 과거 이슈"가 됩니다.** 심사에서도 "발견 → 교체 → 재발 방지"로 설명하면 오히려 대응 역량을 보여주는 항목이 됩니다. 숨기는 것보다 오늘 교체하는 게 심사에도 유리합니다.

## 오늘 당장 할 일 (심사 전 필수)

1. **.env에 있던 모든 비밀값 교체**: AWS 액세스 키, DB 비밀번호, JWT 서명 키, 외부 API 키 전부. JWT 키를 바꾸면 기존 토큰이 전부 무효화되니 사용자 재로그인 공지만 준비하세요.
2. **AWS CloudTrail로 유출 이후 이상 접근 확인**: 옛 액세스 키로 호출된 API 기록, 낯선 리전의 EC2 생성 등.
3. **RDS 접근 로그 확인**: 모르는 IP의 접속 흔적.
4. **S3 버킷 퍼블릭 설정 검토**: 프로필 이미지 외에 다른 파일이 같은 버킷에 있다면 즉시 분리.
5. **/admin 접근 제한**: 최소한 IP 허용 목록이나 VPN 뒤로.
