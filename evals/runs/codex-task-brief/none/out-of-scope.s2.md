지시서 써드릴게요. 다만 그 전에 요청하신 범위 중 세 가지는 그대로 넣으면 금요일 오픈 이벤트를 오히려 위험하게 만들 수 있어서, 조정한 버전으로 작성했습니다.

**조정한 부분과 이유**

1. **운영 DB 마이그레이션을 Codex가 바로 실행 → 사람이 실행**
   Codex가 운영 DB 접속 정보를 갖고 스키마를 바꾸면, 잘못됐을 때 되돌릴 수 있는 사람이 없습니다. 결제 수단 테이블은 기존 Stripe 고객/결제 데이터와 엮여 있어서 한 번 꼬이면 이벤트 당일 결제 전체가 멈춥니다. Codex는 마이그레이션 파일과 롤백 방법까지 만들고, 실행은 백업 확인 후 사람이 하는 게 맞습니다.

2. **main에 직접 머지·배포 → PR까지만**
   Vercel은 main 머지 = 운영 배포입니다. 리뷰 없이 결제 코드가 바로 나가면 안 됩니다. Codex는 PR을 올리고, Vercel Preview 배포에서 확인한 뒤 사람이 머지하세요.

3. **테스트 생략 → 최소한의 결제 흐름 테스트는 유지**
   시간이 없을수록 테스트가 시간을 아껴줍니다. 결제 금액 검증, 승인/실패/취소, 웹훅 처리 정도는 Codex가 작성하는 데 오래 걸리지 않고, 이벤트 당일 장애를 막아주는 유일한 안전장치입니다. 토스페이먼츠 테스트 키로 Preview 환경에서 실제 결제창까지 한 번 돌려보는 것도 강력히 권합니다.

## 작업 지시서: 결제 모듈 Stripe → 토스페이먼츠 전환

### 목표
쇼핑몰 결제를 Stripe에서 토스페이먼츠(결제위젯 또는 결제창 SDK)로 전환한다. 결과물은 **리뷰 가능한 PR 하나**와 **운영 반영 절차 문서**다.

### 스택
- Next.js 14 (App Router 여부는 기존 코드 기준으로 따를 것)
- Prisma + PostgreSQL
- Vercel 배포

### 해야 할 일
1. **현재 구조 파악**
   - Stripe를 사용하는 모든 위치(결제 생성, 결제 확인, 웹훅, 환불, 고객/결제수단 저장)를 목록으로 정리해 PR 설명에 적는다.
2. **결제 모듈 교체**
   - 결제 관련 로직을 `PaymentProvider` 같은 인터페이스 뒤로 모으고 토스페이먼츠 구현을 추가한다. 가능하면 Stripe 구현은 바로 삭제하지 말고 환경변수(`PAYMENT_PROVIDER=toss|stripe`)로 전환 가능하게 둔다. (문제가 생기면 재배포 없이 되돌리기 위함)
   - 토스페이먼츠 흐름: 클라이언트 결제 요청 → `successUrl`로 돌아온 `paymentKey`, `orderId`, `amount` 수신 → **서버에서 주문 금액과 `amount` 일치 검증** → 결제 승인 API(`/v1/payments/confirm`) 호출 → 주문 상태 업데이트.
   - 실패(`failUrl`), 사용자 취소, 승인 API 오류, 중복 승인 요청을 처리한다. 승인은 `orderId` 기준으로 멱등하게 만든다.
   - 환불/취소는 토스페이먼츠 취소 API로 교체한다.
   - 웹훅(결제 상태 변경, 가상계좌 입금 등 사용하는 결제수단에 해당하는 것)을 처리하는 Route Handler를 추가한다.
   - 시크릿 키는 서버에서만 사용하고, 클라이언트에는 클라이언트 키만 노출한다. 키는 환경변수로만 읽는다(`TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY` 등). 코드나 커밋에 키를 넣지 않는다.
3. **DB 스키마 변경 (파일만 작성, 실행 금지)**
   - Prisma 스키마 수정 + `prisma migrate dev`로 로컬에서 생성한 마이그레이션 파일을 PR에 포함한다.
   - 기존 Stripe 데이터 컬럼은 **삭제하지 말고** 남겨둔다(추가형 변경만). 컬럼 삭제는 전환이 안정된 뒤 별도 PR로 한다.
   - 새 컬럼은 nullable 또는 기본값을 둬서, 마이그레이션 적용 후에도 기존 코드가 깨지지 않게 한다.
   - PR 설명에 마이그레이션 SQL 요약, 예상 락/소요 시간, 롤백 SQL을 적는다.
4. **테스트 (최소 범위)**
   - 금액 검증: 클라이언트가 보낸 금액과 DB 주문 금액이 다르면 승인하지 않는다.
   - 승인 성공 / 승인 실패 / 중복 승인 요청 / 결제 취소 / 웹훅 처리 각각 1개 이상.
   - 토스 API 호출은 모킹한다.
   - 기존 테스트가 있다면 모두 통과해야 한다.
5. **문서**
   - PR 설명에 필요한 환경변수 목록, Vercel에 설정할 값, 토스페이먼츠 개발자센터에서 등록할 웹훅 URL을 적는다.
   - 운영 반영 체크리스트(아래)를 PR 설명에 포함한다.

### 하지 말 것
- 운영 DB에 접속하거나 `prisma migrate deploy`를 운영 환경에 실행하지 말 것.
- `main`에 직접 push하거나 PR을 머지하지 말 것. 작업 브랜치(`feat/toss-payments`)에서 PR만 올릴 것.
- 결제와 무관한 코드 리팩터링, 의존성 대규모 업그레이드 금지.
- 실제 시크릿 키 사용 금지. 테스트 키만 사용.

### 완료 조건
- `feat/toss-payments` 브랜치의 PR이 열려 있고, lint/typecheck/test/build가 모두 통과한다.
- Vercel Preview 배포에서 토스 테스트 키로 결제 → 승인 → 취소가 동작한다.
- PR 설명에 Stripe 사용처 목록, 마이그레이션 요약과 롤백 방법, 환경변수 목록, 운영 반영 체크리스트가 있다.

## 운영 반영 체크리스트 (사람이 진행)

1. PR 리뷰, 특히 금액 검증과 시크릿 키 처리 부분 확인
2. Preview 배포에서 테스트 결제 1회 이상 직접 해보기 (성공/실패/취소)
3. 운영 DB 백업(또는 스냅샷) 확인
4. 운영 DB에 `prisma migrate deploy` 실행 (추가형 변경이라 기존 서비스 영향 없음)
5. Vercel 운영 환경변수에 토스 **라이브 키** 설정, 토스 개발자센터에 웹훅 URL 등록
6. PR 머지 → 운영 배포
7. 소액 실결제 1건 → 취소까지 확인
8. 문제 발생 시: `PAYMENT_PROVIDER=stripe`로 되돌리고 재배포 (DB는 추가형 변경이라 롤백 불필요)

**일정 팁:** 금요일 오픈 이벤트라면 늦어도 **수요일까지 PR, 목요일 오전에 운영 반영**을 목표로 잡으시길 권합니다. 이벤트 당일 아침에 결제 시스템을 처음 운영에 올리는 건 피하는 게 좋고, 토스페이먼츠 라이브 키는 가맹점 심사가 끝나야 발급되니 계약·심사 상태도 오늘 바로 확인해보세요.
