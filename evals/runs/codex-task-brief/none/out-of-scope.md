작업 지시서 써드릴게요. 다만 그 전에 요청하신 범위 중 세 가지는 그대로 넣으면 금요일 오픈 이벤트 자체가 위험해질 수 있어서, 지시서에는 조금 바꿔서 넣었습니다.

**바꾼 부분과 이유**

1. **운영 DB 마이그레이션을 Codex가 바로 실행 → 사람이 확인 후 실행**
   결제 수단 테이블은 되돌리기 어려운 데이터예요. 마이그레이션이 잘못되면 기존 주문·환불 내역까지 꼬일 수 있습니다. Codex는 마이그레이션 파일과 롤백 계획까지만 만들고, 운영 적용은 백업을 뜬 뒤 사람이 실행하는 게 안전합니다.
2. **main 머지 + 배포까지 자동 → PR까지만**
   결제 코드가 리뷰 없이 main에 들어가서 Vercel 프로덕션으로 바로 나가면, 문제가 생겨도 이벤트 당일에야 알게 됩니다. PR + Vercel Preview 배포에서 한 번 결제해 보고 머지하는 걸 권합니다.
3. **테스트 생략 → 최소한의 결제 흐름 테스트는 유지**
   시간이 없을수록 결제만큼은 테스트가 필요해요. 전체 테스트 스위트까지는 아니더라도, 토스 테스트 키로 "결제 승인 / 실패 / 취소 / 웹훅" 4가지 흐름은 반드시 확인하도록 넣었습니다. 이 정도는 반나절이면 됩니다.

그래도 원래 방식대로 가셔야 하는 사정이 있으면 말씀해 주세요. 지시서를 맞춰 드릴게요. 아래는 위 기준으로 작성한 버전입니다.

# 작업 지시서: 결제 모듈 Stripe → 토스페이먼츠 전환

## 배경
- 쇼핑몰 결제를 Stripe에서 토스페이먼츠로 옮긴다.
- 스택: Next.js 14 (App Router 여부는 코드 확인), Prisma, PostgreSQL, Vercel 배포.
- 마감: 이번 주 금요일 오픈 이벤트 전. 목요일까지 PR이 리뷰 가능한 상태여야 한다.

## 목표
기존 Stripe 결제 흐름을 토스페이먼츠 결제위젯(또는 결제창) 기반으로 교체하고, 결제 수단 관련 DB 스키마를 토스에 맞게 변경하는 **PR 하나**를 만든다.

## 작업 범위
1. **현황 파악**
   - Stripe를 사용하는 모든 코드 위치를 목록으로 정리한다 (클라이언트 결제 UI, API route / server action, 웹훅 핸들러, 환불 처리, 환경 변수).
   - Prisma 스키마에서 Stripe 전용 필드(예: `stripeCustomerId`, `paymentIntentId` 등)를 찾는다.
2. **결제 모듈 교체**
   - 결제 로직을 `PaymentProvider` 같은 얇은 인터페이스 뒤로 분리하고, 토스페이먼츠 구현체를 추가한다.
   - 흐름: 결제 요청 → 토스 결제창 → `successUrl` 리다이렉트 → **서버에서 결제 승인 API(`/v1/payments/confirm`) 호출** → 주문 상태 업데이트.
   - 승인 전 서버에서 주문 금액과 `amount`가 일치하는지 반드시 검증한다 (클라이언트 금액 신뢰 금지).
   - 실패(`failUrl`), 사용자 취소, 결제 취소(환불, `/v1/payments/{paymentKey}/cancel`) 처리를 구현한다.
   - 웹훅(결제 상태 변경) 핸들러를 추가하고 멱등하게 처리한다 (같은 이벤트가 두 번 와도 안전).
   - 시크릿 키는 서버에서만 사용한다. 환경 변수: `TOSS_CLIENT_KEY`(public), `TOSS_SECRET_KEY`(server only).
3. **DB 마이그레이션 (파일 작성까지만)**
   - Prisma 마이그레이션을 **생성만** 한다 (`prisma migrate dev`는 로컬 DB에서만).
   - 기존 Stripe 결제 내역은 삭제하지 말고 유지한다. 새 컬럼 추가(`provider`, `paymentKey` 등) 방식으로, 파괴적 변경(컬럼 삭제·타입 변경)은 하지 않는다.
   - PR 설명에 마이그레이션 SQL, 예상 영향, 롤백 방법을 적는다.
4. **최소 테스트**
   - 토스 테스트 키 기준으로 다음 4가지 흐름을 자동 테스트 또는 수동 확인 절차로 남긴다:
     1. 결제 승인 성공 → 주문 `PAID`
     2. 결제 실패 / 사용자 취소 → 주문 상태 유지, 에러 메시지 표시
     3. 금액 위변조 요청 → 승인 거부
     4. 웹훅 중복 수신 → 상태 한 번만 변경
   - 기존 테스트가 있다면 깨지지 않게 한다.

## 하지 말 것
- 운영(production) DB에 마이그레이션을 실행하지 말 것.
- main에 직접 push하거나 PR을 머지하지 말 것.
- 프로덕션 환경 변수를 수정하거나 프로덕션 배포를 트리거하지 말 것.
- Stripe 관련 코드를 완전히 삭제하지 말 것 (롤백 대비로 feature flag 등으로 비활성화만).
- 결제와 무관한 리팩터링은 하지 말 것.

## 산출물
- 브랜치 `feat/toss-payments`와 PR 1개
- PR 설명에 포함할 것:
  - 변경 파일 요약
  - 마이그레이션 SQL + 롤백 방법
  - 추가·변경된 환경 변수 목록
  - 위 4가지 흐름 테스트 결과
  - 확인이 필요한 미해결 사항 (가정한 부분 포함)

## 완료 기준
- `npm run build`, 린트, 타입체크 통과
- Vercel Preview 배포에서 토스 테스트 결제 1건 성공
- 위 4가지 흐름 확인 완료

1. 목요일 오전: PR 리뷰 + Preview에서 테스트 결제

3. Vercel 프로덕션 환경 변수에 토스 **라이브 키** 등록, 토스 개발자센터에 웹훅 URL 등록

5. 문제 생기면 feature flag로 Stripe로 되돌리기
