**그대로 넣지 않은 부분**

1. **Codex가 운영 DB에 마이그레이션을 직접 실행하는 것**: 결제 수단 테이블은 되돌리기 어렵고, 잘못되면 금요일 이벤트 당일에 결제가 멈춥니다. Codex는 마이그레이션 파일만 만들고, 실행은 사람이 백업을 뜬 뒤 합니다.
2. **main에 머지하고 배포까지 하는 것**: Codex는 PR까지만 올립니다. 머지와 프로덕션 배포는 사람이 Vercel Preview에서 확인한 뒤 결정합니다.
3. **테스트 생략**: 전부 빼면 결제 오류를 실제 고객이 먼저 발견하게 됩니다. 대신 범위를 최소한으로 줄였습니다(승인, 실패, 웹훅, 금액 검증). 반나절이면 됩니다.

이 세 가지만 사람이 맡아도 금요일 일정은 충분히 맞출 수 있습니다. 아래가 Codex에 그대로 넘기실 지시서입니다.

# 작업 지시서: 결제 게이트웨이를 Stripe에서 토스페이먼츠로 교체

## 목표
쇼핑몰 결제 흐름을 Stripe에서 토스페이먼츠(결제위젯 + 결제 승인 API)로 교체한다. 결과물은 **리뷰할 수 있는 PR 하나**다. 운영 DB에 대한 작업, main 머지, 프로덕션 배포는 이 작업 범위에 포함되지 않는다.

## 스택
- Next.js 14 (App Router인지 Pages Router인지는 저장소를 보고 판단한다)
- Prisma + PostgreSQL
- Vercel 배포

## 범위 (할 것)
1. **결제 모듈 추상화**
   - 현재 Stripe 호출 지점을 모두 찾아 목록으로 만든다(checkout 생성, 웹훅, 환불, 결제 조회 등).
   - `PaymentProvider` 인터페이스(`createPayment`, `confirmPayment`, `cancelPayment`, `handleWebhook`)를 두고, 토스 구현체를 추가한다.
   - 환경변수 `PAYMENT_PROVIDER=toss|stripe`로 전환한다. 롤백할 수 있도록 Stripe 코드는 이번 PR에서 지우지 않는다.
2. **토스페이먼츠 연동**
   - 클라이언트: 결제위젯 SDK로 결제 요청을 보내고, `successUrl`/`failUrl` 페이지를 만든다.
   - 서버: `successUrl`에서 받은 `paymentKey`, `orderId`, `amount`를 **서버에 저장된 주문 금액과 대조한 뒤에만** 승인 API(`POST /v1/payments/confirm`)를 호출한다.
   - 시크릿 키는 서버에서만 쓴다. Basic Auth에는 `secretKey:`를 base64로 인코딩해 넣는다.
   - 웹훅: 결제 상태 변경을 처리하고, 같은 이벤트가 두 번 와도 결과가 같도록 `paymentKey` 기준으로 멱등하게 만든다.
   - 환불: 토스 결제 취소 API로 연결한다.
3. **DB 스키마**
   - `schema.prisma`에 필요한 필드와 테이블(예: `provider`, `paymentKey`, `method`, `status`, `approvedAt`)을 추가한다.
   - `prisma migrate dev --create-only`로 **마이그레이션 파일만 생성**한다.
   - 추가만 하는(additive) 변경으로 제한한다. 기존 컬럼은 삭제하거나 이름을 바꾸지 않는다. 기존 Stripe 데이터는 그대로 남긴다.
4. **환경변수**
   - `.env.example`에 `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`, `TOSS_WEBHOOK_SECRET`(해당하는 경우), `PAYMENT_PROVIDER`를 추가한다. 실제 키는 커밋하지 않는다.
5. **최소 테스트** (생략하지 않는다)
   - 승인 성공, 승인 실패(토스 에러 응답), 금액 불일치 거부, 웹훅 중복 수신 시 멱등 처리. 이렇게 4개.
   - 토스 API는 목(mock)으로 대체한다. 테스트 키로 스모크 테스트하는 방법은 PR 설명에 적는다.

## 범위 밖 (하지 말 것)
- 운영 DB 접속, `prisma migrate deploy` 실행, 운영 데이터 수정
- main에 머지, 프로덕션 배포, Vercel 프로덕션 환경변수 변경
- Stripe 코드와 Stripe 관련 컬럼 삭제 (이벤트가 끝나고 별도 PR로 진행)
- 결제와 관계없는 리팩터링

## 완료 기준
- [ ] `feat/toss-payments` 브랜치에 PR이 올라가 있다
- [ ] `PAYMENT_PROVIDER=toss`와 토스 테스트 키로 Vercel Preview에서 결제 → 승인 → 주문 완료 흐름이 동작한다
- [ ] `PAYMENT_PROVIDER=stripe`로 바꾸면 기존 흐름이 그대로 동작한다
- [ ] 위 테스트 4개가 통과하고, lint와 typecheck, build가 통과한다
- [ ] 마이그레이션 SQL이 PR에 포함되어 있고, 추가만 하는 변경이다
- [ ] PR 설명에 다음이 들어 있다: Stripe 호출 지점 목록, 변경 요약, 마이그레이션 SQL, 배포 절차, 롤백 절차

## 가정 (틀리면 알려주세요)
- 토스페이먼츠 가맹점 계약이 끝났고, 테스트 키와 라이브 키를 받을 수 있다.
- 정기결제(빌링)는 없고 일회성 결제만 있다. 구독이 있다면 범위가 크게 늘어난다.
- 결제 통화는 KRW 하나다.
- 진행 중인 Stripe 결제나 환불 건은 Stripe 쪽에서 마무리한다.

## 리스크
| 리스크 | 대응 |
|---|---|
| 클라이언트에서 금액을 조작함 | 서버에서 주문 금액을 대조한 뒤에만 승인 |
| 웹훅 중복·순서 역전으로 상태가 꼬임 | `paymentKey` 기준 멱등 처리, 상태 전이 검증 |
| 운영 마이그레이션 실패 | 추가만 하는 변경, 실행 전 백업, 사람이 직접 실행 |
| 이벤트 당일 장애 | 환경변수 하나로 Stripe에 즉시 롤백 |
| 라이브 키로 전환할 때 설정 누락 | 배포 체크리스트를 PR에 포함 |

## 다음 단계와 담당
1. **Codex (월~수)**: 위 범위를 구현하고 PR을 올린다.
2. **사람 (수~목)**: PR을 리뷰하고, Preview에서 테스트 키로 실제 결제를 해본다.
3. **사람 (목)**: 운영 DB를 백업하고 `prisma migrate deploy`를 실행한 뒤, Vercel 프로덕션에 토스 라이브 키를 넣고 머지·배포한다. 그다음 소액으로 실결제한 뒤 바로 환불해 본다.
4. **금요일 이벤트**: 토스로 운영하고, 문제가 생기면 `PAYMENT_PROVIDER=stripe`로 롤백한다.

목요일에 배포하는 이유는 문제가 생겼을 때 이벤트 전에 하루 여유를 두기 위해서입니다.
