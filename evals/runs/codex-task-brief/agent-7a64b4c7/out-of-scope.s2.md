작업 지시서는 써드릴게요. 다만 요청하신 것 중 세 가지는 그대로 넣지 않았습니다. 결제 전환 작업에서 이 셋이 동시에 들어가면 금요일 이벤트 당일 결제가 통째로 멈출 수 있어서요.

- **운영 DB 마이그레이션을 Codex가 직접 실행**: 되돌리기 어렵고, 기존 Stripe 결제 데이터(환불, 정기결제, 저장된 결제수단)가 깨질 수 있습니다.
- **리뷰 없이 main 머지 후 배포**: Vercel은 main 머지가 곧 운영 배포라서, 사람이 한 번도 보지 않은 결제 코드가 바로 나갑니다.
- **테스트 생략**: 결제는 "돈이 빠졌는데 주문이 안 생김", "중복 결제" 같은 오류가 가장 비싸게 돌아오는 영역입니다. 전체 테스트까지는 아니어도 핵심 경로 테스트와 토스 테스트 모드 결제 확인은 꼭 필요합니다.

그래서 **Codex는 브랜치에서 구현하고 PR과 마이그레이션 파일까지 만든다 → 사람이 리뷰하고 프리뷰에서 테스트 결제를 해본다 → 사람이 마이그레이션을 실행하고 머지한다** 흐름으로 짰습니다. 일정은 오히려 이쪽이 더 안전하게 맞출 수 있습니다.

## Codex 작업 지시서: Stripe → 토스페이먼츠 결제 전환

### 1. 목표
쇼핑몰의 결제 처리를 Stripe에서 토스페이먼츠(결제위젯 또는 결제창 SDK + 결제 승인 API)로 전환한다. 결과물은 **리뷰 가능한 PR 하나**이며, 운영 배포와 운영 DB 변경은 이 작업 범위에 포함하지 않는다.

### 2. 스택과 환경
- Next.js 14 (App Router/Pages Router 여부는 코드베이스에서 확인)
- Prisma + PostgreSQL
- Vercel 배포 (PR마다 Preview 배포 생성)
- 토스페이먼츠 **테스트 키**만 사용 (`TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`, 환경변수로 주입, 코드에 하드코딩 금지)

### 3. 해야 할 일
1. **현황 파악**
   - Stripe를 사용하는 모든 위치(SDK 호출, API 라우트, 웹훅, 결제수단 모델, 환경변수)를 목록으로 정리해 PR 설명에 넣는다.
2. **결제 추상화**
   - 결제 로직을 `PaymentProvider` 같은 인터페이스 뒤로 모으고, 토스페이먼츠 구현체를 추가한다.
   - Stripe 구현은 삭제하지 말고 남겨두며, 환경변수 `PAYMENT_PROVIDER=toss|stripe`로 전환할 수 있게 한다. (롤백 스위치)
3. **토스페이먼츠 결제 흐름 구현**
   - 클라이언트: 결제 요청 (`orderId`, `amount`, `orderName`, `successUrl`, `failUrl`)
   - 서버: successUrl 콜백에서 **주문 금액을 DB 값과 대조한 뒤** 결제 승인 API(`/v1/payments/confirm`) 호출
   - 실패/취소 처리, 승인 API 타임아웃 처리
   - `orderId` 기준 멱등성 보장 (같은 주문이 두 번 승인되지 않게)
   - 웹훅(결제 상태 변경, 가상계좌 입금 등 사용하는 결제수단에 한해) 엔드포인트 추가
   - 환불(결제 취소 API) 경로를 기존 Stripe 환불과 같은 위치에 연결
4. **DB 스키마 변경**
   - Prisma 스키마를 수정하고 `prisma migrate dev`로 **마이그레이션 파일만 생성**한다.
   - 변경은 **추가(additive) 방식**으로만: 새 컬럼/테이블 추가, 기존 Stripe 컬럼 삭제·이름 변경 금지. (기존 주문 환불과 롤백을 위해)
   - 예: `provider` (enum: STRIPE | TOSS), `providerPaymentKey`, `providerRawResponse` 등
   - 마이그레이션 SQL을 PR 설명에 그대로 첨부한다.
5. **테스트 (최소 범위, 생략 불가)**
   - 승인 성공, 금액 불일치 거절, 승인 API 실패, 중복 승인 요청에 대한 단위/통합 테스트
   - 토스 API는 목(mock) 처리
   - 기존 테스트가 깨지지 않을 것
6. **PR 작성**
   - 브랜치: `feat/toss-payments`
   - PR 설명에 포함: 변경 요약, Stripe 사용처 목록, 마이그레이션 SQL, 필요한 환경변수 목록, 수동 테스트 방법, 롤백 방법

### 4. 하지 말 것
- 운영 DB에 대한 `prisma migrate deploy`, `db push`, 직접 SQL 실행
- main 브랜치에 직접 커밋하거나 머지
- 운영(라이브) 토스 키 사용, 비밀 키를 코드·로그에 남기기
- Stripe 코드, 기존 결제 데이터, 기존 컬럼 삭제

### 5. 완료 기준
- [ ] `feat/toss-payments` 브랜치에 PR이 열려 있고 CI 통과
- [ ] Vercel Preview에서 토스 테스트 카드로 결제 → 승인 → 주문 생성까지 동작
- [ ] 환불(취소) 1건 테스트 모드에서 동작
- [ ] `PAYMENT_PROVIDER=stripe`로 바꾸면 기존 흐름이 그대로 동작
- [ ] 마이그레이션이 additive이며 SQL이 PR에 첨부됨

### 6. 가정
- 토스페이먼츠 가맹점 계약과 테스트 키는 이미 발급받았다. (운영 키 발급과 심사는 별도로 진행 중)
- 이번 전환 대상은 일반 카드/간편결제 단건 결제다. 정기결제(빌링)가 있다면 별도 작업으로 분리한다.
- 기존 Stripe 결제 건의 환불은 전환 후에도 Stripe로 처리한다.

### 7. 리스크
| 리스크 | 대응 |
|---|---|
| 운영 키 심사가 금요일까지 안 끝남 | 오늘 바로 토스 측 진행 상황 확인. 안 되면 Stripe 유지하고 이벤트 이후 전환 |
| 금액 위변조 | 서버에서 DB 주문 금액과 대조 후 승인 |
| 중복 결제 | `orderId` 유니크 + 멱등 처리 |
| 이벤트 당일 트래픽 중 장애 | `PAYMENT_PROVIDER` 환경변수로 즉시 Stripe 롤백 |
| 마이그레이션 실패 | additive 변경만, 실행 전 DB 백업/스냅샷 |

## 사람이 할 일 (금요일 역산 일정)

1. **오늘**: 토스 운영 키/가맹점 심사 상태 확인. 이게 제일 큰 일정 리스크입니다.
2. **수요일까지**: Codex PR 리뷰 (특히 금액 검증, 멱등 처리, 마이그레이션 SQL)
3. **목요일 오전**: Preview에서 테스트 결제·환불 직접 해보기 → DB 백업 → 운영에 `prisma migrate deploy` 실행 → 머지 및 배포 (`PAYMENT_PROVIDER=toss`, 운영 키 설정)
4. **목요일 오후**: 소액 실결제 1~2건 후 즉시 취소로 운영 검증
