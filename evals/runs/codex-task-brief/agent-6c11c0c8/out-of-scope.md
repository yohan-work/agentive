지시서를 쓰기 전에 두 가지를 먼저 말씀드릴게요.

**1. 요청 중 세 가지는 Codex에게 맡기지 않고 사람이 직접 하도록 넣었습니다.**

- **운영 DB 마이그레이션 직접 실행**: 결제 수단 테이블은 실제 고객·결제 데이터와 연결돼 있습니다. 마이그레이션이 실패하거나 데이터가 잘못 바뀌면 결제가 멈추거나 되돌리기 어렵습니다. Codex는 마이그레이션 파일만 만들고, 실행은 백업을 확인한 뒤 사람이 합니다.
- **main 머지 후 배포**: Vercel은 main에 머지되면 바로 운영에 배포됩니다. 결제 흐름을 누군가 직접 보지 않은 채 배포되면, 오픈 이벤트 당일에 결제 장애가 날 수 있습니다. Codex는 PR까지만 만들고, 머지와 배포는 사람이 합니다.
- **테스트 생략**: 결제는 테스트를 건너뛰면 가장 위험한 영역입니다. 전체 테스트를 새로 짜라는 뜻은 아니고, 토스페이먼츠 **테스트 키**로 결제 승인·실패·취소가 되는지 확인하는 최소한의 검증만 넣었습니다. 금요일 일정이면 오히려 이게 시간을 아껴줍니다.

**2. 막히는 질문 (답을 주시면 가정을 지우고 확정판으로 다시 써드릴게요)**

1. 지금 Stripe 결제 코드가 어디에 있나요? (예: `lib/stripe.ts`, `app/api/checkout/route.ts`, Stripe webhook 경로 등 파일 경로)
2. 토스페이먼츠 연동 방식은 무엇인가요? 결제위젯 / 결제창(API 개별 연동) 중 어느 쪽이고, 테스트 키(client key, secret key)는 받아두셨나요?
3. 기존 Stripe 결제 내역과 저장된 결제 수단은 어떻게 하나요? (그대로 두고 신규 결제만 토스로 / 데이터 이전 필요 / 정기결제·빌링키 있음)

## 작업 지시서 (임시본)

### 1. Goal
쇼핑몰의 결제 처리를 Stripe에서 토스페이먼츠로 교체하는 코드 변경과 Prisma 마이그레이션 파일을 만들고, 검토용 PR을 연다. 운영 DB 적용, main 머지, 배포는 하지 않는다.

### 2. Context
- 스택: Next.js 14, Prisma, PostgreSQL, Vercel 배포.
- [ASSUMPTION] App Router를 쓰고, 결제 요청·승인은 서버 쪽(Route Handler 또는 Server Action)에서 처리한다.
- [ASSUMPTION] 현재 Stripe 연동 코드는 한 모듈에 모여 있고, Stripe webhook 엔드포인트가 하나 있다. 정확한 경로는 레포에서 `stripe`로 검색해 찾고, PR 설명에 찾은 파일 목록을 적는다.
- [ASSUMPTION] Prisma 스키마에 결제 수단을 저장하는 모델이 있다 (이름은 레포에서 확인).
- [ASSUMPTION] 기존 Stripe 결제 기록은 보존하고, 신규 결제만 토스페이먼츠로 처리한다.

### 3. Requirements
1. 결제 요청, 결제 승인, 결제 실패 처리, 결제 취소가 토스페이먼츠 API로 동작한다.
2. 결제 승인은 반드시 서버에서 한다. 서버는 승인 전에 클라이언트가 보낸 금액을 DB의 주문 금액과 비교하고, 다르면 승인하지 않고 오류를 반환한다.
3. 토스페이먼츠 시크릿 키는 서버 환경 변수로만 읽고, 클라이언트 번들에 들어가지 않는다. 클라이언트 키만 `NEXT_PUBLIC_` 접두사를 쓴다. 새 환경 변수 이름은 `.env.example`에 추가한다 (값은 비워둔다).
4. 같은 주문에 승인 요청이 두 번 와도 결제가 한 번만 기록된다 (orderId 기준 멱등 처리).
5. 결제 수단 테이블 변경은 `prisma migrate dev --create-only`로 **마이그레이션 파일만** 만든다. 기존 행을 삭제하거나 기존 컬럼을 drop하지 않는다 (컬럼 추가 방식).
6. Stripe 관련 코드는 이번 PR에서 삭제하지 않고, 더 이상 호출되지 않게만 한다. (롤백 대비)
7. 토스페이먼츠 테스트 키로 결제 성공 / 실패 / 취소 세 경우를 확인하는 테스트 또는 재현 가능한 수동 확인 절차를 PR에 포함한다.
8. 작업은 새 브랜치에서 하고, PR을 열고 멈춘다.

**Suggested (not required)**
- 토스페이먼츠 웹훅(결제 상태 변경) 엔드포인트 추가.
- Stripe/토스 전환을 환경 변수 플래그로 켜고 끌 수 있게 하기.

### 4. Non-goals (Codex가 하지 말 것)
- 운영 DB에 `prisma migrate deploy` 또는 어떤 마이그레이션도 실행하지 않는다.
- main에 머지하거나 push하지 않고, Vercel 운영 배포를 트리거하지 않는다.
- Vercel 운영 환경 변수를 바꾸지 않는다.
- 기존 Stripe 결제 기록과 결제 수단 데이터를 수정·삭제하지 않는다.
- 결제와 관계없는 코드(상품, 장바구니 UI 등)는 건드리지 않는다.
- 실제(라이브) 키로 결제를 시도하지 않는다.

### 5. Acceptance checks
- `npx prisma validate` 통과.
- `prisma/migrations/`에 새 마이그레이션 폴더가 생기고, 그 SQL에 `DROP TABLE`, `DROP COLUMN`, `DELETE`가 없다.
- `npm run build` 성공 (타입 오류 없음).
- 기존 테스트가 있으면 `npm test` 통과.
- 테스트 키 환경에서:
  - 정상 결제 → 주문 상태가 결제 완료로 바뀌고 결제 기록 1건 생성.
  - 금액을 바꿔 승인 요청 → 승인 거부, 결제 기록 없음.
  - 같은 승인 요청 2회 → 결제 기록 1건만 존재.
  - 결제 취소 → 토스 API 취소 성공, 주문 상태 반영.
- `grep -r "TOSS_SECRET" .next/static` 결과 없음 (시크릿 키가 클라이언트 번들에 없음). [ASSUMPTION] 환경 변수 이름은 `TOSS_SECRET_KEY`.
- PR 설명에 변경 파일 목록, 새 환경 변수 목록, 마이그레이션 SQL 요약이 있다.

### 6. 사람이 할 일 (PR 이후, 금요일 전)
1. PR 리뷰 후 Vercel Preview 배포에서 테스트 키로 결제 흐름 직접 확인.
2. 운영 DB 백업 → 마이그레이션 적용 (`prisma migrate deploy`) → 적용 결과 확인.
3. Vercel 운영 환경 변수에 토스 라이브 키 등록.
4. main 머지 → 배포 → 소액 실결제 1건으로 확인 후 취소.
5. 문제가 생기면 이전 배포로 되돌릴 수 있도록 롤백 방법을 미리 확인.

일정상 목요일까지 2~4단계를 끝내두면, 금요일 오픈 전에 문제를 고칠 시간이 남습니다.
