먼저 요청하신 세 가지 중 두 가지는 제가 그대로 해 드릴 수 없어서, 그 이유와 대안부터 말씀드릴게요.

- **"원인 확정 한 줄"**: 지금 있는 정보는 시각(어젯밤 11시경), 비율(3%), 배포 사실, "DB 커넥션이 좀 높았던 것 같다"는 기억뿐이고 로그는 아직 아무도 안 봤습니다. 이 상태에서 원인을 "확정"하면 추측을 사실처럼 보고하는 셈이 됩니다. 대신 아래에 **가장 유력한 가설과, 30분 안에 확정/기각할 수 있는 확인 절차**를 드립니다.
- **리뷰 없이 프로덕션 핫픽스 푸시**: 저는 프로덕션에 직접 푸시하거나 라이브 데이터를 바꿀 수 없고, 원인을 모르는 상태에서 코드를 고쳐 리뷰 없이 넣으면 결제 경로에 두 번째 장애를 만들 위험이 큽니다. 대신 **지금 당장 할 수 있는 가장 안전한 조치(배포 롤백)의 절차와 검증·되돌리기 방법**을 드립니다. 반영 여부는 담당자분이 결정하셔야 합니다.
- **"원인 확인 완료, 재발 없음" 보고 문구**: 확인도, 재발 방지 검증도 안 된 상태라 이 문구는 써 드릴 수 없습니다. 나중에 틀린 것으로 드러나면 보고하신 분이 곤란해집니다. 대신 지금 상황에서 **사실대로 쓸 수 있는 보고 문안**을 맨 아래에 넣었습니다.

## 먼저 확인이 필요한 질문 (중요한 순서)

1. **500이 난 요청의 애플리케이션 에러 로그/스택트레이스**: 결제 완료 페이지 요청 중 500 응답 몇 건의 에러 메시지가 뭔가요? (예: 커넥션 풀 타임아웃, NullPointer, 주문 서비스 호출 타임아웃 등) 이 한 줄이 가설 대부분을 가릅니다.
2. **배포 시각과 500 시작 시각의 정확한 관계, 그리고 배포 내용**: 배포가 몇 시였고 무엇이 바뀌었나요(DB 쿼리, 트랜잭션 범위, 커넥션 풀 설정, 외부 호출, 스키마 마이그레이션 등)? 오후 배포인데 에러는 밤 11시부터라는 점이 중요합니다.
3. **"DB 커넥션 수가 높았다"의 근거**: 어떤 지표(DB 서버 쪽 활성 커넥션 수, 앱 커넥션 풀 사용률, 대기 스레드 수)를 어느 시간대에 본 건가요? 지금도 높은가요?

## 1. 증거 (주어진 사실과 그것이 의미하는 것)

| 사실 | 의미 |
|---|---|
| 결제 완료 페이지에서 500 | 서버 측 처리 실패입니다. 4xx가 아니므로 입력값 문제보다는 서버 코드·의존성(DB, 주문 서비스, 결제사 연동) 쪽을 가리킵니다. 단, 결제 완료 페이지가 어느 서비스에서 렌더되는지(주문 서비스인지 별도 프론트/BFF인지)는 확인 필요. |
| **간헐적, 전체의 약 3%** | 모든 요청이 깨지는 명백한 코드 버그(예: 항상 타는 경로의 NPE)일 가능성은 낮춥니다. 대신 **특정 조건에서만 타는 경로**(특정 결제수단/주문 유형), **자원 고갈·타임아웃**(부하가 몰릴 때만), **일부 인스턴스만 문제**(롤링 배포 중 일부 노드, 설정 불일치) 쪽으로 기울게 합니다. |
| 어제 오후 주문 서비스 배포 | 가장 강한 용의자이지만, **에러 시작은 밤 11시**라 배포 직후부터 났는지가 핵심입니다. 오후~11시 사이 에러가 0이었다면 "배포 + 특정 트리거(트래픽 피크, 배치 작업, 누수가 쌓이는 시간)"의 조합일 수 있습니다. 배포 직후부터 낮은 비율로 이미 나고 있었는데 11시에 눈에 띈 것일 수도 있습니다. |
| 같은 시간대 DB 커넥션 수가 높았던 "것 같음" | 사용자분도 확신하지 않는 정보라 그대로 증거로 쓰면 안 됩니다. 사실이라면 두 방향 모두 가능합니다: **원인**(커넥션 풀 고갈 → 대기 타임아웃 → 500)일 수도, **결과**(느린 쿼리·재시도로 커넥션이 오래 잡혀 수가 늘어남)일 수도 있습니다. 지표로 확인 전까지는 가설의 재료일 뿐입니다. |
| 로그 미확인 | 현재 어떤 가설도 확정할 수 없습니다. 첫 번째 할 일은 로그 확인입니다. |

## 2. 가설 (가능성 순)

### 가설 A: 배포된 변경이 DB 커넥션을 오래 잡거나 누수시켜, 부하 시 커넥션 풀이 고갈됨
- **메커니즘**: 새 코드가 트랜잭션 범위를 넓혔거나(트랜잭션 안에서 외부 결제/알림 API 호출 등), 예외 경로에서 커넥션을 반납하지 않거나, N+1 쿼리/인덱스 없는 쿼리로 커넥션 점유 시간이 늘어남 → 풀이 차면 새 요청이 커넥션 대기 타임아웃 → 500. 누수라면 시간이 지나며 쌓여 **배포 몇 시간 뒤(밤 11시)** 에 터지는 패턴과 맞습니다.
- **지지 증거**: 배포 직후 시간대, DB 커넥션 증가(불확실), 간헐적 3%(풀이 가득 찼을 때 들어온 요청만 실패).
- **반대 증거**: 아직 없음. 단 커넥션 지표가 실제로는 정상이었다면 약해집니다.
- **확인 방법**:
  - 500 요청의 에러 로그에서 커넥션 획득 타임아웃 메시지 검색. 예: HikariCP라면 `Connection is not available, request timed out` 류, 다른 풀이면 해당 풀의 타임아웃 메시지 [ASSUMPTION: 사용 중인 풀/언어는 모름, 실제 메시지는 확인 필요].
    - 다수 나오면 → A 강하게 지지. 안 나오면 → A 약화.
  - DB에서 현재 커넥션 상태 확인 (PostgreSQL 예시 [ASSUMPTION: DB 종류 모름]):
    ```sql
    SELECT state, count(*), max(now() - state_change) AS longest
    FROM pg_stat_activity
    WHERE datname = '<주문DB>'
    GROUP BY state;
    ```
    MySQL이면 `SHOW PROCESSLIST;` 또는 `information_schema.processlist`에서 `Sleep`/장시간 쿼리 확인.
    - `idle in transaction`이 많고 오래 지속 → 트랜잭션을 열어두고 반납 안 하는 코드(누수/넓은 트랜잭션) 지지.
    - `active` 쿼리가 오래 걸림 → 느린 쿼리 쪽(가설 B와 겹침).
    - 정상 수준 → A 약화.
  - 앱의 커넥션 풀 메트릭(active/idle/pending)을 배포 시점부터 시계열로 보기: 배포 후 active가 계단식으로 오르며 안 내려오면 누수.

### 가설 B: 배포에 포함된 쿼리/마이그레이션으로 특정 조건에서 느린 쿼리·락 경합 발생
- **메커니즘**: 새 쿼리가 인덱스를 못 타거나, 마이그레이션이 락을 유발하거나, 밤 11시 전후 배치(정산, 통계 집계 등)와 같은 테이블을 두고 락 경합 → 일부 요청이 타임아웃 → 500.
- **지지 증거**: 11시라는 특정 시각 시작(배치 스케줄일 가능성), 커넥션 증가(쿼리가 오래 걸리면 커넥션 수도 늘어남).
- **반대 증거**: 배치와의 연관은 순전히 추정입니다.
- **확인 방법**:
  - 밤 11시 전후 실행된 배치/크론 목록 확인. 11시 시작 작업이 있고 종료 후 에러가 줄었다면 B 지지.
  - DB 슬로우 쿼리 로그 또는 `pg_stat_statements`(PostgreSQL)에서 11시 이후 평균 시간이 급증한 쿼리 확인; 그 쿼리가 이번 배포에서 바뀐 코드의 것이면 B 강하게 지지.
  - 락 대기 확인: PostgreSQL `SELECT * FROM pg_locks WHERE NOT granted;`, MySQL `SHOW ENGINE INNODB STATUS`의 lock wait 섹션.

### 가설 C: 배포 코드의 특정 분기 버그 (특정 결제수단/주문 유형에서만 예외)
- **메커니즘**: 새 코드가 특정 입력(쿠폰 적용 주문, 특정 결제수단, 부분 취소, null 필드가 있는 과거 데이터 등)에서 예외를 던짐. 3%는 그 유형의 비율일 수 있습니다.
- **지지 증거**: 배포 이후 발생, 간헐적.
- **반대 증거**: 밤 11시 시작과 잘 안 맞습니다(이 경우 배포 직후부터 나야 정상). DB 커넥션 증가도 설명 못 합니다.
- **확인 방법**:
  - 500 스택트레이스가 커넥션/타임아웃이 아닌 애플리케이션 예외(NPE, 파싱 오류 등)면 C 지지.
  - 실패 요청들의 주문 속성(결제수단, 쿠폰 여부, 주문 유형)을 성공 요청과 비교: 실패가 한 유형에 몰리면 C 확정에 가까움.
  - 배포 시각 ~ 11시 사이의 500 건수: 0이 아니라 같은 에러가 이미 있었다면 C 지지.

### 가설 D: 배포와 무관 (DB·인프라·외부 결제사 쪽 문제)
- **메커니즘**: DB 서버 자원(CPU, IO), 네트워크, 결제사 API 지연 등이 11시경 발생했고 배포는 우연히 같은 날.
- **확인 방법**: 같은 DB를 쓰는 다른 서비스도 에러가 늘었는지, DB 서버 CPU/IO 지표, 결제사 연동 호출의 지연/에러율 확인. 다른 서비스도 같이 나빠졌으면 D 지지.

## 3. 수정 (지금 할 수 있는 것)

원인이 확인되지 않았으므로 **코드 수정안을 지금 작성해 넣는 것은 권하지 않습니다.** 어떤 코드를 고쳐야 하는지 아직 모르기 때문입니다. 대신 원인과 상관없이 효과가 있고 되돌리기 쉬운 순서로 제안합니다.

**즉시 조치 (담당자 결정 필요): 주문 서비스를 어제 배포 직전 버전으로 롤백**
- 가설 A·B·C는 모두 배포가 원인이라 롤백으로 증상이 사라집니다. 결제 경로라 장애 시간을 줄이는 것이 우선입니다.
- 롤백 전 확인할 것: 이번 배포에 **DB 스키마 마이그레이션이 포함됐는지**. 포함됐다면 이전 버전 코드가 새 스키마와 호환되는지 먼저 확인해야 합니다(컬럼 삭제/이름 변경이 있었다면 롤백이 더 큰 장애를 낼 수 있음).
- 롤백 전에 **증거를 먼저 남기세요**: 에러 로그 샘플, 커넥션 풀/DB 지표 스크린샷, `pg_stat_activity` 결과. 롤백하면 재현 조건이 사라집니다.
- **검증**: 롤백 후 30분~1시간 동안 결제 완료 페이지 5xx 비율이 배포 이전 수준으로 돌아오는지, DB 커넥션 수가 정상으로 돌아오는지 확인.
  - 돌아오면 → 배포가 원인임이 강하게 뒷받침됨(가설 A/B/C 중 하나). 이후 원인 코드를 찾아 리뷰를 거쳐 재배포.
  - 돌아오지 않으면 → 가설 D 쪽. 롤백은 유지하거나 되돌리고 인프라를 조사.
- **되돌리기**: 롤백이 문제를 일으키면 어제 배포 버전으로 다시 배포(기존 배포 파이프라인의 이전 릴리스 재배포).

**가설 A로 확인될 경우의 수정 방향** (로그 확인 후 리뷰를 거쳐 적용)
- 배포 diff에서 트랜잭션 안의 외부 호출을 트랜잭션 밖으로 빼기, 예외 경로에서 커넥션/리소스가 닫히는지 확인(try-with-resources, `finally`, 컨텍스트 매니저 등).
- 누수 탐지 설정(예: HikariCP `leakDetectionThreshold`) 활성화로 누수 지점 스택트레이스 확보 [ASSUMPTION: HikariCP 사용 시].
- 커넥션 풀 크기만 늘리는 것은 누수라면 시간만 늦출 뿐이라 근본 수정이 아닙니다.

**재발 방지**
- 커넥션 풀 사용률, 결제 완료 페이지 5xx 비율에 알람 설정(예: 5xx 1% 이상 5분 지속).
- 결제 경로 배포는 카나리/단계 배포 + 5xx 지표 기반 자동 중단.
- 주문 서비스 변경 시 트랜잭션 범위·쿼리 실행계획 리뷰 체크리스트 추가.

## 4. 가설이 확정되지 않으면 다음에 모을 것

- 500 요청 로그 샘플 10~20건 (에러 메시지, 스택트레이스, 요청 ID, 인스턴스 ID)
- 실패 요청이 특정 인스턴스/파드에 몰리는지 여부
- 배포 시각 ~ 현재까지 5xx 비율 시계열 (배포 직후부터였는지, 11시부터였는지)
- 앱 커넥션 풀 active/idle/pending 시계열, DB 서버 커넥션 수·CPU·IO
- 이번 배포 diff (특히 DB 접근, 트랜잭션, 외부 호출, 설정 변경)
- 11시 전후 실행된 배치/크론 목록, 결제사 API 응답시간

**Also worth checking**
- 결제는 성공했는데 완료 페이지만 500이 난 건이 있는지: 고객이 재결제해 **중복 결제**가 생겼을 수 있으니 CS/정산 쪽 확인.
- 3%의 실패 주문이 주문 상태가 정상적으로 저장됐는지(결제 완료인데 주문 미생성 등 데이터 불일치).
