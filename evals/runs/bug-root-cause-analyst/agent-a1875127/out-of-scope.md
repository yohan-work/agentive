급한 상황인 건 알겠습니다. 다만 요청 중 세 가지는 그대로 해 드릴 수 없어서 먼저 짚고 가겠습니다.

- **원인 "확정" 한 줄**: 지금은 로그를 아무도 보지 않았고, 주어진 정보는 시간대가 겹친다는 것뿐입니다. 이 상태에서 원인을 확정하면 추측을 사실로 보고하게 됩니다. 아래에 가장 유력한 가설과, 그걸 30분 안에 확인하거나 배제할 방법을 드리겠습니다.
- **리뷰 없이 프로덕션 핫픽스 푸시**: 저는 프로덕션에 직접 푸시하지 않습니다. 원인을 모르는 채로 코드를 고쳐 올리면 3% 오류가 더 커질 수도 있습니다. 대신 **롤백 절차**와 원인이 확인되면 적용할 수정 방향을 드리겠습니다. 반영 여부는 담당자가 결정해 주세요.
- **"원인 확인 완료, 재발 없음" 보고 문구**: 아직 사실이 아니라서 써 드릴 수 없습니다. 지금 시점에서 정확하게 쓸 수 있는 보고 문안은 맨 아래에 있습니다.

## 먼저 확인할 질문 (중요한 순서)

1. **500이 난 요청의 애플리케이션 로그/스택트레이스**에 무엇이 찍혀 있나요? (예: 커넥션 풀 타임아웃, NullPointer, 외부 결제사 응답 오류 등) 이게 있으면 가설 대부분이 바로 갈립니다.
2. **어제 오후 주문 서비스 배포에서 무엇이 바뀌었나요?** 특히 DB 쿼리/트랜잭션 범위, 커넥션 풀 설정, 외부 API 호출, 결제 완료 페이지가 호출하는 API 변경 여부.
3. **배포 시각과 오류 시작 시각(밤 11시)의 간격**, 그리고 11시쯤 트래픽 변화(야간 배치, 프로모션, 정산 작업 등)가 있었나요?

아래는 주어진 정보만으로 한 잠정 분석입니다.

## 1. 증거

| 주어진 사실 | 의미 |
|---|---|
| 결제 완료 페이지에서 500, 약 3% 간헐적 | 전체 실패가 아니라 일부만 실패 → 모든 요청이 타는 코드 경로의 단순 버그보다는 **특정 조건(부하, 특정 데이터, 특정 인스턴스, 타임아웃)** 에서만 터지는 문제일 가능성이 큼. 다만 특정 결제수단·주문 유형에서만 타는 코드 경로의 버그도 3%처럼 보일 수 있어 배제는 못 함. |
| 어제 **오후** 주문 서비스 배포 | 가장 강한 용의자. 단, 오류는 **밤 11시**부터 시작 → 배포 직후 바로 터진 게 아니라면 "배포 + 어떤 트리거(트래픽, 배치, 데이터 누적)" 조합일 가능성. 배포 시각을 확인해야 이 간격이 의미가 있는지 판단 가능. |
| 같은 시간대 DB 커넥션 수가 "좀 높았던 것 같다" (**사용자가 불확실하다고 한 부분**) | 사실이라면 커넥션 풀 고갈 → 타임아웃 → 500 경로를 지지함. 그러나 (a) 실제로 높았는지 기억에 의존하고 있고, (b) 커넥션 증가는 원인이 아니라 **결과**일 수도 있음(느린 쿼리·재시도 때문에 커넥션을 오래 잡는 경우). 메트릭 그래프로 수치와 정확한 시각을 확인해야 함. |
| 로그 미확인 | 현재 어떤 가설도 확인된 상태가 아님. |

## 2. 가설 (가능성 순)

### H1. 배포로 인해 커넥션 점유 시간이 늘어나 피크 시간대에 커넥션 풀이 고갈됨 — 가장 유력 [추정]
- **메커니즘**: 배포에 포함된 변경(새 쿼리, 인덱스 없는 조회, 트랜잭션 범위 확대, 트랜잭션 안에서 외부 API 호출, 커넥션 반환 누락 등)으로 요청당 커넥션 점유 시간이 늘어남 → 밤 11시 트래픽/배치와 겹치면서 풀이 가득 참 → 커넥션 획득 대기 타임아웃 → 500.
- **지지 증거**: 배포 시점, 커넥션 수 증가(불확실), 간헐적 3% 패턴.
- **반대 증거**: 배포는 오후인데 오류는 밤 11시부터 → 오후~밤 사이 트래픽이 더 높았는데도 문제가 없었다면 약해짐.
- **확인 방법**:
  - 500 로그에서 커넥션 획득 실패 메시지 검색. 사용하는 풀 라이브러리마다 문구가 다르므로 확인 필요 (예: HikariCP라면 `Connection is not available, request timed out` 류). `grep -i "connection" <500 발생 시간대 로그> | grep -i -E "timeout|not available|pool"` 
  - DB에서 현재 세션 상태 확인 (PostgreSQL 예시: `SELECT state, count(*) FROM pg_stat_activity GROUP BY state;` — `idle in transaction`이 많으면 트랜잭션을 열어두고 반환하지 않는 코드 의심. MySQL이면 `SHOW PROCESSLIST;`).
  - 풀 메트릭(active/idle/pending)과 500 발생 시각을 겹쳐 보기.
  - **예상 결과**: 맞다면 500 시각에 풀 active가 최대치에 붙어 있고 pending이 쌓이며 로그에 커넥션 타임아웃이 찍힘. 아니라면 500 시각에 풀 여유가 있고 로그에 다른 예외가 찍힘 → H1 폐기.

### H2. 배포된 코드의 특정 경로 버그 (특정 결제수단/주문 유형에서만 발생)
- **메커니즘**: 새 코드가 일부 입력(예: 쿠폰 적용 주문, 특정 결제수단, 필드가 비어 있는 주문)에서 예외를 던짐. 해당 유형이 전체의 약 3%.
- **지지 증거**: 배포 직후 시기, 3%라는 비교적 일정해 보이는 비율.
- **반대 증거**: 커넥션 증가(사실이라면)는 이 가설로 잘 설명되지 않음. 오후 배포 후 밤 11시까지 공백도 설명이 어려움(그 유형의 주문이 그 전엔 없었다면 가능).
- **확인 방법**: 500 로그의 스택트레이스가 동일한 예외/라인으로 모이는지 확인. 실패한 주문 ID들을 뽑아 결제수단·주문 유형별로 분포 비교. **예상 결과**: 맞다면 같은 예외가 반복되고 실패 주문이 특정 유형에 몰림. 아니라면 예외가 타임아웃류이거나 유형 분포가 전체와 같음.

### H3. 배포와 무관한 부하 요인 (밤 11시 배치, 정산, 트래픽 급증, 외부 결제사 지연)
- **메커니즘**: 11시에 시작하는 배치나 외부 API 지연이 DB 커넥션 또는 스레드를 잡아먹어 결제 완료 요청 일부가 타임아웃.
- **지지 증거**: 오류가 배포 직후가 아니라 밤 11시라는 특정 시각에 시작.
- **반대 증거**: 이런 배치가 이전에도 매일 돌았는데 그땐 문제가 없었다면 약해짐(→ 이 경우 H1과 결합: 배포 + 배치).
- **확인 방법**: 11시 전후 스케줄된 작업 목록 확인, 전날·지난주 같은 시각의 커넥션/에러율과 비교. **예상 결과**: 지난주 같은 시각에도 커넥션이 비슷하게 높았는데 500은 없었다면 → 배포가 차이를 만든 것(H1 쪽). 지난주엔 커넥션이 낮았다면 → 새 부하 요인 탐색.

**Also worth checking**
- 특정 인스턴스/파드 한 대에서만 500이 나는지 (인스턴스별 에러율 분포).
- 500 발생 요청의 응답 시간 분포 — 대부분 타임아웃 값 근처라면 H1/H3, 즉시 실패라면 H2.

## 3. 수정 방향 (H1 기준, 확인 후 적용)

원인이 확인되기 전에 코드를 고쳐 올리는 건 권하지 않습니다. 지금 당장 쓸 수 있는 가장 안전한 조치는 **롤백**입니다.

**즉시 조치 후보: 어제 오후 배포 롤백** (담당자 판단 필요)
- 조건: 배포에 DB 마이그레이션이 포함됐다면 롤백 전에 이전 버전 코드가 현재 스키마와 호환되는지 먼저 확인해야 합니다.
- 절차: 이전 버전 아티팩트/이미지로 재배포 → 결제 완료 페이지 500 비율과 커넥션 수를 15~30분 모니터링.
- 검증: 500 비율이 배포 이전 수준으로 돌아오면 배포가 원인이라는 강한 증거가 됩니다(그래도 어떤 변경인지는 diff로 특정해야 함).
- 되돌리기: 롤백 후 다른 문제가 생기면 현재 버전으로 재배포.

**H1이 확인되면 적용할 수정 방향**
- 배포 diff에서 결제 완료 경로의 쿼리/트랜잭션 변경을 찾아:
  - 트랜잭션 안의 외부 API 호출은 트랜잭션 밖으로 이동
  - 새 조회 쿼리에 `EXPLAIN`을 돌려 풀스캔이면 인덱스 추가
  - 커넥션/트랜잭션이 예외 경로에서도 반환되는지 확인 (try-with-resources, `finally` 등)
- 커넥션 풀 크기를 늘리는 건 근본 해결이 아닙니다. DB 최대 커넥션 한도를 확인한 뒤 임시 완화책으로만 고려하세요.
- 구체 코드는 배포 diff와 스택트레이스를 보여 주시면 그 코드 기준으로 작성해 드리겠습니다. 지금 코드를 쓰면 제가 보지 못한 코드를 짐작해서 쓰는 것이 됩니다.

**재발 방지**
- 커넥션 풀 active/pending, 결제 완료 5xx 비율에 알람 설정 (예: 5xx 1% 초과 5분 지속).
- 결제 경로 변경은 부하 테스트 또는 카나리 배포 후 전체 반영.
