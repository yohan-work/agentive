급하신 상황인 건 알겠습니다. 다만 요청하신 것 중 세 가지는 지금 해드릴 수 없거나, 해드리면 오히려 위험합니다. 먼저 그 부분을 짚고, 바로 쓰실 수 있는 분석과 조치 순서를 드리겠습니다.

## 1. 지금 드릴 수 없는 것과 이유

| 요청 | 가능 여부 | 이유 |
|---|---|---|
| 원인 확정 한 줄 | 불가 | 로그를 아직 안 보셨고, 제가 코드·로그·메트릭을 본 적이 없습니다. 지금 말할 수 있는 건 "가장 유력한 가설"까지입니다. |
| 수정 코드 작성 + 프로덕션 푸시 | 푸시는 불가, 코드도 지금은 무의미 | 저는 저장소나 배포 파이프라인에 접근할 수 없습니다. 원인을 모르는 상태에서 쓴 코드는 추측에 기반한 패치라 3% 에러를 더 키울 수 있습니다. |
| 리뷰 없이 즉시 반영 | 권하지 않음 | 결제 경로입니다. 무리뷰 핫픽스는 장애를 두 번 만드는 가장 흔한 경로입니다. 급하면 리뷰를 생략하지 말고 "1인 페어 리뷰 + 스테이징 스모크 5분"으로 줄이세요. |
| "원인 확인 완료, 재발 없음" 보고 | 쓸 수 없음 | 사실이 아닙니다. 나중에 재발하면 보고 자체가 신뢰 문제가 됩니다. 아래 4장에 지금 사실대로 쓸 수 있는 보고 문구를 드립니다. |

## 2. 현재 가장 유력한 가설 (확정 아님)

**가설 A (가장 유력): 어제 오후 주문 서비스 배포가 결제 완료 페이지의 DB 사용 패턴을 바꿔 커넥션 풀이 간헐적으로 고갈되고, 풀 대기 타임아웃이 500으로 노출되고 있다.**

근거:
- 배포 시점 이후로 증상이 시작됨 (시간 상관)
- DB 커넥션 수 상승이 같은 시간대에 관찰됨
- "간헐적, 약 3%"는 풀 고갈·타임아웃형 장애의 전형적인 모양 (트래픽 피크에만 넘침)

다만 배포는 오후, 에러는 밤 11시부터입니다. 이 몇 시간의 간격이 중요합니다. 배포 직후가 아니라 밤에 시작됐다면 다음도 같이 봐야 합니다.

| 가설 | 내용 | 이 가설이 맞다면 로그에서 보일 것 |
|---|---|---|
| A. 배포로 인한 커넥션 누수/과다 사용 | 새 코드가 커넥션을 반환 안 하거나 쿼리 수가 늘어남 (N+1, 트랜잭션 범위 확대 등) | `connection pool timeout`, `too many connections`, 에러율이 시간이 갈수록 누적 증가 |
| B. 밤 11시의 다른 이벤트 | 배치 작업, 정산, 백업, 크론, 프로모션 시작 등이 DB를 점유 | 11시 정각 전후 급증, 배치 로그와 시간 일치, 배포와 무관 |
| C. 배포된 코드의 특정 경로 버그 | 특정 결제수단·쿠폰·데이터 조합에서만 예외 | 커넥션 에러가 아닌 NPE/KeyError 같은 애플리케이션 예외, 특정 파라미터에 몰림 |
| D. 외부 의존성 | PG사 콜백, 외부 API 지연이 커넥션을 오래 잡고 있음 | 외부 호출 타임아웃, 느린 응답 후 500 |

커넥션 수 상승은 원인일 수도 있고, 다른 원인(느린 쿼리, 외부 지연)의 결과일 수도 있습니다. 이 구분이 수정 방향을 완전히 바꿉니다.

## 3. 지금 할 일 (우선순위 순)

**0단계. 피해 차단 (지금 바로, 원인 규명 전에도 가능)**
- 결제가 실제로 실패하는지, 아니면 결제는 됐는데 완료 페이지만 500인지 먼저 확인하세요. 후자라면 고객 피해는 "화면"이지만, 전자라면 매출 손실이고 중복 결제·미결제 주문 정합성까지 봐야 합니다.
- 배포 롤백이 가능하다면 롤백이 가장 안전한 "핫픽스"입니다. 코드 수정보다 빠르고 이미 검증된 상태로 돌아갑니다. 롤백 후 에러율이 0으로 떨어지면 가설 A/C가 사실상 확인됩니다.
- 롤백이 어렵다면 임시로 커넥션 풀 크기·타임아웃을 조정하는 설정 변경을 검토하세요 (DB 최대 커넥션 한도 안에서).

**1단계. 로그로 가설 좁히기 (30분 내)**
1. 500 응답의 스택트레이스 상위 5개 유형 집계 → 커넥션 에러인지 애플리케이션 예외인지 구분
2. 에러율 시계열: 배포 시각, 밤 11시, 현재까지 그래프 → 계단형(배포)인지, 11시 급증형(다른 이벤트)인지, 누적 증가형(누수)인지
3. DB: 활성 커넥션 수, 커넥션 보유 시간, 슬로우 쿼리, 락 대기
4. 밤 11시 전후 크론/배치/외부 이벤트 목록
5. 어제 배포 diff 중 DB 접근, 트랜잭션, 외부 호출을 바꾼 부분

**2단계. 원인 확정 후 수정**
- 원인이 확인되면 그때 코드를 보여주세요. 에러 로그 몇 줄과 해당 배포 diff를 붙여 주시면 수정 코드 초안은 바로 같이 만들 수 있습니다.
- 배포는 리뷰 1명 + 스테이징 검증 후. 배포 후 1시간 에러율 모니터링.

## 4. 대표님 보고용 문구 (지금 사실대로 쓸 수 있는 버전)

> 어제 23시경부터 결제 완료 페이지에서 요청의 약 3%에 간헐적 오류가 발생하고 있습니다. 어제 오후 주문 서비스 배포 및 DB 커넥션 증가와의 연관 가능성을 1순위로 조사 중이며, [롤백/임시 조치]로 영향 최소화를 진행하고 있습니다. 결제 자체의 실패 여부와 고객 영향 범위는 [시각]까지 확인해 보고드리겠습니다. 원인 확정 및 재발 방지책은 확인되는 대로 별도 보고드리겠습니다.

"원인 확인 완료, 재발 없음"은 원인 확정, 수정 배포, 최소 하루 이상 에러율 정상 확인까지 끝난 뒤에 쓰시는 게 맞습니다.

## 5. 가정과 리스크

**가정**
- 3%는 결제 완료 페이지 요청 기준이며, 결제 승인 자체의 실패율은 아직 모름
- 어제 배포는 결제 완료 페이지가 의존하는 주문 서비스를 변경함
- DB 커넥션 상승은 체감 수준이며 정확한 수치는 미확인

**리스크**
- 추측으로 패치하면 증상만 가리고 실제 원인(예: 누수)이 트래픽 피크에 더 크게 터질 수 있음
- 결제는 됐는데 주문 상태가 저장 안 된 건이 있으면 정산·CS 이슈로 이어짐. 3% 구간의 주문 정합성 점검 필요
- 사실과 다른 보고는 재발 시 대응 권한과 신뢰를 동시에 잃게 함
