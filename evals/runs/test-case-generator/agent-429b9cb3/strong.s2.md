## 먼저 확인이 필요한 부분

명세에서 서로 부딪히는 부분은 없습니다. 다만 아래 세 가지는 비어 있어서 몇몇 케이스의 기대결과가 달라집니다.

1. **페이지 안의 검색창에 입력하면 URL의 `?query=`도 바뀌나요? "모두 지우기"를 누르면 `?query=`가 URL에서 지워지나요?** 명세에는 "`?query=`만 읽음"이라고만 되어 있습니다. 쓰지 않는다면 `?query=foo`로 들어와서 "모두 지우기"를 누른 뒤 새로고침하면 검색어가 다시 적용됩니다. 이 경우 U-05와 CL-05가 회귀가 아니라 명세대로의 동작이 됩니다.
2. **필터 값과 EmptyState의 한국어 라벨 원문이 무엇인가요?** 주신 문자열은 "난이도: 중급", "100개 중 N개 표시", "모두 지우기", "필터만 지우기"뿐입니다. 역할·카테고리·검증 상태·자동화 수준의 칩 접두어와 값, EmptyState 문구는 원문이 없어서 "번역되어 있는지 확인"으로만 적었습니다. 검색 대상에 **번역된 라벨**(예: "초급", "커뮤니티")도 들어가는지도 알려 주세요. 명세대로라면 원본 값만 들어갑니다.
3. **`src/lib/search.ts`에 있는 함수의 export 이름과 범위를 알려 주세요.** 검색만 있는지, 필터 적용과 도구 목록(중복 제거·정렬)도 있는지에 따라 단위 테스트 후보가 달라집니다. 아래 표에는 함수 이름을 추측하지 않고 "search.ts 검색 함수", "search.ts 필터 함수"로만 적었습니다.

아래 케이스 중 확인되지 않은 내용에 기댄 것에는 [ASSUMPTION]을 붙였습니다.

## 공통 전제조건 약어

- **KO 기본**: 데스크톱(≥1280px)에서 `/ko/agents`를 새로 로드해 JS 로드가 끝났고, `?query=` 없음, 검색·필터 없음
- **EN 기본**: 위와 같고 경로만 `/en/agents`
- **환경**: 로컬 `npm run dev`와 배포된 GitHub Pages에서 각각 한 번씩 실행합니다. 특히 URL 관련 케이스(U-*)는 둘 다 필수입니다.
- **N 확인 방법**: 기대 개수가 데이터에 따라 달라지는 경우에는 `content/agents/*.yaml`이나 빌드 산출물에서 조건에 맞는 에이전트 수를 세어 화면 카운트와 비교합니다. 세는 방법은 각 케이스에 적었습니다.

## 2. 커버리지 노트

**다루는 것**
- 동작: 검색 8개 필드, trim, 대소문자, 빈 값과 공백, 부분 일치 방식(단어별 AND가 아님, 필드 경계를 넘는 매칭), 필터 7종 각각, 토글과 교체, AND 조합과 순서 무관성, 두 가지 지우기, EmptyState
- 경계값: 자동화 수준 1과 5, 결과 0/1/20/100개, 빈 installTargets, 긴 입력과 특수문자
- 상태: JS 로드 전, 하이드레이션, 새로고침, `?query=` 진입(영문, 인코딩된 한국어, 빈 값, 알 수 없는 파라미터), 상단 검색으로 query가 바뀔 때, GitHub Pages 경로
- locale: ko/en 카운트 문구, 칩, 버튼, EmptyState, 교차 locale 검색, IME 조합, NFD
- 기기: 데스크톱과 375px

**일부러 뺀 것과 이유**
- 필터를 URL에 저장하는 동작: 명세상 저장하지 않으므로 U-04, U-09에서 "저장되지 않음"만 확인합니다.
- 성능 측정: 100개 규모라 수치 기준이 없어 R-06의 체감 확인으로만 다뤘습니다.
- 브라우저 매트릭스: 명세에 대상 브라우저가 없습니다. 최소한 모바일 Safari와 데스크톱 Chrome에서 한 번씩 돌리기를 권장합니다.

**가정**
- [ASSUMPTION] 칩 접두어가 "역할:", "카테고리:" 같은 형식입니다("난이도: 중급"에서 추정).
- [ASSUMPTION] 페이지 검색창은 URL에 쓰지 않습니다(질문 1).
- [ASSUMPTION] 검색은 원본 값만 대상으로 하고 번역 라벨은 포함하지 않습니다(질문 2).

**리스크**
- 한국어 사용자가 "초급"이나 "커뮤니티"처럼 **번역된 라벨로 검색하면 결과가 0개**일 수 있습니다. 검색 대상이 원본 값(beginner, community)이기 때문입니다. 한국어화 PR에서 가장 체감되기 쉬운 문제입니다.
- EN 페이지에서도 한국어 사용 사례 텍스트가 검색 대상이라, 영어 사용자가 예상하지 못한 결과가 섞일 수 있습니다(S-06).
- JS 로드 전에는 전체 100개가 보였다가 `?query=`가 적용되며 목록이 줄어드는 깜빡임이 생깁니다(IN-04, IN-05). 느린 모바일 회선에서 눈에 띕니다.
- "모두 지우기" 뒤에도 URL의 query가 남아 있으면 새로고침할 때 검색어가 되살아납니다(CL-05).
- 필드를 공백으로 이어 붙이는 방식 때문에 필드 경계를 넘는 오탐이 생길 수 있습니다(S-12).

**Also consider**
- ko/en 사전의 키 집합이 같은지 확인하는 단위 테스트(`src/i18n/dictionaries.ts`, 이번 범위 밖이지만 비용이 적음)
- 키보드만으로 필터 칩 조작하기(Tab, Enter/Space), 포커스 표시
- 스크린리더가 결과 카운트 변경을 읽어 주는지(aria-live)
- 페이지 안에서 ko와 en을 전환할 때 검색어와 필터가 유지되는지
- 활성 칩에 개별 삭제(x) 버튼이 있다면 토글과 같은 결과가 나오는지
- 다크 모드에서 칩의 선택/비선택 대비
