## 먼저 확인할 점

요구사항끼리 직접 충돌하는 부분은 없습니다. 다만 아래 세 가지는 설명에 없어서 기대 결과를 확정할 수 없습니다. 해당 케이스는 결과를 추측하지 않고 "확인/기록"하는 형태로 적었습니다.

1. **페이지 안의 검색창에 입력하면 URL의 `?query=`도 바뀌나요? "모두 지우기"를 누르면 `?query=`가 URL에서 지워지나요?** 지워지지 않으면, 모두 지우기를 누른 뒤 새로고침했을 때 검색어가 되살아납니다(TC-50, TC-57과 관련).
2. **화면에 보이는 정확한 문자열을 알려주세요.** 한국어에서는 "난이도: 중급" 말고 다른 칩(역할, 카테고리, 자동화 수준, 도구, 검증 상태, 설치 가능) 문구가 어떻게 나오는지, 영어 칩 형식이 무엇인지, EmptyState 문구가 무엇인지 필요합니다(TC-63, 64, 67).
3. **`src/lib/search.ts`가 어떤 함수를 export하나요?** 검색 매칭만 있는지, 필터 AND 조합과 도구 목록(중복 제거·정렬) 생성도 이 파일에 있는지 알아야 합니다. 이 답에 따라 단위 테스트 후보 표시가 바뀝니다.

아래 표는 다음 가정을 두고 작성했습니다.
- [ASSUMPTION] 필터 AND 조합과 도구 목록 생성도 `search.ts`의 함수가 맡습니다. 컴포넌트 안에 있다면 해당 행의 "단위" 표시는 무효입니다.
- [ASSUMPTION] 모든 에이전트는 난이도, 자동화 수준, 검증 상태를 정확히 하나씩 가집니다. 그래서 값별 개수를 더하면 100이 됩니다.
- [ASSUMPTION] 검색 대상 문자열에 들어가는 한국어 realUseCases는 로케일과 상관없이 /en에서도 검색됩니다.

## 1. 테스트 케이스 매트릭스

**공통 전제조건**
- **P-ko**: `/ko/agents`를 열고 JS 로드(하이드레이션)가 끝난 상태. 검색어와 필터 없음, 카운트 "100개 중 100개 표시".
- **P-en**: `/en/agents`에서 같은 상태. "Showing 100 of 100 agents".
- 특별한 말이 없으면 데스크톱 기준입니다. 로컬 `npm run dev`와 GitHub Pages 배포본에서 둘 다 실행합니다.
- "N"은 테스트하는 순간 화면에 보이는 결과 카드 수입니다. **모든 케이스에서 "카운트 문구의 N = 실제 카드 수"를 함께 확인합니다.**
- 기대 결과에 필요한 개수(예: 특정 도구를 가진 에이전트 수)는 QA가 에이전트 데이터에서 미리 세어 적어 둡니다. 모르는 값은 추측하지 말고 "기록"합니다.

**단위** 열: ✅ = node:test로 옮길 후보(대상 함수) / — = 수동만

## 2. 단위 테스트로 옮길 후보 (node:test + tsx, `src/lib/search.ts`)

- **검색 매칭 함수**: TC-03~18의 로직. 실제 데이터 100개 대신 필드별로 고유 단어를 넣은 **작은 fixture(3~5개)**로 만드는 편이 좋습니다. 그래야 기대값을 정확한 숫자로 고정할 수 있습니다. 케이스는 8개 필드 각각, 대소문자, trim, 공백만, 빈 문자열, 한국어 부분 일치, 여러 단어, 필드 경계, 특수문자입니다.
- **필터 함수 / AND 조합**: TC-21~41. 필터 7종 각각, 두 개 조합, 7개 전부, 교집합 0, 순서 무관. [ASSUMPTION] 필터 로직이 `search.ts` 안에 있어야 합니다.
- **도구 목록 생성**: TC-27. 중복이 있는 fixture를 넣고 정렬된 고유 목록이 나오는지 확인합니다. [ASSUMPTION] 이 함수가 `search.ts` 안에 있어야 합니다.
- **회귀 스냅샷**: TC-76~78. 실제 에이전트 데이터를 불러와 몇 가지 검색어·필터의 결과 slug 목록을 스냅샷으로 저장해 두면, 다음 콘텐츠 변경 때 결과 변화를 잡을 수 있습니다.
- **단위로 옮길 수 없는 것**: 토글, 교체, 지우기 버튼, URL, 새로고침, 칩 문구, 카운트 문구, 레이아웃, IME. 이런 상태는 컴포넌트에 있고 E2E 도구가 없으므로 수동으로 남깁니다. 토글 로직을 순수 함수(예: `toggleFilter(state, key, value)`)로 `search.ts`에 빼 두면 TC-32~35도 단위 테스트로 옮길 수 있습니다.

## 3. 커버리지 메모

**다룬 것**
- 검색 필드 8개 각각, 대소문자, trim, 빈 입력, 한국어 부분 일치, 여러 단어·필드 경계·특수문자 같은 경계 사례
- 필터 7종 각각과 값의 경계(자동화 1·5, 값별 합계), 토글과 교체, 2개·7개 AND 조합, 교집합 0
- 두 가지 지우기 버튼의 차이
- URL `?query=`(영문, 한글 인코딩, 빈 값, 공백, 무시되는 파라미터), 새로고침 뒤 상태, 상단 검색으로 query가 바뀔 때 필터 유지
- ko/en 문자열, 375px 모바일, JS 로드 전 렌더링, PR #19 전후 결과 비교

**일부러 뺀 것**
- 성능(에이전트 100개 규모라 의미가 작음)
- 브라우저 호환성 매트릭스 전체. 데스크톱 Chrome과 모바일 브라우저 1종만 다룹니다.
- 명세에 없는 동작의 정답. TC-46, 47, 57, 67, 75는 결과를 기록만 합니다.

**리스크**
- 한국어 텍스트가 검색 대상 문자열에 추가되면서 영어 검색 결과가 늘어날 수 있습니다(TC-76).
- 필터가 URL에 저장되지 않으므로, 사용자가 필터를 건 링크를 공유하거나 새로고침하면 필터가 사라집니다. 명세상 의도된 동작이지만 사용자 불만이 생길 수 있는 지점입니다.
- 느린 네트워크에서 `?query=`로 들어오면 전체 목록이 먼저 보였다가 바뀌는 깜빡임이 생깁니다(TC-74).
- 모두 지우기를 눌러도 URL에 query가 남는다면, 새로고침할 때 검색어가 되살아납니다(TC-47).

## Also consider (명세에 없는 동작, 한 줄씩)

- 카드를 클릭해 상세로 갔다가 뒤로 왔을 때 검색어와 필터가 유지되는지
- 결과 카드 링크가 현재 로케일(`/ko/agents/...`)을 유지하는지
- macOS에서 복사한 한글(NFD, 자모 분리)을 붙여넣으면 `includes`로 일치하지 않을 수 있음
- 키보드만으로 칩 선택·해제가 가능한지, 스크린리더가 카운트 변화를 읽어 주는지
- 사전(ko/en) 키가 서로 빠짐없이 짝을 이루는지 검사하는 테스트. `search.ts` 범위 밖이라 현재 도구 제약에 포함되지 않음
- 검색어가 아주 길 때(수백 자) 입력창과 칩 레이아웃
