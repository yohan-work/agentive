# /agents 검색·필터 회귀 테스트 케이스 (PR #19 한국어화)

## 0. 범위와 표기

- **대상 경로**: `/en/agents`, `/ko/agents` (GitHub Pages 배포본은 trailing slash 형태 `/ko/agents/`도 확인)
- **환경**: 로컬 `npm run dev` + 배포된 GitHub Pages. 둘 다 돌려야 하는 케이스는 "배포본 필수"로 표시함 (정적 export·basePath·hydration 관련 이슈는 dev 서버에서 재현이 안 되는 경우가 많음).
- **뷰포트**: 데스크톱(≥1280px), 모바일(375px). 뷰포트를 따로 적지 않은 케이스는 데스크톱 기준이고, 모바일 전용 케이스는 M-xx로 따로 뺌.
- **우선순위**: P0 = 릴리스 차단 / P1 = 이번 회귀 사이클에서 반드시 실행 / P2 = 시간 되면 실행
- **단위 후보**: ✅ = `src/lib/search.ts` 단위 테스트로 옮기기 좋음, △ = 로직 일부만 가능(UI 부분은 수동으로 남김), – = 수동 전용
- **데이터 기준값**: 전체 100개, 설치 가능(`installTargets` 있음) 20개. 아래 "N개"로 쓴 기대값은 **실행 전에 QA가 데이터에서 실측해 채워 넣을 것** (아래 §3 "기준값 준비" 참고).

## 2. 단위 테스트로 옮길 후보 (node:test + tsx)

`src/lib/search.ts`에 있는 함수 시그니처를 모르기 때문에, 아래는 "검색어 + 필터 객체 → 에이전트 배열"을 반환하는 순수 함수(예: `filterAgents(agents, query, filters)`)와 도구 목록 생성 함수가 있다고 가정하고 작성했습니다. 실제 이름에 맞춰 바꿔 주세요.

**원칙**: 픽스처는 실제 100개 데이터가 아니라 5~8개짜리 **작은 가짜 에이전트 배열**로 만드세요. 실제 데이터를 쓰면 콘텐츠가 바뀔 때마다 테스트가 깨집니다. 다만 "설치 가능 = 20"처럼 데이터 무결성 성격의 검증은 실제 데이터로 1~2개만 따로 둡니다.

| 우선 | 단위 테스트 | 원래 케이스 |
|---|---|---|
| 1 | 빈 문자열/공백만 → 전체 반환 | N-07 |
| 1 | 앞뒤 공백 trim | N-06 |
| 1 | 대소문자 무시 | N-04 |
| 1 | 8개 필드 각각에만 있는 토큰으로 매칭 (필드별 1 케이스, table-driven) | N-05, R-05 |
| 1 | realUseCases 한국어 텍스트 매칭 | K-01 |
| 1 | 필터 7종 각각 단일 적용 | N-12 |
| 1 | 필터 AND 조합, 적용 순서 무관 | F-01, F-05 |
| 1 | 검색 + 필터 교집합 | F-03 |
| 1 | 배열 필드(categories, roles, tools)에서 첫 번째가 아닌 값으로 필터 | F-08 |
| 1 | `installTargets` 없음 / `[]` / 1개 이상 → 설치 가능 판정 | R-07 |
| 1 | 필터 값은 enum 원본으로 비교 (라벨 문자열 넣으면 매칭 안 되는 게 정상) | R-01, R-03 |
| 2 | 0건 반환 | E-01, E-02 |
| 2 | 도구 목록: 중복 제거·정렬 | N-16, K-15 |
| 2 | NFC/NFD: 현재 동작을 명시적으로 고정 (실패하면 정규화 추가 논의) | K-06 |
| 2 | 알려진 한계 고정: 띄어쓰기 차이·순서 뒤집힘·필드 경계 오탐 (현재 동작을 문서화하는 목적. 나중에 토큰화 검색으로 바꾸면 기대값을 함께 변경) | K-07~K-09 |
| 2 | dictionaries의 en/ko 키 집합이 동일 | R-04 |
| 3 | 실제 데이터 기준: 설치 가능 20개, 전체 100개 | N-13 (데이터 무결성) |

토글/교체/모두 지우기/필터만 지우기(N-10, N-11, N-17, N-18)는 지금은 컴포넌트 state 안에 있을 가능성이 높습니다. 이 로직을 `(state, action) => state` 형태의 순수 리듀서로 `src/lib/`에 빼면 단위 테스트로 옮길 수 있어서, 수동 케이스를 4개 더 줄일 수 있습니다.

예시 골격:

```ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { filterAgents } from "../src/lib/search";
import { fixtures } from "./fixtures/agents";

test("공백만 있는 검색어는 전체를 반환한다", () => {
  assert.equal(filterAgents(fixtures, "   ", {}).length, fixtures.length);
});

test("필터는 라벨이 아니라 enum 값으로 비교한다", () => {
  const byEnum = filterAgents(fixtures, "", { difficulty: "intermediate" });
  assert.ok(byEnum.length > 0);
  assert.ok(byEnum.every((a) => a.difficulty === "intermediate"));
});

for (const [field, token] of [
  ["summary", "zzsummarytoken"],
  ["realUseCases", "고유사용사례토큰"],
  // ... 8개 필드
] as const) {
  test(`${field} 필드에서 검색된다`, () => {
    const ids = filterAgents(fixtures, token, {}).map((a) => a.slug);
    assert.deepEqual(ids, [`only-${field}`]);
  });
}
```

## 3. 실행 전 준비 (QA)

1. **기준값 표 만들기**: 필터 7종의 각 값별 결과 수, 설치 가능 20개, 0건이 나오는 조합 1개, 7종 전부 걸어도 ≥1건 나오는 조합 1개, 필드별 고유 토큰, realUseCases 전용 한국어 단어. 데이터(`content/agents/*.yaml` 또는 번들 결과)에서 한 번 뽑아 두고 테스트 시트 상단에 고정. 콘텐츠가 바뀌면 이 표만 갱신.
2. **실행 순서 제안**: P0 전체(데스크톱 ko → en) → 모바일 M-01/M-02 → 배포본 필수 케이스(U-13, U-14, R-08) → P1 → P2.
3. **예상 소요**: P0 약 30개 × 2~3분 ≈ 1.5시간, P1 포함 시 반나절 정도. 단위 테스트로 옮기면 수동은 UI/IME/URL/모바일 위주로 약 절반으로 줄어듭니다.

## 4. 가정

- 필터 비교는 에이전트 데이터의 enum/slug 원본 값으로 하고, 한국어는 표시 라벨에만 적용된다고 가정했습니다 (R-01~R-03이 이 가정을 검증).
- 자동화 수준 필터는 "N 이상"이 아니라 "정확히 N"으로 가정했습니다.
- categories, roles, tools는 배열이고, 필터는 "배열에 해당 값 포함" 조건이라고 가정했습니다.
- 검색 haystack은 로케일과 무관하게 동일하다고 가정했습니다 (K-02에서 확인).
- 페이지 내 검색 입력은 URL을 갱신하지 않는다고 가정했습니다 (U-07에서 확인).
- 페이지네이션/무한 스크롤이 없어 결과가 한 번에 모두 렌더된다고 가정했습니다 (N-19).
- `src/lib/search.ts`의 필터링 로직은 React에 의존하지 않는 순수 함수라고 가정했습니다. 그렇지 않다면 먼저 분리가 필요합니다.
