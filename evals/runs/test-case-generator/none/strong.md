아래는 말씀하신 현재 동작을 기준으로 정리한 회귀 테스트 매트릭스입니다. QA 1명이 한 번에 돌릴 수 있도록 **P0 → P1 → P2** 순으로 우선순위를 붙였고, `자동화` 열에 **U**(node:test 단위 테스트로 옮길 후보) / **M**(수동 유지)을 표시했습니다.

## 0. 공통 전제와 테스트 데이터 준비

**환경**
- E1: 로컬 `npm run dev` (`http://localhost:3000/ko/agents`, `/en/agents`)
- E2: 배포된 GitHub Pages (basePath 포함 경로, 정적 export 결과물)
- 뷰포트: 데스크톱(1280px 이상), 모바일(375px, Chrome DevTools 에뮬레이션 + 가능하면 실기기 1대)

**미리 뽑아 둘 기준값(테스트 오라클)**
수동 테스트에서 "N개가 맞는지"를 판단하려면 기대값이 먼저 있어야 합니다. 테스트 전에 데이터에서 아래 값을 뽑아 표로 만들어 두세요(단위 테스트의 fixture로도 재사용 가능).

| 기준값 | 용도 |
|---|---|
| 전체 수 = 100, 설치 가능 수 = 20 | 기본 카운트 |
| 특정 태그/도구 1개로만 매칭되는 검색어 1~2개 (예: 한 에이전트에만 있는 도구명) | 필드별 매칭 확인 |
| realUseCases의 한국어 문장에만 있는 단어 1개 | 한국어 사용 사례 검색 확인 |
| 난이도 `intermediate` 수, 자동화 수준 `3` 수 등 필터별 개수 | 필터 카운트 확인 |
| "필터 A AND 필터 B" 결과가 **0개**가 되는 조합 1개 | 빈 결과 확인 |
| "검색어 + 설치 가능만" 결과가 1~3개인 조합 1개 | 조합 확인 |

> 이 기준값 목록 자체를 `src/lib/search.ts` 함수로 계산하는 스크립트가 되면 QA와 단위 테스트가 같은 오라클을 쓰게 됩니다.

## 2. 단위 테스트로 옮길 후보 (node:test + tsx, `src/lib/search.ts`)

E2E 도구가 없으니 **"결과 집합이 맞는가"는 전부 단위 테스트로, "화면에서 그렇게 보이는가"만 수동으로** 나누는 것이 가장 효율적입니다.

**1순위 (P0, 바로 옮길 것)**
- 필드별 매칭: S-03, S-04, K-01 — 필드마다 한 개씩, 작은 fixture 에이전트 2~3개로 테이블 테스트
- 대소문자·trim·빈값: S-05, S-06, S-07
- 필터별 단일 적용과 AND 조합: F-01~F-08, C-01, C-02, C-06
- 로케일 무관성: X-01, X-02 — 같은 입력에 대해 로케일 인자가 결과에 영향을 주지 않는지(필터 함수가 로케일을 받지 않는다면 이 자체가 보장)
- 사전 키 동기화: K-12 — `Object.keys(en)`과 `Object.keys(ko)` 비교(중첩이면 재귀)

**2순위**
- 특수문자 안전성(S-08), 전각 공백(K-08), 영한 혼합(K-09)
- 도구 목록 dedupe + 정렬(F-05, X-03)
- 설치 가능 판정(X-06), 카운트 분모(X-07)
- 실제 데이터 스냅샷: 실제 100개 데이터로 "설치 가능 = 20", 난이도 합계 = 100 같은 **불변식** 테스트. 데이터가 바뀌면 깨지므로 정확한 수 대신 불변식(합계, 부분집합 관계) 위주로

**3순위 (현재 동작을 고정하는 characterization test, 기대값 결정 후)**
- S-09(필드 경계 매칭), S-10(다중 단어), K-02(en에서 한국어 매칭), K-06(NFD), K-07(띄어쓰기)
  → 제품 결정 전까지는 "현재 동작은 이렇다"를 테스트로 박아 두고, 동작을 바꿀 때 의도적으로 테스트를 수정하게 만듭니다.

**토글/교체/Clear 로직(F-10, F-11, C-07, C-08)** 은 현재 컴포넌트 안의 상태 로직일 가능성이 큽니다. `toggleFilter(state, key, value)`, `clearAll(state)`, `clearFilters(state)` 같은 순수 함수로 `src/lib`에 빼면 단위 테스트가 가능해지고, 수동 케이스가 약 6개 줄어듭니다.

예시 골격:

```ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { filterAgents } from "../src/lib/search"; // 실제 함수명에 맞게 수정

const fixtures = [ /* 필드별로 고유 단어를 가진 최소 에이전트 3~5개 */ ];

test("검색은 대소문자와 앞뒤 공백을 무시한다", () => {
  const a = filterAgents(fixtures, { query: "REVIEW" });
  const b = filterAgents(fixtures, { query: "  review " });
  assert.deepEqual(a.map((x) => x.slug), b.map((x) => x.slug));
});

test("난이도와 카테고리는 AND로 결합된다", () => {
  const r = filterAgents(fixtures, { difficulty: "intermediate", category: "engineering" });
  assert.ok(r.every((x) => x.difficulty === "intermediate" && x.categories.includes("engineering")));
});
```

## 4. 가정

- **A-1** 필터 비교는 번역 라벨이 아니라 데이터의 원시 값(`intermediate`, `tested`, 숫자 1~5)으로 이루어진다.
- **A-2** 모든 에이전트는 난이도·자동화 수준·검증 상태를 하나씩 가진다(합계 = 100 불변식의 근거). 누락이 있으면 F-03/F-04 기대결과를 수정해야 합니다.
- **A-3** 목록 페이지 검색창에서 직접 타이핑한 값이 URL `?query=`에 반영되는지는 설명에 없습니다. 반영되지 않는다면 새로고침 시 검색어도 사라지는 것이 정상입니다. U-07은 이 동작을 먼저 확인한 뒤 기대결과를 확정하세요.
- **A-4** 도구·역할·카테고리 값의 번역 여부는 PR #19 범위에 따라 다릅니다. D-06은 번역 사전이 있는 값만 번역을 기대합니다.
- **A-5** "설치 가능" = `installTargets`가 존재하고 비어 있지 않음.
- **A-6** 로케일 전환 시 query 유지 여부는 스펙이 없어 "확인 후 기록"으로 두었습니다.
