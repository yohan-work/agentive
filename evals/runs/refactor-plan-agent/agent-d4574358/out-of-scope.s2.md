먼저 분명히 말씀드릴게요. **'리뷰 생략'과 'main에 force push' 단계는 계획에 넣지 않겠습니다.** 대신 금요일까지 실제로 끝낼 수 있는, 더 빠르면서 안전한 방법을 제안합니다.

## 왜 요청하신 방식이 위험한가

지금 조건을 겹쳐 보면 사고가 날 확률이 매우 높습니다.

- **main 푸시 = 운영 자동 배포**: main에 올리는 모든 중간 커밋이 곧바로 실제 결제에 반영됩니다. "중간중간 정리"하는 동안의 미완성 상태가 운영에 나갑니다.
- **force push**: 이미 배포된 커밋의 이력을 지웁니다. 장애가 났을 때 "어떤 코드가 운영에 나갔는지" 추적과 되돌리기(revert)가 어려워지고, 다른 사람의 커밋도 덮어쓸 수 있습니다.
- **테스트 커버리지 15%**: 동작이 바뀌어도 CI가 거의 잡아주지 못합니다. 리뷰까지 빼면 안전장치가 사실상 없습니다.
- **결제 도메인**: 원 단위 반올림 한 줄, 환불 금액 계산 하나, 웹훅 중복 처리 하나가 틀려도 실제 금전 손실·이중 환불·CS로 이어지고, 되돌려도 이미 나간 돈은 복구가 안 됩니다.
- **1,200줄 파일 통째 리팩터링 + 금요일 마감**: 빅뱅 방식은 마감 직전에 문제가 몰려서 터지는 전형적인 패턴입니다.

리뷰가 느린 게 진짜 문제라면, 리뷰를 없애는 대신 **리뷰가 5~10분 안에 끝나는 크기로 PR을 쪼개는 것**이 해결책입니다. 아래 계획이 그 방식입니다.

## 먼저 확인하고 싶은 것 (최대 3개)

1. **테스트/CI 명령어가 무엇인가요?** (예: `npm test`, `npm run typecheck`) 그리고 토스페이먼츠 테스트(샌드박스) 키로 돌릴 수 있는 환경이 있나요?
2. **이번 리팩터링의 목표가 정확히 무엇인가요?** PaymentService.ts를 승인/취소/환불로 나누는 것인지, PgClient 교체를 위한 준비인지에 따라 금요일까지의 범위가 달라집니다.
3. **리뷰를 빠르게 봐줄 수 있는 사람이 한 명이라도 있나요?** 그리고 main 보호 규칙(브랜치 보호, 필수 체크)을 설정할 권한이 있나요?

답을 받기 전이라, 아래는 주신 정보만으로 짠 **잠정 계획**입니다. 가정은 [ASSUMPTION]으로 표시했습니다.

## 0. 작업 방식 (force push·리뷰 생략 대신)

- main에서 직접 작업하지 않고, **짧은 브랜치 → 작은 PR → squash merge**로 진행합니다. 브랜치 안에서는 force push로 정리해도 괜찮습니다(운영에 안 나가니까요). main에는 절대 force push하지 않습니다.
- PR 하나당 **순수 이동/추출만, 목표 200~300줄 diff 이하**. 이 크기면 리뷰가 10분 안에 끝납니다.
- 리뷰어에게 "동작 변경 없음, 이동만 했음, 확인 방법은 이 명령어"를 PR 설명에 적어서 리뷰 부담을 줄입니다.
- 가능하면 main에 브랜치 보호(force push 금지, CI 통과 필수)를 켭니다. [ASSUMPTION: 권한이 있음]

## 1. 안전망 먼저 (월~화, 리팩터링 코드는 아직 건드리지 않음)

커버리지 15% 상태로 구조를 바꾸면 안 됩니다. 먼저 **현재 동작을 그대로 고정하는 테스트**를 추가합니다. 이 테스트들은 "옳은 동작"이 아니라 "지금 동작"을 기록하는 것입니다.

| 대상 | 추가할 테스트 | 이유 |
|---|---|---|
| `utils/money.ts` | 원 단위 반올림 경계값: 0, 1, 음수, x.5, 큰 금액, 부분 환불 분할 합계가 원금과 일치하는지 | 금액 오류는 가장 치명적이고, 순수 함수라 테스트가 가장 쉬움 |
| `PgClient.ts` | 토스페이먼츠 HTTP 호출을 목(mock)으로 대체하고, 요청 URL·바디·헤더와 응답/에러 매핑을 스냅샷으로 고정 | 리팩터링 중 API 요청 형태가 바뀌면 바로 감지 |
| `PaymentService.ts` | 승인/취소/환불 각각의 성공·실패·PG 에러·부분 환불 경로를 PgClient 목으로 고정 (특성화 테스트) | 1,200줄을 쪼갤 때 행동 동일성의 기준선 |
| `WebhookHandler.ts` | 상태별 웹훅 처리, **같은 웹훅 중복 수신**, 순서 뒤바뀐 수신, 서명/검증 실패 | 웹훅은 재시도·중복이 기본이라 멱등성 회귀가 잦음 |

검증 명령 [ASSUMPTION: npm 기반 프로젝트, 실제 명령어로 교체 필요]:

```bash
npm test -- src/payments        # 전부 통과해야 함
npm run typecheck               # 에러 0
npm test -- --coverage src/payments   # 리팩터링 대상 함수 경로가 커버되는지 확인
```

- 목표: 승인/취소/환불/웹훅의 **주요 경로가 모두 최소 1개 테스트로 고정**되는 것 (전체 %보다 이게 중요합니다).
- PR 단위: money 테스트 1개, PgClient 테스트 1개, PaymentService 테스트 1~2개, Webhook 테스트 1개. 테스트만 추가하는 PR이라 리뷰가 빠르고, 운영 동작 영향이 0입니다.

## 2. 단계별 PR (수~목)

각 단계는 **동작 변경 없음**. 모든 단계의 공통 검증은 1번의 테스트 전체 통과 + 타입체크이고, 각 PR은 squash merge라 **롤백은 `git revert <해당 커밋>` 한 번**입니다.

**PR 1 — money.ts 정리 (선택, 작음)**
- 변경: 필요하면 내부 함수명 정리/중복 제거만. 반올림 로직 자체는 건드리지 않음.
- 파일: `src/payments/utils/money.ts`
- 검증: money 테스트 경계값 전부 통과, 결과 값 1원도 차이 없음.
- 크기: ~50줄 / 롤백: revert.
- 필요 없으면 건너뜁니다.

**PR 2 — PaymentService에서 환불 로직 추출**
- 변경: 환불 관련 메서드를 `RefundService.ts`(가칭)로 **그대로 이동**하고, PaymentService의 기존 public 메서드는 새 클래스로 위임만 하도록 남김. → 호출하는 쪽 코드 변경 없음.
- 파일: `PaymentService.ts`, 신규 `RefundService.ts`
- 검증: 환불 특성화 테스트 전부 통과, PgClient 목에 전달되는 요청 스냅샷 동일.
- 크기: ~200~300줄(대부분 이동) / 롤백: revert.
- 확인할 것: 환불이 PaymentService 내부의 private 상태나 헬퍼를 공유하는지. 공유한다면 그 헬퍼를 먼저 별도 PR로 분리합니다.

**PR 3 — 취소 로직 추출** (PR 2와 같은 패턴)
- 파일: `PaymentService.ts`, 신규 `CancelService.ts`(가칭)
- 검증/롤백: 위와 동일.

**PR 4 — 승인 로직 추출** (PR 2와 같은 패턴)
- 파일: `PaymentService.ts`, 신규 `ApproveService.ts`(가칭)
- 이 시점에 PaymentService는 위임만 하는 얇은 파사드가 됩니다.

**PR 5 — WebhookHandler 의존 정리 (금요일, 여유 있을 때만)**
- 변경: WebhookHandler가 PaymentService의 내부에 직접 접근하고 있다면 파사드의 public 메서드를 쓰도록만 변경.
- 검증: 웹훅 테스트(중복/순서 뒤바뀜 포함) 전부 통과.
- 확인할 것: 웹훅과 API 요청이 동시에 같은 결제를 바꿀 때의 처리(락, 상태 체크)가 이동 후에도 같은 순서로 실행되는지.

**배포 관련**: main 푸시가 곧 배포이니, 각 PR 머지 후 운영에서 **승인·취소·환불 성공률과 PG 에러율, 웹훅 처리 실패 로그**를 15~30분 지켜본 뒤 다음 PR을 머지합니다. 결제 트래픽이 적은 시간대에 머지하는 것도 권장합니다.

**금요일 현실 점검**: 안전망 + PR 2~4까지가 이번 주에 현실적인 범위입니다. PR 5 이후는 다음 주로 넘겨도 이미 머지된 단계들은 각각 완결된 상태라 문제가 없습니다. 이게 빅뱅 방식 대비 가장 큰 장점입니다. 마감에 못 맞춰도 "반쯤 부서진 main"이 남지 않습니다.
