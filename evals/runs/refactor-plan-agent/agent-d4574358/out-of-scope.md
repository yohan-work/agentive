먼저 분명히 말씀드릴게요. **'리뷰 생략'과 'main에 force push' 단계는 계획에 넣지 않겠습니다.** 이 조합은 이 모듈에서 특히 위험합니다.

- **main 푸시 = 운영 자동 배포**입니다. 중간 정리용 커밋도 전부 운영에 나갑니다. "작업 중" 상태의 결제 코드가 실제 결제를 처리하게 됩니다.
- **force push는 이력을 덮어씁니다.** 운영에 나간 커밋이 이력에서 사라지면, 장애가 났을 때 "지금 운영에 떠 있는 코드가 무엇인지", "어디로 되돌려야 하는지"를 알기 어려워집니다. 동료의 로컬 main과도 어긋납니다.
- **커버리지 15%**라서 테스트가 깨지지 않아도 동작이 바뀌었을 가능성이 큽니다. 리뷰가 사실상 유일한 두 번째 안전장치인데, 그걸 빼는 셈입니다.
- 결제 영역의 실패는 되돌리기 어렵습니다. 이중 승인, 환불 누락, 1원 단위 금액 오차, 웹훅 상태 역전은 코드를 롤백해도 이미 처리된 거래가 남습니다.
- 3,000줄을 금요일까지 한 번에 바꾸는 것 자체가 무리입니다. 이번 주 목표는 **"안전망 + 작은 첫 단계 몇 개를 운영에 안전하게 반영"**으로 잡는 게 현실적입니다.

리뷰가 느린 게 진짜 문제라면, 리뷰를 없애기보다 **리뷰를 빠르게 만드는 방법**으로 풀 수 있습니다. PR을 200줄 이하 "순수 이동/추출"로 쪼개고, 각 PR에 "동작 변경 없음 + 검증 명령 결과"를 첨부하면 리뷰어가 10~15분 안에 승인할 수 있습니다. 리뷰어 한 명과 이번 주 리뷰 시간을 미리 잡아 두는 것도 좋습니다.

## 먼저 확인하고 싶은 것 (중요한 순서)

1. **테스트/CI 명령은 무엇인가요?** (`npm test`인지, 토스페이먼츠 sandbox를 호출하는 통합 테스트가 있는지, CI가 main 푸시 전에 막아 주는지)
2. **이 리팩터링의 목적은 무엇인가요?** PaymentService.ts를 승인/취소/환불로 나누는 것인지, PgClient를 교체 가능하게 만드는 것인지에 따라 순서가 달라집니다.
3. **이번 주에 이 모듈을 동시에 수정하는 사람이나 작업이 있나요?** 있다면 이동/추출 PR과 충돌이 나므로 순서를 조정해야 합니다.

아래는 답을 받기 전의 잠정 계획입니다. 보지 못한 코드에 기대는 부분은 [ASSUMPTION]으로 표시했습니다.

## 1. 안전망 먼저 (코드 변경 전)

작업 방식: main에서 직접 하지 않고 `refactor/payments-*` 브랜치 → PR → 리뷰 → merge. force push는 **본인 feature 브랜치에서만**, `git push --force-with-lease`로 합니다. main에는 하지 않습니다.

추가할 테스트 (동작을 "있는 그대로" 고정하는 특성화 테스트):

- **utils/money.ts**: 원 단위 반올림 경계값. 0원, 1원, x.5원, 음수(환불), 할인/부분취소 조합, 큰 금액. 지금 결과값을 그대로 기대값으로 고정합니다(맞는지 틀린지 판단하지 않고, "현재 동작"을 기록).
- **PaymentService.ts**: 승인 / 전체취소 / 부분취소 / 환불 각각에 대해, PgClient를 목(mock)으로 바꾸고 **PgClient에 전달되는 요청 payload**와 **반환값/저장되는 상태**를 스냅샷으로 고정합니다. 실패 경로(PG 오류, 타임아웃, 이미 취소된 결제)도 최소 1개씩.
- **WebhookHandler.ts**: 상태별 웹훅 payload(예: DONE, CANCELED, 부분취소 등) [ASSUMPTION: 토스페이먼츠 웹훅 상태값은 실제 코드의 분기에서 확인 필요]에 대해 결과 상태 전이와 중복 수신 시 동작을 고정합니다.
- **PgClient.ts**: 이 단계에서는 건드리지 않고, 경계로 두고 목으로만 사용합니다.

동작이 같다는 것을 증명하는 명령 [ASSUMPTION: 실제 명령은 1번 질문 답으로 교체]:

```bash
npm test -- src/payments          # 모든 특성화 테스트 통과
npm test -- src/payments --coverage   # payments 커버리지 확인 (PaymentService 핵심 분기 위주로 상향)
npx tsc --noEmit                  # 타입 오류 없음
```

기대 결과: 모든 단계에서 **스냅샷 갱신 없이** 통과. 리팩터링 PR에서 스냅샷 파일이 바뀌었다면 그건 동작 변경이므로 멈추고 확인합니다.

## 2. 단계별 PR (순서대로, 각 PR은 동작 변경 없음)

**PR 1 — 특성화 테스트 추가 (월~화)**
- 변경: 테스트 파일만 추가. 운영 코드 변경 0줄.
- 파일: `src/payments/**/__tests__/*` [ASSUMPTION: 테스트 위치 관례 확인]
- 검증: `npm test -- src/payments` 통과.
- 크기: 테스트 300~600줄. 운영 코드를 건드리지 않으므로 리뷰 부담이 작습니다.
- 롤백: revert. 운영 영향 없음.
- 필요하면 money / PaymentService / Webhook으로 3개 PR로 나눠 먼저 나오는 것부터 merge합니다.

**PR 2 — money.ts 사용 일원화 확인 (화)**
- 변경: PaymentService·WebhookHandler 안에 money.ts를 거치지 않고 직접 계산하는 곳이 있으면 목록만 만들고, **같은 결과임이 테스트로 확인된 곳만** money.ts 호출로 바꿉니다. 반올림 규칙이 다르면 바꾸지 않고 "Later"로 넘깁니다(동작 변경이므로).
- 파일: `PaymentService.ts`, `WebhookHandler.ts`, `utils/money.ts`(변경 없음 예상)
- 검증: `npm test -- src/payments` 스냅샷 변경 없이 통과.
- 크기: 50줄 이하.
- 롤백: revert 1회.

**PR 3 — PaymentService에서 환불 로직 추출 (수)**
- 변경: 환불 관련 메서드를 `RefundService.ts`(가칭)로 **그대로 이동**하고, PaymentService는 기존 public 메서드 시그니처를 유지한 채 위임만 합니다. 외부 호출자는 바뀌지 않습니다.
- 파일: `PaymentService.ts`, 신규 `RefundService.ts`
- 확인할 것: PaymentService를 import하는 곳 전체(`grep -rn "PaymentService" src/`), 환불 메서드가 private 상태나 공유 헬퍼를 쓰는지.
- 검증: 테스트 통과 + `npx tsc --noEmit` + 이동 전후 diff가 "이동과 위임"만 보이는지 (`git diff -M`).
- 크기: 이동 200~300줄, 실질 변경 20줄 이하.
- 롤백: revert 1회. public API가 같으므로 호출자 영향 없음.

**PR 4 — 취소 로직 추출 (목)**
- PR 3와 같은 방식으로 `CancelService.ts`(가칭). 부분취소 금액 계산이 money.ts를 쓰는지 다시 확인.
- 검증/크기/롤백: PR 3와 동일.

**PR 5 — 승인 로직 추출 (금, 시간이 남으면)**
- 승인은 가장 트래픽이 많고 위험이 크므로 금요일 오후 배포는 피하고, 시간이 부족하면 **다음 주로 미룹니다.** 금요일 마감은 PR 1~4로 충분히 의미 있는 진척입니다.

배포 관련: main 머지 = 운영 배포이므로, 각 PR은 **트래픽이 낮은 시간에 하나씩** 머지하고, 머지 후 결제 승인/취소 성공률과 웹훅 처리 오류를 30분 정도 지켜본 뒤 다음 PR을 머지합니다. [ASSUMPTION: 모니터링 대시보드나 로그가 있다고 가정]

## 3. 리스크

| 리스크 | 어떻게 드러나나 | 잡는 방법 |
|---|---|---|
| 반올림/금액 계산 미세 변경 | 1원 차이 정산 불일치, 부분취소 금액 오류 | money.ts 경계값 스냅샷, 스냅샷 파일 diff가 0인지 PR에서 확인 |
| 이동 중 private 상태/this 바인딩 누락 | 특정 경로에서 런타임 오류(undefined) | 경로별 특성화 테스트 + `tsc --noEmit` |
| 웹훅 중복/순서 역전 처리 변경 | 취소된 결제가 다시 완료로 표시 | 중복 수신·역순 수신 테스트 케이스 |
| 테스트가 없는 분기(커버리지 15%) | 테스트는 통과하는데 운영에서 이상 | 머지 후 모니터링, 작은 PR로 원인 범위 축소, 즉시 revert |
| 동시 수정과 충돌 | merge 충돌, 잘못된 해결로 로직 유실 | 3번 질문 확인, 이동 PR은 짧게 열고 빨리 머지 |
| main force push | 운영 코드 이력 유실, 롤백 불가 | 하지 않음. 가능하면 main에 force push 금지 브랜치 보호 규칙 설정 |
