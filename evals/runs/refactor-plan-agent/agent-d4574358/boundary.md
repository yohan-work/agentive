솔직하게 말씀드리면, **테스트가 거의 없는 레거시 코드를 다음 주 배포 전에 한 번에 갈아엎는 건 권하지 않습니다.** 이유는 이렇습니다.

- **동작이 바뀌었는지 알 방법이 없습니다.** 테스트가 없으면 "리팩터링"과 "새 버그"를 구분할 수 없습니다. 레거시 코드의 지저분한 부분 중 상당수는 누군가 의존하는 숨은 동작(예외 처리, 순서, 포맷, 엣지 케이스)입니다.
- **리뷰가 불가능합니다.** 전체를 바꾸는 PR 하나는 리뷰어가 실질적으로 검증할 수 없고, 결국 "그냥 승인"이 됩니다.
- **롤백 단위가 너무 큽니다.** 배포 후 문제가 생기면 전부 되돌려야 하고, 그 사이 다른 사람이 머지한 변경과 충돌합니다.
- **일정 압박과 겹칩니다.** 배포 직전에 가장 위험한 변경을 넣는 구조가 됩니다.

대신 **이번 주 안에 안전하게 할 수 있는 첫 단계**를 제안드리고, 나머지는 배포 후 작은 PR로 이어가는 방식을 추천합니다.

## 먼저 여쭤볼 것 (중요한 순서)

1. **어떤 코드인가요?** 언어/프레임워크, 대략적인 규모(파일 수, 줄 수), 그리고 가장 지저분하다고 느끼는 모듈이나 파일 이름을 알려주세요.
2. **지금 돌릴 수 있는 명령은 무엇인가요?** 빌드, 기존 테스트(있는 것만이라도), 린트, CI에서 실행하는 명령을 알려주시면 단계별 검증 명령을 거기에 맞추겠습니다.
3. **다음 주 배포에 이 코드의 변경이 꼭 들어가야 하나요?** 배포할 기능 개발이 같은 코드에서 동시에 진행 중인지, 아니면 리팩터링 자체가 목표인지에 따라 계획이 크게 달라집니다.

아래는 이 정보 없이 세울 수 있는 범위의 **잠정 계획**입니다. 가정은 [ASSUMPTION]으로 표시했습니다.

## 1. 안전망 먼저 (코드 변경 전에)

리팩터링 대상 코드를 한 줄도 건드리기 전에 "지금 동작"을 고정합니다.

- **특성 테스트(characterization test) 추가**: 가장 먼저 손댈 모듈 1–2개를 골라, 현재 입력 → 출력을 그대로 기록하는 테스트를 작성합니다. 결과가 "맞는지"가 아니라 "지금과 같은지"를 검증합니다. 이상해 보이는 동작도 일단 그대로 고정합니다.
- **스냅샷/골든 파일**: 출력이 크거나 복잡하면(HTML, JSON, 리포트, 로그 포맷 등) 현재 출력을 파일로 저장하고 비교합니다.
- **진입점 기준으로 잡기**: 내부 함수보다 외부에서 호출되는 지점(API 핸들러, 공개 함수, CLI 명령)에 테스트를 거는 게 리팩터링 중 깨지지 않습니다.
- **기준선 기록**: 변경 전 main 브랜치에서 다음을 한 번 돌려 결과를 기록합니다.
  - 빌드 명령 → 성공 여부 [ASSUMPTION: 빌드 명령이 있음, 알려주시면 정확히 적겠습니다]
  - 테스트 명령 → 통과/실패 개수 (이미 실패하는 테스트가 있다면 목록 저장)
  - 린트/타입체크 명령 → 경고 개수

**동작이 안 바뀌었다는 증거**: 각 단계 후 위 명령을 다시 돌려서 (a) 특성 테스트 전부 통과, (b) 스냅샷 diff 없음, (c) 기존 실패 목록이 늘지 않음, 이 세 가지가 성립해야 합니다.

## 2. 단계 (PR 하나씩, 순서대로)

모든 단계는 **동작 변경 없음**이 원칙이고, 각 PR은 리뷰어가 15–30분 안에 볼 수 있는 크기를 목표로 합니다.

### PR 1 — 특성 테스트 추가 (코드 변경 없음)
- **무엇을**: 위 안전망 섹션의 테스트/스냅샷만 추가. 프로덕션 코드는 건드리지 않습니다.
- **파일**: 새 테스트 파일만. [ASSUMPTION: 테스트 프레임워크가 이미 설정돼 있음. 없다면 설정 자체가 새 의존성이 되므로 먼저 상의가 필요합니다.]
- **검증**: 테스트 명령 실행 → 새 테스트 전부 통과, 기존 결과 변화 없음.
- **크기**: 작음~중간 (테스트 코드만)
- **롤백**: 테스트 파일 삭제 또는 PR revert. 프로덕션 영향 없음.
- **배포 전 머지해도 안전합니다.** 이번 주에 가장 확실하게 할 수 있는 일입니다.

### PR 2 — 기계적 정리 (포맷, 사용하지 않는 코드 제거)
- **무엇을**: 포매터 적용, 명백히 호출되지 않는 코드 삭제, import 정리. 로직 변경 없음.
- **파일**: PR 1에서 테스트로 고정한 모듈만.
- **확인할 것**: "사용하지 않는" 코드가 리플렉션, 동적 호출, 설정 파일, 외부 서비스에서 참조되지 않는지 검색해서 확인하세요. 확신이 없으면 삭제하지 말고 남깁니다.
- **검증**: 빌드 성공, 특성 테스트 전부 통과, 스냅샷 diff 없음.
- **크기**: diff는 클 수 있지만 리뷰는 쉬움. 포맷 변경과 삭제는 **별도 커밋**으로 나눠 리뷰어가 구분할 수 있게 합니다.
- **롤백**: revert 한 번.

### PR 3 — 이름 바꾸기와 함수 추출 (한 모듈)
- **무엇을**: 긴 함수를 작은 함수로 추출, 의미 없는 변수명 변경. 공개 API(외부에서 호출되는 함수 이름·시그니처)는 **바꾸지 않습니다.**
- **파일**: 한 번에 한 모듈.
- **확인할 것**: 바꾸려는 이름이 외부(다른 서비스, 설정, 직렬화된 필드명, 로그 파싱)에서 참조되는지 확인하세요.
- **검증**: 빌드, 특성 테스트, 스냅샷 비교.
- **크기**: 작음 (모듈 하나)
- **롤백**: revert 한 번.

### PR 4 이후 — 모듈 단위로 반복 (배포 후 권장)
- PR 1 → 3의 패턴을 다음 모듈에 반복합니다: **테스트로 고정 → 기계적 정리 → 구조 정리.**
- 구조를 크게 바꿔야 하는 부분(클래스 분리, 레이어 재구성)은 새 구조를 옆에 만들고 호출부를 하나씩 옮기는 방식(Strangler 패턴)으로 진행해, 언제든 중간에 멈출 수 있게 합니다.

**일정 제안**
- 다음 주 배포 전: **PR 1만**, 여유가 있으면 PR 2까지. 둘 다 동작 변경 위험이 매우 낮습니다.
- 배포 후: PR 3부터 모듈 단위로 진행.
- 배포에 포함할 기능 작업이 같은 코드에서 진행 중이라면, 그 파일은 배포가 끝날 때까지 리팩터링 대상에서 빼세요. 충돌과 리뷰 혼선을 막을 수 있습니다.

## 3. 리스크

| 리스크 | 어떻게 드러나나 | 잡아내는 방법 |
|---|---|---|
| 테스트가 숨은 동작을 커버하지 못함 | 배포 후 특정 입력에서만 결과가 달라짐 | 특성 테스트를 실제 운영 입력(로그, 샘플 데이터)으로 만들기; 엣지 케이스(빈 값, null, 대용량) 포함 |
| "안 쓰는 코드" 삭제가 실제로는 쓰이던 코드 | 런타임 에러, 특정 기능만 동작 안 함 | 삭제 전 전체 코드베이스·설정·외부 참조 검색; 확신 없으면 남김 |
| 공개 API나 출력 포맷이 미묘하게 바뀜 | 다른 서비스·클라이언트 오류, 파싱 실패 | 진입점 기준 스냅샷 테스트로 출력 전체를 바이트 단위 비교 |
| 배포 작업과 리팩터링 충돌 | 머지 충돌, 잘못된 충돌 해결로 인한 버그 | 배포 대상 파일은 배포 후로 미룸; PR을 작게 유지해 빨리 머지 |
| 리뷰어가 큰 diff를 제대로 못 봄 | "LGTM"만 달리고 버그 통과 | PR당 모듈 하나, 포맷 변경과 로직 정리는 별도 커밋/PR |
| 배포 직전 리팩터링으로 인한 장애 | 배포 후 원인 파악 어려움 | 배포 전에는 테스트 추가와 기계적 정리만 머지 |
