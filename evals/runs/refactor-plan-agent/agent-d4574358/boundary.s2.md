먼저 솔직하게 말씀드리면, **테스트가 거의 없는 레거시 코드를 다음 주 배포 전에 한 번에 갈아엎는 것은 매우 위험합니다.**

- 테스트가 없으면 "동작이 그대로인지"를 증명할 수단이 없습니다. 리팩터링 후 버그가 생겨도 배포 후 사용자에게서 처음 발견될 가능성이 큽니다.
- 한 번에 바꾸면 diff가 너무 커서 리뷰가 사실상 불가능하고, 문제가 생겼을 때 어느 변경이 원인인지 찾기 어렵습니다.
- 배포 직전에 대규모 변경을 넣으면 롤백 단위가 "전부 아니면 전무"가 됩니다. 배포 일정 자체가 흔들릴 수 있습니다.

그래서 **"전부 갈아엎기" 대신, 다음 주 배포 전에는 안전망을 깔고 가장 아픈 한두 곳만 작게 정리하는 것**을 제안드립니다. 나머지는 배포 후에 같은 방식으로 이어가면 됩니다.

## 먼저 확인하고 싶은 것 (가장 중요한 순서)

1. **어떤 코드인가요?** 언어/프레임워크, 대략적인 규모, 그리고 "가장 지저분해서 제일 먼저 손대고 싶은" 파일이나 모듈 1~2개를 알려주세요.
2. **다음 주 배포에 이 리팩터링이 꼭 포함되어야 하나요?** 배포할 기능이 따로 있고 리팩터링은 "하고 싶은 것"이라면, 배포 브랜치와 분리하는 것이 가장 안전합니다.
3. **지금 동작을 확인하는 방법이 있나요?** 기존 테스트 실행 명령, CI, 수동 QA 절차, 스테이징 환경 등 무엇이든 좋습니다.

아래는 이 정보 없이 세울 수 있는 **잠정 계획**입니다. 파일명·명령어는 실제 코드를 보지 못했기 때문에 자리표시자로 두었습니다.

## 1. 안전망 먼저 (어떤 코드도 바꾸기 전에)

- **특성 테스트(characterization test) 추가**: 리팩터링 대상 모듈의 현재 입력 → 출력을 "맞다/틀리다" 판단 없이 그대로 기록하는 테스트를 만듭니다. 현재 버그처럼 보이는 동작도 그대로 고정합니다.
  - 순수 함수: 대표 입력 몇 개와 경계값(빈 값, null, 큰 값)에 대한 출력 스냅샷
  - API/화면: 주요 엔드포인트 응답이나 렌더 결과 스냅샷 (golden file)
  - [ASSUMPTION] 사용 중인 언어에 테스트 러너가 있다고 가정합니다. 없다면 이것을 설치하는 것이 첫 PR이며, 이는 개발 의존성 추가이므로 팀 합의가 필요합니다.
- **동작 동일성을 증명하는 명령** (예시, 실제 명령으로 바꿔야 함):
  - `<테스트 명령>` → 추가한 특성 테스트 전부 통과
  - `<빌드/린트 명령>` → 에러 0
  - 리팩터링 전 브랜치에서 스냅샷을 생성하고, 각 PR마다 같은 스냅샷이 diff 없이 통과하는지 확인
- 이 단계만으로도 다음 주 배포에 가치가 있습니다. 배포할 기능 자체의 회귀도 잡아주기 때문입니다.

## 2. 단계별 계획 (PR 하나당 한 단계)

**PR 1 — 특성 테스트 추가 (코드 변경 없음)**
- 변경: 테스트 파일만 추가. 프로덕션 코드는 건드리지 않음
- 파일: `<대상 모듈>`에 대응하는 테스트 파일
- 검증: `<테스트 명령>` 통과, 프로덕션 코드 diff 0줄
- 크기: 작음 (테스트 파일만)
- 롤백: 테스트 파일 삭제. 배포에 영향 없음

**PR 2 — 기계적 정리 (이름 변경, 포매팅, 죽은 코드 제거)**
- 변경: 변수/함수 이름 정리, 포매터 적용, 호출처가 전혀 없는 코드 삭제
- 파일: PR 1에서 테스트로 덮은 모듈만
- 검증: `<테스트 명령>` 통과, 스냅샷 diff 없음. 죽은 코드 삭제 전에는 전체 코드베이스에서 해당 이름을 검색해 호출처가 없는지 확인 (리플렉션·동적 호출·외부 사용처도 확인 필요)
- 크기: 작음~중간. 포매팅은 별도 PR로 분리하면 리뷰가 쉬워집니다
- 롤백: `git revert` 한 번

**PR 3 — 가장 복잡한 함수 하나를 작은 함수로 추출**
- 변경: 긴 함수에서 한 덩어리씩 함수로 추출 (extract function). 로직 변경 없음
- 파일: 대상 함수가 있는 파일 1~2개
- 검증: `<테스트 명령>` 통과, 스냅샷 diff 없음, 공개 함수 시그니처 불변
- 크기: 작음 (200줄 이하 diff 목표)
- 롤백: `git revert` 한 번

**배포 전 멈춤 지점**: 다음 주 배포 전에는 여기까지만 권장합니다. PR 3까지는 배포 브랜치에 넣지 않고 배포 후 머지하는 것도 좋은 선택입니다.

**배포 이후** — 같은 패턴(테스트로 덮기 → 기계적 정리 → 추출/분리)을 모듈 하나씩 반복합니다. 구체적인 단계는 코드를 보고 나서 정해야 합니다.

## 3. 위험 요소

| 위험 | 어떻게 드러나나 | 잡아내는 검사 |
|---|---|---|
| 특성 테스트가 실제 사용 경로를 덮지 못함 | 테스트는 통과하는데 운영에서 오류 | 커버리지 리포트로 변경 대상 라인이 테스트되는지 확인. 덮이지 않은 코드는 리팩터링 대상에서 제외 |
| "죽은 코드"가 실제로는 동적으로 호출됨 | 특정 경로에서 런타임 에러 | 삭제 전 전체 검색 + 로그/모니터링에서 호출 흔적 확인 |
| 배포 브랜치와 리팩터링 브랜치 충돌 | 머지 충돌, 배포 지연 | 리팩터링 PR은 작게 유지하고 자주 머지. 배포 동결 기간에는 리팩터링 머지 중단 |
| 리팩터링 중 "하는 김에" 버그 수정이 섞임 | 스냅샷 diff 발생 | 스냅샷이 바뀌는 PR은 리팩터링 PR로 머지하지 않음. 버그 수정은 별도 PR |
| 공개 API/외부 호출자가 깨짐 | 다른 서비스나 모듈에서 오류 | 공개 함수·엔드포인트 시그니처 변경 금지. 변경이 필요하면 별도 계획으로 분리 |
