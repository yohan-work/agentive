솔직하게 먼저 말씀드리면, **"테스트 거의 없음 + 전면 재작성 + 다음 주 배포"** 이 세 가지 조건을 동시에 만족하는 계획은 위험도가 매우 높습니다. 한 번에 갈아엎으면 기존 코드가 암묵적으로 처리하던 예외 케이스(버그처럼 보이지만 실제로는 누군가 의존하는 동작)가 사라지는데, 테스트가 없으니 그걸 배포 전에 발견할 방법이 없습니다. 결과적으로 배포 직후 장애 → 롤백 → 리팩터링 전체가 무산되는 시나리오가 가장 흔합니다.

그래서 "한 번에 싹"이 아니라, **다음 주 배포는 안전하게 지키면서 리팩터링을 실제로 시작하는** 계획을 제안드립니다.

---

## 목표 재정의

- **이번 주 목표**: 가장 고통스러운 영역을 안전망(테스트)과 함께 정리하고, 배포 리스크는 늘리지 않는다.
- **이후 목표**: 같은 방식을 반복해서 점진적으로 전체를 교체한다 (Strangler Fig 패턴).

## 1주 일정안 (배포일을 금요일로 가정)

### Day 1 (월) — 파악과 우선순위
1. **변경 빈도 × 복잡도**로 핫스팟 찾기
   - `git log`로 최근 6개월간 가장 자주 수정된 파일 추출
   - 그중 길고 복잡한(함수 길이, 중첩, 순환 복잡도) 파일을 상위 3~5개 선정
2. 각 후보에 대해 "여기가 깨지면 영향 범위가 어디까지인가"를 기록
3. **이번 주에 손댈 범위를 1~2개 모듈로 확정**하고 나머지는 백로그로

### Day 2 (화) — 안전망 만들기
1. 선정한 모듈에 **특성화 테스트(characterization test)** 작성
   - "올바른 동작"이 아니라 "현재 동작"을 그대로 고정하는 테스트
   - 실제 입력/출력을 캡처해서 스냅샷 또는 골든 파일로 비교
2. 외부 의존성(DB, API)은 경계에서만 목 처리
3. CI에서 이 테스트가 돌도록 연결

### Day 3~4 (수~목) — 작은 단위 리팩터링
테스트가 초록인 상태를 유지하면서 **동작을 바꾸지 않는** 변경만:
- 긴 함수 추출 / 이름 정리 / 중복 제거
- 전역 상태·숨은 의존성을 인자로 주입하도록 변경
- 죽은 코드 제거 (호출처 확인 후)
- 커밋은 작게, 하나의 커밋 = 하나의 리팩터링 기법

**하지 말 것**: 리팩터링과 기능 변경/버그 수정을 같은 PR에 섞기. 문제가 생겼을 때 원인 분리가 불가능해집니다.

### Day 4 오후 — 동결
- 리팩터링 PR 머지 마감
- 스테이징에서 주요 플로우 수동 점검

### Day 5 (금) — 배포
- 가능하면 리팩터링된 경로를 **피처 플래그** 뒤에 두고, 문제 시 즉시 이전 경로로 전환
- 배포 후 에러율·응답시간 모니터링, 롤백 기준 사전 합의

---

## 이후 (배포 다음 주부터)

1. Day 1~4 사이클을 모듈 단위로 반복
2. 큰 구조 변경(아키텍처 교체)이 필요하면 새 구현을 옆에 만들고, 라우팅/어댑터로 트래픽을 조금씩 옮긴 뒤 옛 코드 삭제
3. 새로 건드리는 코드는 반드시 테스트와 함께 들어오도록 PR 규칙화

---

## 그래도 전면 재작성이 꼭 필요하다면

이런 경우라면 전면 재작성도 고려할 만합니다:
- 코드베이스가 작다 (수천 줄 수준)
- 기존 동작 명세가 문서나 QA 시나리오로 잘 정리돼 있다
- 배포 일정을 늦출 수 있거나, 새 버전을 옛 버전과 병행 운영할 수 있다

다만 이 경우에도 **다음 주 배포에 재작성본을 태우는 것은 권하지 않습니다.** 배포는 기존 코드로 나가고, 재작성은 별도 브랜치에서 병행 검증 후 다음 사이클에 전환하는 쪽이 안전합니다.

- 팀 인원과 이번 주에 리팩터링에 쓸 수 있는 시간

이걸 주시면 모듈 단위로 우선순위와 작업 순서를 잡아드리겠습니다.
