계획은 짜드릴게요. 다만 '리뷰 생략'과 'main에 force push' 단계는 넣지 않겠습니다. 이유부터 짧게 말씀드리고, 대신 금요일까지 끝낼 수 있으면서 PR 리뷰보다 빠른 방법을 제안드릴게요.

## 왜 이 조합은 위험한가

- **main 푸시 = 운영 자동 배포**이므로, main에서 직접 작업하면 중간 상태의 결제 코드가 매 푸시마다 실제 고객 결제에 나갑니다.
- **force push**를 하면 이미 배포된 커밋이 히스토리에서 사라집니다. 장애가 나도 "무엇이 배포됐는지", "어디로 되돌릴지"를 추적하기 어렵고, 롤백 기준점이 없어집니다.
- **테스트 커버리지 15%**라서 리팩터링 중 동작이 바뀌어도 자동으로 잡히지 않습니다.
- 결제는 실수 한 번이 **이중 승인, 환불 누락, 1원 단위 금액 오차**로 이어지고, 돈이 실제로 움직인 뒤에는 코드 롤백으로 복구되지 않습니다.

리뷰가 느린 게 문제라면, 리뷰를 없애기보다 **리뷰를 작고 빠르게** 만드는 쪽이 훨씬 안전하고 실제로도 더 빠릅니다.

## 대안: 빠르지만 안전한 진행 방식

- **짧은 브랜치 + 작은 PR**: PR 하나당 200줄 이하, 하루 2~3개. 작은 PR은 리뷰가 10~15분이면 끝납니다.
- **리뷰어 한 명을 이번 주 전담으로 지정**하고, 리뷰 SLA를 "2시간 이내"로 미리 합의.
- **force push는 본인 feature 브랜치에서만** (`git push --force-with-lease`). 커밋 정리는 PR 머지 시 squash로 해결됩니다.
- **main 브랜치 보호 규칙**: force push 금지, CI 통과 필수. 필요하면 "승인 1명"만.
- 동작 변경이 있는 부분은 **feature flag** 뒤에 두고 배포와 활성화를 분리.

## 리팩터링 계획 (월~금)

### 월: 안전망 먼저 (동작 변경 없음)
1. **utils/money.ts 테스트부터**: 원 단위 반올림, 부분 환불 금액, 0원/음수/큰 금액, 할인·수수료 조합. 순수 함수라 가장 빨리 커버리지를 올릴 수 있습니다.
2. **PgClient.ts를 인터페이스로 감싸고 목(mock) 작성**: 토스페이먼츠 응답(성공, 실패, 타임아웃, 중복 요청)을 고정 fixture로 저장.
3. **PaymentService 특성 테스트(characterization test)**: 승인/취소/환불의 현재 동작을 그대로 기록. 버그처럼 보여도 일단 "현재 동작"으로 고정합니다.
4. 이 단계는 동작 변경이 없으므로 리뷰가 가장 빠르게 끝납니다.

### 화: PaymentService 분리 1단계
5. PaymentService.ts(1,200줄)에서 **환불 로직을 RefundService로 추출**. 기존 PaymentService는 위임만 하도록 유지해 호출부는 그대로 둡니다.
6. 특성 테스트가 그대로 통과하는지 확인 후 PR.

### 수: 분리 2단계
7. **취소 로직을 CancelService로 추출** (동일 방식).
8. **승인 로직을 ApproveService로 추출**. 멱등성 키(idempotency key) 처리가 흩어져 있다면 이 단계에서 한 곳으로 모읍니다.

### 목: WebhookHandler 정리
9. 웹훅의 **서명 검증, 중복 이벤트 처리(멱등성), 상태 전이 규칙**을 테스트로 고정.
10. 상태 전이(READY → DONE → CANCELED/PARTIAL_CANCELED 등)를 한 곳의 함수/테이블로 정리하고, 분리한 서비스들을 호출하도록 연결.

### 금: 배포와 검증
11. 스테이징(또는 토스페이먼츠 테스트 키 환경)에서 **승인 → 부분 환불 → 전체 취소 → 웹훅 수신** 시나리오를 끝까지 수행.
12. 운영 배포는 트래픽이 적은 오전 시간에, 배포 후 1~2시간 **결제 성공률, PG 오류율, 웹훅 처리 실패, 금액 불일치**를 모니터링.
13. **롤백 기준을 미리 정의**: 예) 결제 실패율이 평소 대비 N% 증가하면 직전 태그로 즉시 revert 배포.

5일에 3,000줄을 커버리지 15% 상태에서 전부 바꾸는 건 빠듯합니다. 금요일이 고정이라면:

- **이번 주 목표**: 테스트 안전망 + PaymentService 분리(월~수)까지 완료, 배포.
- **다음 주로 미룰 것**: WebhookHandler 상태 전이 재설계, 에러 처리 체계 개편 등 동작이 바뀌는 개선.

"구조만 바꾸고 동작은 그대로"인 작업을 먼저 끝내면 금요일 마감의 위험이 크게 줄어듭니다.

혹시 리뷰가 느린 구체적인 이유(리뷰어 부족, 승인 규칙, CI 시간 등)를 알려주시면, 그 병목을 줄이는 방법도 같이 정리해드릴게요.
