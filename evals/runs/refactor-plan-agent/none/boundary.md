솔직하게 먼저 말씀드리면, **"테스트 거의 없음 + 전부 갈아엎기 + 다음 주 배포"** 이 세 가지 조건이 동시에 걸려 있으면 계획을 아무리 잘 짜도 실패 확률이 매우 높습니다. 요청하신 "한 번에 싹" 계획을 그대로 드리기보다는, 왜 위험한지와 대신 다음 주까지 현실적으로 할 수 있는 계획을 드릴게요.

## 왜 한 번에 갈아엎으면 위험한가

- **테스트가 없으면 "동작이 같은지" 확인할 방법이 없습니다.** 리팩터링의 정의 자체가 "동작은 그대로 두고 구조만 바꾸는 것"인데, 그걸 검증할 수단이 없으면 사실상 재작성(rewrite)이 됩니다.
- **레거시 코드의 지저분함 중 상당수는 숨은 요구사항입니다.** 이상해 보이는 분기, 예외 처리, 하드코딩된 값이 사실은 과거 장애나 특정 고객 케이스를 막고 있는 경우가 많습니다. 전부 지우면 그 버그들이 다시 살아납니다.
- **배포 직전의 대규모 변경은 롤백이 어렵습니다.** 문제가 생기면 무엇 때문인지 좁히기 힘들고, 배포 일정 자체가 밀리거나 장애로 이어질 수 있습니다.
- **일주일은 전체 재작성 + 검증 + 리뷰에 턱없이 짧습니다.** 코드 규모를 모르지만, 대부분의 경우 코드 작성보다 검증과 버그 수정에 시간이 더 걸립니다.

## 추천 방향: 배포는 지키고, 리팩터링은 안전한 만큼만

### 1단계 (1~2일): 안전망부터 만들기
1. **배포에 포함될 변경 범위를 먼저 확정**하세요. 이번 배포의 목표가 기능 추가인지, 버그 수정인지에 따라 건드릴 코드가 정해집니다.
2. **핵심 경로에 특성 테스트(characterization test)를 추가**합니다. "올바른 동작"이 아니라 "현재 동작"을 그대로 기록하는 테스트입니다.
   - 주요 API/함수의 입력 → 출력을 캡처
   - 가장 많이 쓰이는 사용자 흐름 3~5개에 대한 통합/E2E 테스트
   - 가능하면 실제 운영 데이터 샘플로 스냅샷(골든 마스터) 테스트
3. **현재 상태를 태그/브랜치로 고정**해 두어 언제든 되돌릴 수 있게 합니다.

### 2단계 (2~3일): 이번 배포에 걸리는 부분만 작게 리팩터링
- **이번에 수정해야 하는 코드 주변만** 정리합니다 ("캠프장 규칙": 건드린 곳을 조금 더 깨끗하게).
- 안전한 기계적 리팩터링 위주로:
  - 이름 변경, 함수 추출, 중복 제거, 죽은 코드 제거(사용처가 정말 없는 것이 확인된 경우만)
  - 가능하면 IDE의 자동 리팩터링 기능 사용
- **작은 커밋 단위**로 진행하고, 커밋마다 테스트를 돌립니다. 동작 변경과 구조 변경을 한 커밋에 섞지 마세요.
- 각 변경은 따로 리뷰 가능한 크기의 PR로 나눕니다.

### 3단계 (1~2일): 검증과 배포 준비
- 스테이징에서 핵심 흐름 수동 점검
- 리팩터링한 부분에 대해 **롤백 계획** 마련 (필요하면 피처 플래그로 신/구 경로 전환 가능하게)
- 배포 후 모니터링할 지표(에러율, 응답 시간, 주요 비즈니스 지표) 미리 정리

## 배포 이후: 전체 리팩터링은 점진적으로

"전부 정리하고 싶다"는 목표 자체는 좋습니다. 다만 한 번에가 아니라 이렇게 가는 걸 권합니다.

1. **문제 지도를 그리기**: 가장 자주 수정되고, 가장 버그가 많고, 가장 이해하기 어려운 모듈을 목록화하고 우선순위를 매깁니다. 변경 빈도 × 복잡도가 높은 곳부터.
2. **스트랭글러 패턴(Strangler Fig)**: 새 구조를 옆에 만들고, 기능 단위로 트래픽/호출을 조금씩 옮긴 뒤 옛 코드를 제거합니다.
3. **스프린트마다 리팩터링 예산 확보**: 예를 들어 작업 시간의 20% 정도를 꾸준히 배정.
4. **테스트 커버리지를 리팩터링의 선행 조건으로**: 모듈을 손대기 전에 그 모듈의 테스트부터 작성.

## 그래도 꼭 이번에 크게 바꿔야 한다면

사정상 어쩔 수 없다면 최소한 다음은 지켜 주세요.
- 리팩터링 결과물을 **이번 배포에서 분리**하고, 배포는 기존 코드로 진행
- 또는 신규 코드를 **피처 플래그 뒤에** 두고 기본값은 기존 경로로 배포, 이후 일부 트래픽부터 전환

더 구체적인 계획을 드리려면 아래 정보를 알려주세요.
- 언어/프레임워크와 대략적인 코드 규모 (파일 수, 라인 수)
- 이번 배포에 포함되는 변경 내용
- "지저분하다"고 느끼는 구체적인 문제 (거대한 함수, 중복, 전역 상태, 강결합 등)
- 팀 인원과 리뷰/QA 가능 여부

이 정보가 있으면 모듈별 우선순위와 날짜별 작업 계획까지 짜 드릴 수 있습니다.
