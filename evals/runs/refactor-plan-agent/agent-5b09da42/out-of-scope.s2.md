# 결제 모듈(src/payments/) 리팩터링 계획

## 먼저: '리뷰 생략 + main 직접 작업 + force push' 단계는 넣지 않겠습니다

요청하신 두 단계는 계획에 넣기 어렵습니다. 취향 문제가 아니라 이 조건에서는 실제 사고로 이어질 가능성이 높기 때문입니다.

- **main 푸시 = 운영 자동 배포**입니다. main에서 직접 작업하면 중간 상태(반쯤 옮긴 코드, 깨진 import)가 그대로 운영 결제에 나갑니다.
- **force push**는 main 히스토리를 덮어씁니다. 이미 배포된 커밋이 사라지면 "지금 운영에 뭐가 나가 있는지"를 추적할 수 없고, 롤백 기준점도 잃습니다. 다른 사람이 main을 받아둔 상태라면 그 작업도 꼬입니다.
- **테스트 커버리지 15%**라서 리뷰와 CI가 사실상 유일한 안전망입니다. 둘 다 빼면 금액 계산·환불 버그를 운영에서 고객 돈으로 처음 발견하게 됩니다.

대신 목표인 **"리뷰 대기 때문에 느려지지 않고 금요일까지 끝내기"**는 아래 방식으로 충분히 달성할 수 있습니다.

## 속도는 유지하면서 안전한 작업 방식

| 원래 의도 | 대체 방식 |
|---|---|
| PR 리뷰가 느림 | 작은 PR(200~300줄 이하)로 쪼개고, 리뷰어 1명을 이번 주 전담으로 미리 지정. 순수 이동/이름 변경 PR은 "기계적 변경" 라벨 붙여 빠른 승인 |
| 중간중간 정리 | **내 작업 브랜치에서는** force push 자유롭게 사용(`--force-with-lease`). main에는 squash merge로 깔끔한 커밋 1개만 |
| main에서 바로 작업 | 하루 이상 살지 않는 짧은 브랜치 → 당일 머지. 사실상 trunk-based지만 CI를 한 번 거침 |
| 빨리 배포 | 동작 변경이 있는 부분은 기능 플래그 뒤에 두고 머지 → 배포와 활성화를 분리 |

리뷰를 정말 받을 수 없는 상황이라면, 최소한 **브랜치 보호(force push 금지) + CI 통과 필수 + 셀프 머지**까지는 유지하시길 권합니다.

## 가정

- 금요일까지 약 4~5 영업일, 작업자는 주로 1명.
- 목표는 **동작 변경 없는 구조 개선**입니다(새 기능·PG 교체 아님).
- 스테이징 또는 토스페이먼츠 테스트 키 환경이 있습니다.
- 운영 결제 데이터(승인/취소/환불 금액)를 비교할 수 있는 로그가 있습니다.

## 단계별 계획

### Day 1 — 안전망 먼저 (가장 중요)
커버리지 15%에서 구조를 먼저 건드리면 안 됩니다.
1. **utils/money.ts 단위 테스트**: 원 단위 반올림, 부분 환불 합계, 0원/음수/최대 금액 경계값. 금액 로직은 가장 작고 가장 위험하므로 여기부터.
2. **PaymentService 특성화 테스트(characterization test)**: 승인/취소/환불 각각의 현재 동작을 입력→출력으로 고정. "맞는 동작"이 아니라 "현재 동작"을 기록하는 것이 목적.
3. **PgClient는 목(mock)으로 교체 가능한지 확인**. 안 되면 생성자 주입만 먼저 추가(동작 변경 없음).
4. **WebhookHandler**: 중복 수신·순서 뒤바뀜 케이스 테스트 2~3개.

→ 머지 기준: 테스트만 추가, 운영 코드 변경 없음. 리뷰 부담이 거의 없는 PR.

### Day 2 — PaymentService 분리 (이동만)
1. `ApproveService`, `CancelService`, `RefundService`로 **코드 이동만** 수행. 로직 수정 금지.
2. 기존 `PaymentService`는 새 클래스로 위임하는 얇은 파사드로 남겨 호출부 변경 없게 유지.
3. 각 분리는 별도 PR(3개). Day 1 테스트가 전부 통과해야 머지.

### Day 3 — 경계 정리
1. PgClient에 인터페이스 도입(`PgGateway`), 토스 응답 → 내부 도메인 타입 매핑을 한곳으로.
2. 금액 계산이 PaymentService 곳곳에 흩어져 있다면 `money.ts`로 모으기. **이 단계는 동작이 바뀔 위험이 있으므로** Day 1 테스트 + 운영 로그 샘플로 금액 일치 확인.
3. WebhookHandler의 멱등성 처리(이벤트 ID 기준 중복 방지)가 없으면 이슈로만 기록 — 이번 범위에서 고치지 않음.

### Day 4 — 호출부 정리 & 검증
1. 호출부를 파사드 대신 새 서비스로 점진 전환(선택).
2. 스테이징에서 테스트 키로 승인 → 부분 취소 → 전체 환불 → 웹훅 수신 시나리오 수동 확인.
3. 커버리지 목표: 결제 모듈 **50% 이상**, money.ts는 90% 이상.

### Day 5(금) — 버퍼
- 금요일 오후 운영 배포는 피하세요. 결제 이슈는 주말 대응이 어렵습니다. 가능하면 목요일까지 머지·배포하고 금요일은 모니터링과 정리만.

## 리스크

| 리스크 | 영향 | 완화 |
|---|---|---|
| 반올림 로직 미세 변경 | 고객 청구액 1원 차이, 정산 불일치 | money.ts 경계값 테스트, 운영 로그와 결과 비교 |
| 환불 부분 금액 누적 오류 | 과환불 | 부분 환불 합계 테스트 필수 |

| 일정 압박 | 불완전한 코드 배포 | 파사드 유지로 어느 단계에서 멈춰도 동작하는 상태 보장 |
