# 리팩터링 계획: "한 번에 싹 갈아엎기" 대신 "배포는 지키고, 안전하게 줄여 나가기"

## 먼저 솔직한 판단

요청하신 조건 세 가지를 같이 놓으면 위험도가 매우 높습니다.

| 조건 | 의미 |
|---|---|
| 레거시 전체를 리팩터링 | 변경 범위가 최대 |
| 테스트가 거의 없음 | 동작이 바뀌어도 알아챌 방법이 없음 |
| 다음 주 배포 전 완료 | 검증·롤백 여유가 거의 없음 |

이 상태에서 빅뱅 방식으로 전부 갈아엎고 다음 주에 배포하면, "코드는 깨끗해졌는데 무엇이 깨졌는지 모르는" 상황이 될 가능성이 큽니다. 리팩터링의 정의가 "동작은 그대로, 구조만 개선"인데, 테스트가 없으면 "동작이 그대로"임을 보장할 수 없습니다.

그래서 추천은 다음과 같습니다.

- **다음 주 배포에는 전면 리팩터링을 포함하지 않는다.** 배포 대상 기능은 현재 코드 기준으로 안정적으로 나간다.
- **이번 주는 "리팩터링을 안전하게 할 수 있는 기반"을 만드는 데 쓴다.** (특성화 테스트, 핫스팟 파악, 작은 저위험 정리)
- **본격적인 구조 개선은 배포 이후 점진적으로 진행한다.** (Strangler Fig 방식)

만약 반드시 이번 배포에 리팩터링 결과가 들어가야 하는 사정이 있다면(예: 배포 기능이 레거시 구조 때문에 구현 불가), 그 기능이 건드리는 모듈로 범위를 좁혀서 하는 게 유일하게 현실적인 선택지입니다.

---

## 가정

아래 내용은 정보가 없어서 가정했습니다. 다르면 알려주세요.

1. 운영 중인 서비스이고, 다음 주 배포는 기능/수정 배포이다.
2. 팀 규모는 1~3명 정도이며, 리팩터링 전담 인력은 없다.
3. CI는 있거나 간단히 만들 수 있다.
4. 롤백(이전 버전 재배포)이 가능한 배포 구조다.

## 실행 계획

### 이번 주 (배포 전, 약 4~5일)

**Day 1: 현황 파악 (반나절~1일)**
- 변경이 잦고 버그가 많은 파일 찾기: `git log` 기반 변경 빈도 × 파일 크기/복잡도로 상위 10개 정도의 핫스팟 목록 작성
- 다음 주 배포 기능이 건드리는 모듈 표시
- "건드리면 안 되는 곳"(결제, 인증, 데이터 마이그레이션 등) 명시

**Day 2~3: 안전망 만들기**
- 핫스팟 + 배포 대상 모듈에 **특성화 테스트(characterization test)** 작성
  - "올바른 동작"이 아니라 "현재 동작"을 그대로 기록하는 테스트
  - API 레벨이면 주요 엔드포인트의 요청/응답 스냅샷, 함수 레벨이면 대표 입력값에 대한 출력 고정
- 핵심 사용자 흐름 3~5개에 대한 스모크 테스트(수동 체크리스트라도 OK)
- CI에서 테스트가 자동으로 돌도록 연결

**Day 3~4: 저위험 정리만 수행 (선택)**
- 동작 변화가 없는 기계적 변경만:
  - 포매터/린터 적용 (별도 커밋으로 분리)
  - 죽은 코드 삭제 (사용처 없음이 확인된 것만)
  - 이름 변경, 명백한 중복 함수 추출
- 커밋은 작게, 기능 변경과 절대 섞지 않기

**Day 5: 배포 준비**
- 배포 기능을 현재 구조 기준으로 마무리
- 리팩터링 커밋이 섞였다면, 문제가 생겼을 때 그 커밋만 되돌릴 수 있는지 확인

### 배포 이후 (2~6주, 점진적)

- **Strangler Fig 패턴**: 새 구조를 옆에 만들고, 기능 단위로 하나씩 새 구조로 옮긴 뒤, 옛 코드 삭제
- 모듈 하나당 흐름: 특성화 테스트 보강 → 구조 변경 → 테스트 통과 확인 → 배포 → 1~2일 모니터링
- 핫스팟 목록 순서대로 진행 (변경 빈도 높고 버그 많은 곳부터)
- 새로 추가하는 기능은 새 구조에서만 작성하는 규칙을 둠 (레거시가 더 커지지 않도록)

## 리스크와 대응

| 리스크 | 가능성 | 대응 |
|---|---|---|
| 테스트 없이 바꾼 부분에서 회귀 버그 | 높음 | 특성화 테스트 먼저, 기계적 변경만 배포 전 수행 |
| 리팩터링 때문에 배포 일정 지연 | 높음 | 배포 기능과 리팩터링을 분리, 리팩터링은 언제든 빼낼 수 있게 작은 커밋 |
| 숨은 의존성(전역 상태, 리플렉션, 외부 시스템 연동) | 중간 | 핫스팟 분석 시 외부 호출·전역 변수 목록 작성 |
| 점진적 전환이 중간에 멈춰 두 구조 공존 | 중간 | 모듈 단위로 "완료" 기준 정하고, 옛 코드 삭제까지를 한 작업으로 정의 |
| 팀 내 합의 부족 | 낮음~중간 | 코드 스타일/구조 원칙을 1페이지로 정리해 공유 |

## 추천 요약

- **빅뱅 전면 리팩터링 + 다음 주 배포**는 권장하지 않습니다.
- 이번 주: 핫스팟 파악 → 특성화 테스트 → 동작 변화 없는 정리만.
- 배포 후: 모듈 단위 점진적 전환.

## 계획을 구체화하려면 필요한 정보

아래를 알려주시면 모듈별 순서와 일정까지 구체적으로 짜 드릴 수 있습니다.

1. **언어/프레임워크**와 대략적인 코드 규모 (파일 수 또는 LOC)
2. **다음 주 배포 내용**이 무엇이고, 레거시 코드 중 어디를 건드리는지
3. "지저분하다"의 구체적인 증상: 거대한 파일/함수, 중복, 전역 상태, 레이어 뒤섞임 등 중 어떤 것이 가장 고통스러운지
4. 리팩터링에 쓸 수 있는 인원과 시간
5. 이번 배포에 리팩터링이 **반드시** 포함되어야 하는 이유가 있는지 (있다면 그 범위만 집중 계획을 드리겠습니다)
