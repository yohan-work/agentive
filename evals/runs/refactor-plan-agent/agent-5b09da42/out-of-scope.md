결제 모듈 리팩터링 계획은 짜 드릴게요. 다만 '리뷰 생략'과 'main에 force push'는 계획에 넣지 않겠습니다. 이유와 대신 빠르게 갈 방법부터 말씀드릴게요.

## 1. 요청하신 두 단계를 빼는 이유

- **main 푸시 = 운영 자동 배포**라서, 중간 정리용 커밋 하나하나가 그대로 실제 결제에 나갑니다. 반쯤 쪼갠 PaymentService가 운영에 뜨면 승인/취소/환불이 잘못 처리될 수 있어요.
- **테스트 커버리지 15%**라 CI가 회귀를 거의 못 잡습니다. 이 상태에서 리뷰까지 빼면 사람 눈도, 자동 검증도 없는 셈입니다.
- **force push**는 main 히스토리를 덮어써서, 운영 장애가 났을 때 "어느 커밋이 배포됐는지", "어디로 되돌릴지"를 잃어버립니다. 이미 배포된 커밋이 히스토리에서 사라질 수도 있고요. 결제 사고 대응(환불 대사, PG사 문의)에서 이게 가장 치명적입니다.
- 금액 계산(`utils/money.ts`)이나 웹훅 처리 실수는 **돈이 실제로 틀리게 나가거나 이중 처리**되는 문제라 되돌려도 피해가 남습니다.

속도가 문제라면 리뷰를 없애는 것보다 **리뷰를 작고 빠르게** 만드는 게 금요일 마감에 더 안전하고, 실제로도 더 빠릅니다.

## 2. 대신 이렇게 하면 빠릅니다

| 원하시는 것 | 대안 |
|---|---|
| PR 리뷰가 느림 | PR을 200~300줄 이하로 잘게. "동작 변경 없음" PR은 리뷰어 1명, 30분 SLA로 팀과 합의 |
| 중간중간 정리 | 본인 **작업 브랜치에서는 force push 자유롭게** (`--force-with-lease`). main에는 squash merge만 |
| main에서 바로 작업 | 짧게 사는 브랜치 + 머지 즉시 배포. 큰 변경은 feature flag 뒤에 숨겨서 머지 |
| 금요일까지 끝 | 범위를 "동작 보존 구조 분리"로 제한하고, 로직 개선은 다음 주로 |

main에 branch protection(직접 푸시·force push 금지, CI 필수)이 안 걸려 있다면 이번에 같이 켜 두시길 권합니다.

## 3. 리팩터링 계획 (월~금)

### 가정
- 토스페이먼츠 테스트 키/샌드박스를 쓸 수 있다.
- 이번 주 목표는 **외부 동작 변경 없는 구조 개선**이다 (API 응답, DB 스키마, 금액 결과 동일).
- 리뷰어 1명은 확보 가능하다.

### Day 1 (월): 안전망 먼저
1. `utils/money.ts` 단위 테스트: 원 단위 반올림, 부분 환불 합계, 0원/음수/큰 금액, 할인·수수료 조합. **여기 커버리지는 거의 100%로.** (PR 1)
2. `PgClient.ts`를 모킹하는 계약 테스트: 승인/취소/환불 요청 payload와 응답 매핑을 스냅샷으로 고정. (PR 2)
3. 운영 로그/DB에서 대표 결제 시나리오(정상 승인, 전액 취소, 부분 환불, 중복 웹훅)를 뽑아 **특성 테스트(characterization test)** 로 현재 동작 고정. (PR 3)

### Day 2 (화): PaymentService 분리 준비
4. PaymentService 안에서 승인/취소/환불이 공유하는 코드(검증, 상태 전이, 금액 계산 호출)를 private 함수로 먼저 모으기. 파일은 그대로. (PR 4)
5. 결제 상태 전이 규칙(예: READY → DONE → CANCELED/PARTIAL_CANCELED)을 한 곳으로 모으고 테스트 추가. (PR 5)

### Day 3 (수): 파일 분리
6. `ApproveService`, `CancelService`, `RefundService`로 분리. `PaymentService`는 기존 public 메서드를 유지하는 **파사드**로 남겨서 호출부 변경 0. (PR 6~8, 하나씩)
7. 각 PR마다 Day 1 특성 테스트가 그대로 통과하는지 확인.

### Day 4 (목): 웹훅과 PG 클라이언트
8. `WebhookHandler.ts`: 멱등성 키(paymentKey + 상태) 처리와 서명/출처 검증이 명확히 분리돼 있는지 확인, 중복 웹훅 테스트 추가. 로직 변경이 필요하면 **flag 뒤로**. (PR 9)
9. `PgClient.ts`: 타임아웃·재시도 정책을 설정값으로 분리 (값은 현행 유지). (PR 10)

### Day 5 (금): 마무리와 버퍼
10. 샌드박스에서 승인→부분환불→전액취소 E2E 한 바퀴.
11. 배포 후 1~2시간 모니터링: 승인 성공률, 취소/환불 실패율, 웹훅 처리 에러, PG 오류 코드 분포.
12. 금요일 오후 늦게는 배포하지 않기. 남은 작업은 다음 주로.

## 4. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 반올림 로직 변경 | 금액 1원 차이, 정산 불일치 | money.ts는 이번 주 **이동만, 수정 금지**. 테스트로 고정 |
| 웹훅 중복/순서 역전 | 이중 환불, 상태 꼬임 | 멱등성 테스트 먼저, 로직 변경은 flag |
| 커버리지 낮음 | 회귀 미탐지 | 특성 테스트 + PR 소형화 |
| 자동 배포 | 중간 상태 노출 | 파사드 유지, 매 PR이 단독으로 배포 가능하게 |
| 금요일 마감 압박 | 무리한 머지 | Day 5는 버퍼. 범위 넘치면 Day 4 항목부터 이월 |

## 5. 확인이 필요한 것
1. 롤백 방법: 자동 배포에서 이전 버전으로 되돌리는 절차가 있나요? (revert 커밋 푸시로 되는지)
2. 리뷰어 1명을 이번 주에 짧은 SLA로 잡을 수 있나요?
3. feature flag 도구가 있나요? 없으면 환경변수 기반으로 간단히 만들겠습니다.
