요청하신 "다음 주 배포 전에 한 번에 싹 갈아엎는" 계획은 그대로 짜 드리기 어렵습니다. 테스트가 거의 없는 레거시를 일주일 안에 전면 재작성하면, 배포 직전에 기존 동작이 깨졌는지 확인할 방법이 없습니다. 그러면 버그가 배포에 그대로 실려 나갈 가능성이 매우 높습니다. 그래서 **이번 배포는 지키고, 전면 리팩터링은 배포 뒤에 단계적으로 진행하는 계획**을 제안드립니다. 결과적으로 "깨끗한 코드"라는 목표에는 이 방식이 더 빨리, 더 안전하게 도달합니다.

## 1. 먼저 여쭤볼 것 (계획을 구체화하는 데 꼭 필요한 정보)

1. **다음 주 배포에 무엇이 들어가나요?** 리팩터링 자체가 배포 목표인지, 아니면 신규 기능 배포가 있는데 그 전에 코드를 정리하고 싶으신 건지에 따라 계획이 크게 달라집니다.
2. **규모와 스택:** 대략적인 코드 규모(파일 수·라인 수), 언어·프레임워크, 모놀리스인지 서비스가 여러 개인지 알려 주세요.
3. **가장 괴로운 지점:** "지저분하다"는 게 구체적으로 무엇인가요? 거대한 파일·함수, 중복 코드, 뒤엉킨 의존성, 전역 상태, 이름 문제 가운데 어떤 건지, 또 어느 모듈에서 버그와 수정이 가장 잦은지 알려 주세요.
4. **투입 인원:** 이번 주에 리팩터링에 쓸 수 있는 인원과 시간은 어느 정도인가요?

아래 계획은 이 정보가 없다는 전제에서 쓴 일반안입니다. 답을 주시면 구체적인 모듈 단위 계획으로 바꿔 드리겠습니다.

## 2. 가정

- 다음 주 배포는 날짜가 고정되어 있고, 운영 중인 서비스에 나갑니다.
- 자동화 테스트가 거의 없고, 현재 동작을 문서화한 사양도 충분하지 않습니다.
- 코드는 현재 운영에서 "대체로 동작"하고 있고, 그 동작을 사용자가 기대하고 있습니다.
- 소수 인원(1~3명)이 기존 업무와 병행합니다.

## 3. 핵심 권고: 빅뱅 재작성 대신 "안전망 → 점진적 개선"

| 구분 | 한 번에 전면 재작성 | 단계적 리팩터링 (권장) |
|---|---|---|
| 회귀 버그 위험 | 매우 높음 (검증 수단 없음) | 낮음 (작은 단위로 검증) |
| 배포 일정 영향 | 일정 초과나 배포 연기 가능성 큼 | 배포는 그대로, 개선은 병행 |
| 롤백 | 사실상 불가능 | 변경 단위별로 가능 |
| 숨은 비즈니스 규칙 | 재작성하면서 유실되기 쉬움 | 테스트로 먼저 고정한 뒤 보존 |

레거시 코드의 "지저분함" 안에는 문서화되지 않은 예외 처리와 버그 수정이 섞여 있는 경우가 많습니다. 테스트 없이 갈아엎으면 이런 규칙이 조용히 사라집니다.

## 4. 실행 계획

### 0단계: 이번 주, 배포 전 (목표는 배포를 안전하게 내보내는 것)
- **코드 동결 수준 정하기:** 배포 브랜치에는 배포에 필요한 변경만 넣고, 대규모 구조 변경은 넣지 않습니다.
- **핵심 흐름 스모크 테스트 작성:** 로그인, 결제, 핵심 조회·저장처럼 매출과 사용자에 직결되는 흐름 3~5개를 E2E나 API 수준에서 자동화합니다. 이번 배포의 안전망이면서 리팩터링의 출발점이 됩니다.
- **부담 없는 정리만 허용:** 포매터와 린터 적용, 명백한 죽은 코드 삭제처럼 동작이 바뀌지 않는 변경만 넣습니다. 포매터 변경은 별도 커밋으로 분리합니다.
- **리팩터링 백로그 작성:** "지저분한 곳" 목록을 만들고, 각 항목을 변경 빈도 × 버그 빈도 × 비즈니스 중요도로 점수를 매깁니다.
- **롤백 절차 확인:** 이전 버전으로 되돌리는 방법을 배포 전에 한 번 리허설합니다.

### 1단계: 배포 후 1~2주 (안전망 구축)
- 우선순위 상위 모듈에 **특성 테스트(characterization test)**를 붙입니다. "올바른 동작"이 아니라 "현재 동작"을 그대로 기록하는 테스트입니다. 입출력 스냅샷이나 골든 파일 방식이 효율적입니다.
- CI에서 테스트, 린트, 빌드를 자동으로 실행하도록 설정합니다.
- 필요하면 에러 모니터링과 로그를 보강해 리팩터링 뒤 이상 징후를 빨리 잡을 수 있게 합니다.

### 2단계: 이후 스프린트마다 (점진적 리팩터링)
- **보이 스카우트 규칙:** 기능 작업으로 건드리는 파일은 조금씩 정리합니다.
- **작은 PR 원칙:** 리팩터링 PR과 기능 PR을 섞지 않고, PR 하나에는 한 종류의 구조 변경만 담습니다.
- **Strangler Fig 패턴:** 크게 갈아엎어야 하는 모듈은 새 구현을 옆에 만들고, 기능 플래그나 라우팅으로 트래픽을 조금씩 옮긴 뒤 기존 코드를 제거합니다.
- **주요 기법 순서:** 이름 정리 → 긴 함수 분리 → 중복 제거 → 의존성 분리(인터페이스·주입) → 모듈 경계 재설계 순서로 진행합니다. 위험이 낮은 것부터 합니다.

### 3단계: 마무리와 유지
- 테스트 커버리지와 핵심 모듈의 복잡도를 추적해 개선이 실제로 이루어지는지 확인합니다.
- 코딩 컨벤션과 아키텍처 원칙을 짧게 문서화해 다시 지저분해지는 것을 막습니다.

| 리스크 | 영향 | 대응 |
|---|---|---|
| 배포 전 구조 변경으로 회귀 버그 발생 | 운영 장애 | 배포 브랜치에는 구조 변경 금지, 스모크 테스트 필수 |
| 숨은 비즈니스 규칙 유실 | 조용한 데이터·로직 오류 | 특성 테스트로 현재 동작을 먼저 고정 |
| 리팩터링이 끝없이 길어짐 | 기능 개발 지연 | 백로그 우선순위와 스프린트당 시간 상한(예: 20%) 설정 |
| 대형 PR로 리뷰 품질 저하 | 버그가 리뷰를 통과 | PR 크기 제한, 구조 변경과 동작 변경 분리 |
| 팀 내 합의 부족 | 방향이 흔들림 | 목표 구조와 원칙을 짧게 합의한 뒤 시작 |
