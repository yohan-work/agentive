## 먼저 솔직하게

지금 주신 정보("사이트가 느리다")만으로는 **어디가 문제인지 특정할 수 없습니다.** 원인을 짐작해서 "여기를 고치세요"라고 드리면 엉뚱한 곳을 고치느라 시간을 쓰실 가능성이 큽니다. 그래서 아래 두 가지를 드립니다.

1. 진단에 꼭 필요한 정보 (이것만 주시면 실제 감사가 가능합니다)
2. 정보를 모으는 동안 직접 돌려볼 수 있는 10~15분짜리 1차 진단 절차

## 2. 지금 바로 해볼 수 있는 1차 진단 (약 15분)

### A. 느림이 "어디서" 발생하는지 가르기
Chrome에서 느린 페이지를 열고 DevTools(F12) → **Network** 탭 → "Disable cache" 체크 → 새로고침.

- **첫 번째 문서 요청(HTML)의 TTFB가 길다** (예: 1초 이상, "Waiting for server response")
  → **서버/백엔드 문제** 가능성이 높음 (느린 DB 쿼리, 외부 API 호출, 캐시 없음, 서버 리소스 부족)
- **HTML은 빨리 오는데 화면이 늦게 뜬다**
  → **프론트엔드 문제** (큰 JS 번들, 최적화 안 된 이미지, 렌더링 차단 CSS/폰트, 서드파티 스크립트)
- **특정 API 요청 하나가 유독 오래 걸린다** (Fetch/XHR 필터)
  → 그 **엔드포인트** 문제
- **화면은 떴는데 클릭/스크롤이 버벅인다**
  → **메인 스레드를 막는 JS** 문제 (Performance 탭에서 긴 작업(Long Task) 확인)

### B. Lighthouse 한 번 돌리기
DevTools → **Lighthouse** 탭 → Mobile, Performance만 선택 → 실행.
다음 값을 알려주세요:
- LCP (최대 콘텐츠 표시 시간), CLS, TBT (총 차단 시간)
- "Opportunities / Diagnostics"에 나온 상위 3~5개 항목

### C. 공개 사이트라면
PageSpeed Insights(pagespeed.web.dev)에 URL을 넣으면 **실제 사용자 데이터(CrUX)**도 볼 수 있습니다. 실사용자 수치와 실험실 수치가 크게 다르면 그것 자체가 단서입니다.

## 3. 흔한 원인 (확인 전까지는 가설일 뿐입니다)

결과를 받기 전 참고용으로, 실무에서 빈도가 높은 순서대로 적습니다. **이 목록을 바로 다 고치는 것은 권하지 않습니다.** 측정으로 확인된 항목부터 손대야 효과가 확실합니다.

| 영역 | 흔한 원인 | 신호 |
|------|-----------|------|
| 이미지 | 원본 크기 그대로 업로드, WebP/AVIF 미사용, lazy-loading 없음 | Network에서 수백 KB~수 MB 이미지 |
| JS | 거대한 번들, 쓰지 않는 라이브러리, 코드 스플리팅 없음 | JS 합계 1MB 이상, TBT 높음 |
| 서드파티 | 광고·분석·채팅 위젯 다수 | 외부 도메인 요청이 많고 느림 |
| 서버 | 느린 쿼리(N+1, 인덱스 누락), 캐시 부재 | TTFB 높음 |
| 전송 | 압축(gzip/brotli) 미적용, CDN 미사용, HTTP 캐시 헤더 없음 | 정적 파일 응답이 크고 매번 새로 받음 |
| 폰트/CSS | 렌더링 차단 리소스 | LCP 지연, 흰 화면 시간 길음 |

## 리스크

- **측정 없이 고치기:** 추측으로 여러 곳을 동시에 바꾸면 무엇이 효과가 있었는지 알 수 없고, 새로운 버그를 만들 수 있습니다.
- **개발자 PC 기준 판단:** 빠른 PC·네트워크에서는 문제가 안 보일 수 있습니다. Lighthouse Mobile 모드나 DevTools 네트워크 스로틀링(Fast 4G)으로 확인하세요.
- **한 번 측정:** 수치는 편차가 있으니 2~3회 측정해 중앙값을 보세요.
