디자인이 아직 없으니, 아래 스펙은 **가정 기반 초안**입니다. 먼저 한 가지를 짚고 가겠습니다.

> **"모든 화면에서 다 쓰는 만능 테이블"은 권장하지 않습니다.** 정렬·필터·편집·트리·가상 스크롤·드래그 등을 한 컴포넌트에 전부 넣으면 props가 수십 개로 늘어나고, 한 화면을 고치면 다른 화면이 깨지는 구조가 됩니다. 대신 **작은 코어 테이블 + 선택형 기능(opt-in) + 조합 가능한 하위 컴포넌트** 구조를 제안합니다. "모든 화면에서 쓸 수 있다"는 목표는 이 방식으로 더 안전하게 달성할 수 있습니다.

---

## 먼저 확인이 필요한 것 (필수 3가지)

아래 답에 따라 스펙 범위가 크게 달라집니다. 답을 주시면 초안을 확정본으로 다듬겠습니다.

1. **기술 스택**: React / Vue / 기타? 기존 디자인 시스템(MUI, Ant, shadcn 등)이나 테이블 라이브러리(TanStack Table 등)를 쓰나요, 직접 구현인가요?
2. **데이터 규모와 처리 위치**: 한 화면에 보통 몇 행인가요(수십 / 수천 / 수만)? 정렬·필터·페이지네이션을 **서버**에서 하나요, **클라이언트**에서 하나요?
3. **실제로 필요한 화면 목록**: 지금 테이블이 들어갈 화면 3~5개와, 각 화면에 필요한 기능(정렬, 선택, 인라인 편집 등)을 알려주세요. "모든 화면"의 실제 범위를 여기서 정합니다.

## 1. 목적과 범위

- **목적**: 여러 화면에서 반복되는 목록/표 UI를 일관된 동작과 접근성으로 제공.
- **범위 안 (v1)**: 데이터 표시, 컬럼 정의, 정렬, 페이지네이션, 행 선택, 로딩/빈/에러 상태, 반응형 기본 대응.
- **범위 밖 (v1에서는 제외, 필요 시 별도 확장)**: 인라인 편집, 트리/그룹 행, 컬럼 드래그 재정렬, 셀 병합, 엑셀형 스프레드시트 동작, 피벗.

## 2. 구조 (제안)

| 계층 | 역할 |
|---|---|
| `Table` (코어) | 순수 렌더링: 헤더, 행, 셀. 상태 없음에 가깝게 유지 |
| 기능 모듈 (opt-in) | 정렬, 선택, 페이지네이션, 컬럼 표시/숨김 등. 필요한 화면만 켬 |
| 상태 슬롯 | Loading / Empty / Error 표시 영역 |
| 툴바 (선택) | 검색, 필터, 일괄 작업 버튼 영역. 테이블 밖에 조합 |
| 셀 렌더러 | 텍스트, 숫자, 날짜, 상태 배지, 링크, 액션 메뉴 등 재사용 셀 |

## 3. API 초안 (React 가정)

```ts
type Column<T> = {
  id: string;
  header: string | ReactNode;
  accessor: (row: T) => unknown;
  cell?: (row: T) => ReactNode;      // 커스텀 렌더링
  sortable?: boolean;
  align?: "left" | "center" | "right"; // 숫자는 right 권장
  width?: number | string;
  minWidth?: number;
  hideBelow?: "sm" | "md" | "lg";     // 반응형 숨김
};

type TableProps<T> = {
  columns: Column<T>[];
  data: T[];
  rowKey: (row: T) => string;         // 필수: index를 key로 쓰지 않음
  loading?: boolean;
  error?: ReactNode;
  emptyState?: ReactNode;

  // 정렬 (controlled 우선)
  sort?: { columnId: string; direction: "asc" | "desc" } | null;
  onSortChange?: (sort) => void;

  // 선택
  selectable?: "none" | "single" | "multiple";
  selectedKeys?: Set<string>;
  onSelectionChange?: (keys: Set<string>) => void;

  // 페이지네이션
  pagination?: { page: number; pageSize: number; total: number };
  onPageChange?: (page: number) => void;

  onRowClick?: (row: T) => void;
  density?: "compact" | "default" | "comfortable";
  stickyHeader?: boolean;
  caption?: string;                   // 접근성용 표 설명
};
```

**원칙**: 정렬·선택·페이지 상태는 **controlled**(부모가 소유)로 설계해 서버/클라이언트 처리 방식 모두 지원합니다.

## 4. 상태 정의

| 상태 | 동작 |
|---|---|
| Loading (최초) | 스켈레톤 행 표시, 헤더는 유지 |
| Loading (재조회) | 기존 데이터 유지 + 상단 진행 표시 (깜빡임 방지) |
| Empty | "데이터 없음"과 "검색 결과 없음"을 구분해 문구/액션 다르게 |
| Error | 메시지 + 재시도 버튼 |
| Row hover / selected / disabled | 시각적 구분 필요 (디자인 단계에서 토큰 확정) |

## 5. 접근성

- 네이티브 `<table>`, `<thead>`, `<th scope="col">` 사용.
- 정렬 가능한 헤더는 `<button>` + `aria-sort`.
- 선택 체크박스에 행 단위 라벨 제공 ("○○ 선택").
- 행 클릭 동작이 있으면 키보드로도 동일하게 접근 가능해야 함 (행 전체를 클릭 영역으로 쓸 때 주의).
- `caption` 또는 `aria-label`로 표 목적 명시.

## 6. 반응형

- 기본: 가로 스크롤 + 첫 컬럼 고정(선택).
- 좁은 화면: `hideBelow`로 우선순위 낮은 컬럼 숨김.
- 모바일 카드형 전환은 **v1 제외** 권장 (별도 컴포넌트가 더 깔끔함).

## 7. 가정

- React + TypeScript 환경.
- 데이터는 수백 행 이하가 일반적이고, 대용량은 서버 페이지네이션으로 처리.
- 디자인 토큰(색상, 간격, 타이포)은 추후 디자인 시스템에서 정의.
- 한국어/영어 등 다국어 문구는 props로 주입.

## 8. 권장 사항

1. **v1은 작게**: 위 범위 안 기능만 구현하고, 실제 화면 2~3개에 먼저 적용해 검증.
2. **헤드리스 라이브러리 검토**: 정렬/선택/페이지 로직은 TanStack Table 같은 헤드리스 라이브러리를 쓰고 UI만 직접 만드는 쪽이 유지보수 비용이 낮습니다.
3. **기능 추가 기준 마련**: "2개 이상 화면에서 필요할 때만 코어에 추가, 아니면 해당 화면에서 조합"이라는 규칙을 둡니다.
4. **디자인과 병행**: 밀도(density), 상태 색상, 정렬 아이콘, 빈 상태 일러스트는 디자이너와 우선 합의할 항목입니다.

## 9. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 만능화로 인한 props 폭증 | 사용법 복잡, 버그 증가 | opt-in 모듈 구조, 기능 추가 기준 |
| 서버/클라이언트 처리 혼재 | 정렬·페이지 동작 불일치 | controlled API로 통일 |
| 대용량 데이터 성능 | 스크롤 끊김 | 서버 페이지네이션 우선, 필요 시 가상 스크롤 별도 도입 |
| 디자인 부재 상태에서 구현 선행 | 재작업 | 구조/API 먼저 확정, 스타일은 토큰으로 분리 |
| 접근성 누락 | 키보드/스크린리더 사용 불가 | 체크리스트를 완료 기준에 포함 |
