## 한 줄 요약

**"주문을 놓치게 만드는 문제"(알림, 누락, 로그인 풀림, 피크 시간 크래시)가 26건 중 11건이고, 이는 해지 사유 1위와 정확히 겹칩니다.** 그중 상당수가 9/18 v4.12.0 배포(토큰 저장 방식 변경, 쿠팡이츠 SDK 업데이트)와 관련 있을 가능성이 높아, 다음 스프린트는 신규 기능 없이 이 회귀를 안정화하는 데 쓰는 것을 권합니다.

## 2. 테마별 상세

### A. 주문 알림을 인지하지 못함 (5건, P0)
> "쿠팡이츠 주문이 알림음 없이 들어와서 20분 동안 몰랐어요. 손님한테 취소당했습니다." (#1)
> "알림 소리 놓쳐서 주문 취소 당한 게 이번 달만 3번. 진동이라도 같이 오면 좋겠어요." (#21)

- 하위 유형이 서로 다릅니다.
  - 소리가 아예 안 남: #1(쿠팡이츠), #9(화면 꺼짐 상태)
  - 소리가 너무 작음: #7(배민, 볼륨 최대에서도)
  - 중복 알림: #5(요기요 알림이 두 번 울림, 주문은 한 건)
  - 인지 보조 수단이 부족함: #21(진동 요청). 관련 요청으로 H의 #8(앱별 알림음 구분)이 있습니다.
- #9는 Android의 Doze/배터리 최적화나 알림 채널 설정 문제일 가능성이 큽니다. #7은 알림음을 알림(notification) 스트림으로 재생하고 있어서 미디어나 알람 볼륨과 따로 노는 문제일 수 있습니다.
- **권장 액션**
  1. 개발: 신규 주문 알림을 접수할 때까지 반복 재생하고, 알람 스트림이나 전용 채널로 재생하도록 검토합니다. 화면이 꺼져 있을 때는 foreground service와 full-screen intent로 확실히 깨웁니다.
  2. 개발: #5 요기요 중복 알림은 주문 ID 기준 dedupe를 확인합니다. 작업량이 작습니다.
  3. CS(즉시): "배터리 최적화 예외, 방해금지 모드 해제, 알림 채널 볼륨" 설정 가이드를 배포하고 A 테마 문의 매장에 직접 안내합니다.
  4. 확인: #1이 9/18 이후 건인지, 쿠팡이츠에만 집중되는지 확인합니다(SDK 업데이트 관련 여부).

### B. 쿠팡이츠 주문 누락 (1건, P0)
> "주문 누락! 쿠팡이츠 주문이 앱에 아예 안 뜬 적이 2번 있음. 쿠팡 사장님앱엔 있었음." (#13)

- 건수는 1건이지만 **제품의 핵심 가치("한 태블릿에서 다 받는다")가 깨진 사례**입니다. 리뷰(★1)로 공개되어 있고, 해지 사유 1위와 같습니다.
- 리뷰까지 쓰지 않고 조용히 해지한 매장이 더 있을 수 있어, 건수보다 실제 발생 규모가 클 가능성이 있습니다.
- **권장 액션**
  1. 개발: 9/18 이후 쿠팡이츠 수신 로그와 쿠팡 측 주문 건수를 매장 단위로 대조해 누락률을 정량화합니다. 이게 가장 먼저입니다.
  2. 개발: SDK 업데이트 전후의 웹훅/폴링 실패, 재시도 로직을 점검합니다.
  3. 단기 안전장치: 플랫폼 주문 수와 앱 수신 수가 어긋나면 매장과 내부에 경고를 보내는 기능을 검토합니다.
  4. CS: #13 매장에 개별 연락하고, 누락 일시를 받아 로그 대조에 씁니다.

### C. v4.12.0 이후 로그인 풀림 (3건, P0)
> "로그아웃 문제요. 9/18 업데이트(v4.12.0) 이후부터 그래요." (#22)
> "비밀번호 저장했는데도 매일 로그아웃." (#15)

- 원인 후보가 명확합니다. v4.12.0의 "로그인 토큰 저장 방식 변경"과 시점이 일치합니다. 리프레시 토큰 만료나 저장 실패, 앱 재시작 시 토큰 미복원 등을 의심해 볼 수 있습니다.
- **A/B와 연결되는 이유**: 아침에 로그아웃된 상태를 모르고 오픈하면 첫 주문들을 받지 못합니다. 불편 문제가 아니라 주문 누락 문제로 봐야 합니다.
- **권장 액션**
  1. 개발: 핫픽스를 최우선으로 진행합니다. 재현 범위가 좁고 원인 후보가 분명해 작업량 대비 효과가 가장 큽니다.
  2. 개발: 로그아웃 상태면 화면 전체에 "주문을 받을 수 없음" 경고를 표시합니다.
  3. CS: 알려진 이슈로 공지하고 수정 일정을 안내합니다.

### D. 점심 피크 시간 지연/크래시 (2건, P1)
> "점심 피크 때 주문 접수 버튼 눌러도 반응이 5초 넘게 없음. 태블릿은 갤럭시탭 A7 라이트." (#2)
> "주문 접수 누르면 가끔 앱이 튕겨요. 오후 12시~1시 사이에 특히." (#18)

- 두 건 모두 12~1시에 집중되어 있습니다. 부하(동시 주문, 서버 응답)나 저사양 기기의 메모리 문제로 보입니다.
- 크래시는 접수가 안 되는 문제라 P0에 가깝지만, 건수와 재현 정보가 부족해 P1로 뒀습니다.
- **권장 액션**
  1. 개발: 크래시 리포트(Crashlytics 등)를 기기와 시간대별로 분석하고, 접수 API의 피크 시간 p95 응답 시간을 확인합니다.
  2. 확인: 저사양 기기 비중과 해당 기기의 크래시율을 봅니다.

### E. 3사 연동 불일치 (3건, P1)
> "쿠팡이츠 품절 연동 안 되는 거 언제 고쳐지나요? 벌써 세 번째 문의." (#19)
> "영업 종료 버튼 한 번에 3사 다 닫히면 좋겠음. 지금은 요기요만 따로 해야 함." (#12)

- 품절 처리가 반영되지 않으면 품절 메뉴 주문이 들어오고, 매장이 직접 취소하게 되어 매장 지표가 떨어집니다.
- #19는 **반복 문의(3번째)**입니다. 이 고객은 해지 위험이 높습니다.
- #12는 요청 형태지만 실제로는 "통합 앱"이라는 약속과의 기능 공백입니다.
- **권장 액션**
  1. 개발: 쿠팡이츠 품절 API가 SDK 업데이트 이후 깨진 것인지, 원래 미지원인지 확인합니다(1~2 person-day).
  2. PM: 플랫폼 API 제약 때문이면 앱 안에 "쿠팡이츠는 사장님앱에서 직접 처리 필요"라고 명시합니다.
  3. CS: #19 고객에게 ETA나 현황을 먼저 연락합니다.

### F. 정산 금액 불일치 (2건, P1)
> "정산 화면에서 쿠팡이츠 수수료가 실제랑 달라요. 9월 1주 차 기준 8천원 차이." (#6)

- 금액은 작아도 "숫자를 믿을 수 없다"는 신뢰 문제가 되어 세무/매출 관리 용도(#16과 연결) 전체를 흔들 수 있습니다.

  2. 단기: 정산 화면에 "예상치이며 플랫폼 정산과 다를 수 있음, 반영 항목: ..."을 명시합니다.

## 4. 가정과 리스크

**가정**
- 각 의견의 정확한 날짜가 없어 v4.12.0과의 연관성은 **추정**입니다. #22만 명시적으로 9/18 이후라고 밝혔습니다.
- 각 번호를 서로 다른 매장으로 가정했습니다. #3과 #15처럼 같은 매장의 중복 문의일 수도 있습니다.
- 공수는 대략적인 추정입니다. 개발 리드가 확인해야 합니다.

**리스크 / 해석상 주의**
- **표본이 작습니다.** 3,800곳 중 26건이고 테마별로 1~5건이라, 건수 순위를 영향도 순위로 읽으면 안 됩니다. 이 자료의 심각도는 건수가 아니라 "주문 손실 여부" 기준입니다.
- **채널 편향**이 있습니다. 플레이스토어 리뷰는 극단적인 경험이 과대 대표되고, 전화 메모는 요약 과정에서 정보가 빠졌을 수 있습니다.
- **말 없는 이탈**: 주문 누락을 겪은 매장은 문의 없이 해지할 수 있습니다. B는 1건이지만 실제 규모는 로그 대조 전까지 알 수 없습니다.
- 쿠팡이츠 품절 문제가 플랫폼 API 제약이면 우리 쪽에서 고칠 수 없어, 기대 관리가 필요합니다.

**회의 전에 있으면 좋은 데이터**
1. 9/18 전후 크래시율과 로그아웃 이벤트 수
2. 쿠팡이츠 주문 수신 건수와 플랫폼 주문 건수의 대조(샘플 매장이라도)
3. 9월 해지 매장의 해지 사유와 v4.12.0 업데이트 여부
4. 9/18 전후 CS 콜량과 대기 시간
